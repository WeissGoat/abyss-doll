# 正式纵切 UI 与素材覆盖矩阵

> **定位：** 把 `09` 路线和 `11` 批次矩阵翻译成美术侧 UI / 素材覆盖表。目标是先把需要的 UI 设计纳入系统，再按 Manifest 流程生产素材。

---

## 1. 当前覆盖结论

截至 2026-06-08，active `screen_layouts.json` 已覆盖 21 个界面。其中 V2-A 五个核心流程界面已经迁移为 Formal V2 active 规格：

```text
workshop_main
combat_hud
inventory_loot
dungeon_map
settlement
```

其余 16 个界面仍保持 Formal V1 active 规格：

```text
sell_panel
prosthetic_panel
layer_select
safe_room
stairs_room
maintenance_panel
daily_bill_report
shop_staging
business_settlement
order_board
rumor_board
faction_shop
doll_interaction
scenario_event
doll_room
chassis_upgrade_panel
```

这些界面已经可以进入素材生产、程序接入或运行时截图验收。V2-A 现在以 active `screen_layouts.json` 为程序和美术工具合同，不再只是 `formal_v2/*.md` 草案。A4 出货分配、营业结算演出、订单、传闻、势力商店、人偶交互、剧本事件和人偶房间界面仍处于 Formal V1 active 规格；已补齐对应 seed / Manifest / Prompt / Spec 入口，后续按可接入清单推进素材入库、程序接入和可玩路径绑定。

近期执行不再新增与当前纵切无关的横向界面。latest 可接入素材清单中的 `program_integrate` 队列当前为 0，表示 Approved 资源没有待程序登记的 VisualID；latest Formal V1 验收队列显示 21 个 active 界面均已 captured，`Program add capture action=0`，表示屏幕层面的 ArtAcceptance 截图覆盖已补齐。上述两项只能证明“资源登记完成”和“运行时截图覆盖完成”，不等于玩家已经能从正常主流程进入这些界面，也不等于界面按钮已经接入真实后端操作。

素材覆盖、缺图生成、截图覆盖、可玩接入和素材质量分开判断：`可接入素材清单.md` 回答“程序现在能接什么 / 美术还缺什么”；`缺图生成计划.md` 回答“哪些 generate_needed 新素材可以直接跑图”；`FormalV1验收队列.md` 回答“哪些仍为 Formal V1 的 active 界面缺截图或可交美术审图”；`素材质量替换清单.md` 回答“哪些 Approved 素材仍是 local_v0 / placeholder，后续要同名替换”。当前缺图队列为 `generate_needed=58`，可接入队列为 `program_integrate=0`，质量替换清单为 `technical_fix=0`、`visual_v2_replace=121`。`acceptance_needed=191` 是按单个 VisualID 统计的运行时截图验收或 Manifest 状态回填队列，不等同于 191 个界面缺程序接入。4 个 P0 新节点图标已通过 NovelAI 验证并同步为 `formal_ai_v2`，因此不再进入替换队列。

程序侧后续声明某个 Formal V1 界面“可玩接入完成”时，必须额外满足两项：玩家主流程可达，以及关键按钮 / 操作调用真实后端或领域服务形成闭环。只通过 ArtAcceptance、debug 入口、验收专用 preview 对象或只读数据快照展示的界面，只能标记为“资源 / 截图接入完成”或“只读预览”，不能标记为“可玩完成”。

Formal V2 当前口径：V2-A 的 `workshop_main`、`combat_hud`、`inventory_loot`、`dungeon_map`、`settlement` 已由用户评审概念方向后迁移为 active 规格；V2-B / V2-C 仍是 draft，不作为本批次程序接入口或跑图入口。后续新增界面或结构重做仍先写设计草案，经确认后再进入 active `screen_layouts.json`、Manifest 和跑图队列。

## 3.1 Formal V2 UI Skin 优先资产

Formal V2 UI Skin 详细清单见 `美术文档/ui_design/formal_v2/00_formal_v2_ux_ui_overview.md` 的 `4.4 Formal V2 UI Skin 资产清单`。覆盖矩阵只记录本轮优先级：

| 优先级 | 资产组 | 代表 VisualID / 组件 | 处理口径 |
|---|---|---|---|
| P0 | 主面板、主/次/危险按钮、列表行 | `ui_panel_main`、`ui_panel_info`、`ui_button_*`、`ui_list_row_*` | 所有 FormalV2 屏幕都会暴露，优先保证统一风格和 nine-slice 可用。 |
| P0 | 地图节点、路线、背包格、战斗状态条 | `ui_dungeon_node_plate`、`ui_dungeon_route_line`、`ui_inventory_*`、`ui_combat_status_bar_*` | V2-A 的地图、战斗、清点直接依赖，优先进入质量替换或缺图复核。 |
| P0 | 战斗反馈、结果徽记 | `ui_combat_feedback_*`、`ui_combat_grid_lock_marker`、`ui_settlement_outcome_*` | 影响战斗可读性和结算结果识别；已入库 local_v0 的继续走 `visual_v2_replace`。 |
| P1 | 标题分隔、弹窗壳、锁定/装备态、共享系统图标 | `ui_title_divider`、`ui_icon_locked`、`ui_icon_equipped`、`ui_icon_*` | 用于提高正式感和统一性；按 V2-B/C/D active 顺序推进。 |

UI Skin 只承载形状、材质、状态和装饰，不烘焙可读文字、数值、按钮文案或配置字段。

详细清单见 `美术文档/ui_design/formal_v2/00_formal_v2_ux_ui_overview.md` 的 `4.5 Formal V2 场景 / 背景资产清单`。

环境背景默认 `Alpha=false`。未进入 active 的背景规划不能触发程序接入或批量跑图。

## 7. 执行规则

1. 新 UI 或结构重做先写 `formal_v1/*.md` 草案，用户确认后再进入 `screen_layouts.json`。
2. active `screen_layouts.json` 更新后，先跑 `Validate-UIDesign.ps1`，再补 `art_requirements_seed.json`、Manifest 和提示词。
3. 每轮生成、预处理或 Approved 同步后，刷新 `可接入素材清单.*` 并留快照。
4. 每轮 `generate_needed` 队列变化或生成额度探测后，刷新 `缺图生成计划.*` 并留 `art_generation_plan_snapshots/` 快照。
5. 每轮技术修复或质量替换后，刷新 `素材质量替换清单.*` 并留 `art_quality_snapshots/` 快照；已接入素材的 Visual V2 替换必须通过 `CandidateBatchID` 和 `QualityTier` 记录，不回退原 `Status`。
6. 每轮 Visual V2 队列变化或生成额度探测后，刷新 `VisualV2生成计划.*` 并留 `visual_v2_plan_snapshots/` 快照。`Recommended Execution Batches` 是默认执行顺序，除非用户明确调整，不一次性跑完 121 项。
7. 进入跑图、Approved 同步或程序交接前，先按 Formal V2 总览 `8.1 静态美术验收门禁` 区分 `concept_ready`、`layout_ready`、`prompt_ready`、`approved_ready` 和 `runtime_validated`；没有 Unity 验收证据时不得标记运行时通过。
8. 未进入 active 的 UI 不作为程序接入口，也不作为批量跑图入口。
9. Draft UI 队列进入 active 时必须同步更新本文、对应 `formal_v1/` 或 `formal_v2/` 总览、`screen_layouts.json` 和 `versions/migration_log.md`。
