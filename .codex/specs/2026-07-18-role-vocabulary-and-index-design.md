# Project P3 Role 词表与知识索引归属设计

状态：待用户书面复核
日期：2026-07-18
范围：Role 概念、文档元数据归属、知识索引和入口说明

## 1. 背景

当前项目把 `主策`、`主程`、`主美`、`实现 Owner`、`0-12 小时细案 Owner`、`剧情 Owner` 和 `专工` 混在 Role、任务定位和工作环节中。这样会导致知识索引把任务分工名称误当成专业职能，跨职能模块文档也被迫归入某个单一职能。

本次只调整 Role 概念和知识索引归属，不改变 Owner 的责任流水、执行 / 验收流程、状态回写矩阵、P3 Mission 机制或业务进度。

## 2. 目标与非目标

### 2.1 目标

- 建立稳定、可索引的 Role 词表。
- 把 `Owner` 定义为跨职能模块整体责任 Role。
- 把 `剧情` 定义为独立专业 Role，不并入策划。
- 把 `策划`、`程序`、`美术` 定义为专业 Role。
- 允许 Owner 在处理中切换策划、剧情、程序、美术等专业视角，但 Owner 定位不变化。
- 让 `docs_index.json` 的 active 文档不再出现旧的 Owner 变体或主职能称谓。

### 2.2 非目标

- 不重写 Owner 责任流水。
- 不重新设计执行、自验、外部验收和状态回写流程。
- 不新增专工 Role；专工只是独立 Agent 处理某个 Role 范围工作的使用方式。
- 不新增剧情状态体系；优先复用现有 `设计文档/剧情/README.md` 作为剧情入口。
- 不改变 T0、T1、配置、Unity、美术或验收业务事实。

## 3. Role 词表

正式 active Role 词表如下：

| Role | 定位 |
|---|---|
| `全局` | 项目级入口、状态、根规则和跨项目知识库规范 |
| `游戏导演` | 玩家体验主线、系统开放节奏、优先级和总体体验口径 |
| `Owner` | 对一个完整模块或玩家结果进行跨职能统筹和整体负责 |
| `剧情` | 剧情大纲、叙事结构、角色关系、对白节奏、CG / 漫画叙事和剧情一致性 |
| `策划` | 游戏系统规则、数值、配置意图、经济和玩法设计 |
| `程序` | Unity、领域服务、UI 程序、Validator、工具和自动化 |
| `美术` | UI 视觉、素材、Manifest、VisualID 和运行时视觉验收 |
| `知识库` | 文档元数据、索引、双向关系和阅读入口治理 |

### 3.1 Owner 规则

`Owner` 是 Role，不是 `实现 Owner` 或 `细案 Owner` 的前缀。Owner 负责完整模块，例如 `T0-01A`，可以在处理中切换专业工作视角：

```text
Owner
  -> 策划视角：规则、玩家路径、配置意图
  -> 剧情视角：叙事节奏、对白、CG / 漫画一致性
  -> 美术视角：UI、镜头、素材和视觉表现
  -> 程序视角：领域服务、运行时接入和验证
```

切换专业视角不改变 Owner 的整体责任定位。

### 3.2 非 Role 名称

- `实现 Owner`、`0-12 小时细案 Owner`、`剧情 Owner`：旧的组合称谓，不能继续作为 active Role。
- `主策`、`主程`、`主美`：资历 / 验收称谓，不作为 Role 词表值。
- `专工`：任务处理方式，不是 Role。
- `执行`、`自验`、`外部验收`、`回写`：工作环节，不是 Role。
- `P3 Mission`：长期任务机制，不是 Role。

## 4. 文档元数据归属映射

`role` front matter 表示文档主要专业归属或整体责任归属，不表示当前处理环节。

| 文档类别 | 新 `role` |
|---|---|
| `AGENTS.md`、`PROJECT_STATUS.md`、根规则、知识库规范 | `全局` |
| `版本规划/14_0-12小时候选主循环细案设计.md` | `游戏导演` |
| `版本规划/0-12小时细案/T0-01_序章首次循环.md` | `Owner` |
| `T0-01` 总方案、`T0-01A` 实现设计、开发方案、T0-VAL-01 Owner 文档 | `Owner` |
| `设计文档/剧情/README.md`、剧情大纲、序章演出与对话节奏 | `剧情` |
| GDD、规则卡、配置设计和数值模型 | `策划` |
| Unity 架构、开发文档、程序验证和 UI 程序契约 | `程序` |
| 美术路线、UI 规格、Manifest、素材和视觉验收 | `美术` |
| 文档索引、视图、元数据与关系校验 | `知识库` 或 `全局`，按现有文档职责保留 |

历史 / 归档文档可以保留追溯信息，但不应继续作为 active Role 使用旧组合称谓。兼容入口可保留 `兼容`，但不参与 active Role 路由。

## 5. 文档修改范围

### 5.1 根入口与全局协议

- `AGENTS.md`：把 Role 路由改为“Owner、游戏导演、剧情、策划、程序、美术、知识库”；删除 `实现 Owner`、`细案 Owner`、`UI 程序` 顶层 Role。
- `rules/02_智能体任务路由与完成协议.md`：只修改 Role 定义、Owner 定义和旧称谓；保留执行、验收、回写协议不变。

### 5.2 知识库入口

- `知识库/README.md`：增加正式 Role 词表，说明 `role` 元数据不填写专工、执行者或验收者。
- `知识库/views/director.md`：增加 Owner 和剧情入口说明。
- `知识库/views/art.md`、`知识库/views/design.md`、`知识库/views/program.md`：统一使用美术、策划、程序 Role 语义。
- `设计文档/剧情/README.md`：继续作为剧情 Role 阅读入口，不新增重复的剧情视图。
- `agent_status/README.md`：说明状态页按职能维护，剧情使用现有剧情事实入口和对应状态记录。
- `GEMINI.md`：同步 Role 词表和 Owner 切换专业视角的定义。

### 5.3 文档元数据

至少更新以下 active 文档的 front matter：

- `0-12 小时细案 Owner` -> `游戏导演` 或 `Owner`，按第 4 节映射。
- `实现 Owner` -> `Owner`。
- `剧情 Owner` -> `剧情`。
- `主策 / 主程 / 主美` -> `策划 / 程序 / 美术`。

### 5.4 索引校验

在 `tools/docs/validate_docs.py` 增加 active Role 词表校验，允许：

```text
全局、游戏导演、Owner、剧情、策划、程序、美术、知识库
```

历史、归档和兼容文档允许保留旧值用于追溯，但不能参与 active Role 路由。

重新生成：

```powershell
.\tools\docs\Generate-DocsIndex.ps1
.\tools\docs\Validate-Docs.ps1
```

## 6. 验收标准

- `AGENTS.md` 的 Role 路由不再列出实现 Owner、细案 Owner、剧情 Owner、主策、主程、主美、专工或 UI 程序顶层 Role。
- `rules/02` 能明确区分 Owner Role、专业 Role 和工作环节。
- `设计文档/剧情/` 在索引中以 `剧情` Role 出现。
- T0-01 / T0-01A 的完整跨职能文档在索引中以 `Owner` Role 出现。
- active 文档的 Role 全部来自正式词表。
- `docs_index.json` 能按新 Role 聚合文档，旧 Owner 变体不再出现在 active Role 统计中。
- 文档索引和双向关系校验通过。
- 项目当前阶段、T0 / T1 状态、执行 / 验收流程没有被本轮修改。

## 7. 设计结论

采用“Owner 作为跨职能整体责任 Role，剧情作为独立专业 Role，策划 / 程序 / 美术作为专业 Role，执行 / 验收作为流程环节”的模型。`全局` 仅用于真正的项目级文档，不再承接 T0-01A 这类模块 Owner 文档。
