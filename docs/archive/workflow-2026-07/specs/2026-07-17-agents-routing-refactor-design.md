# Project P3 AGENTS 职责路由重构设计

> 历史设计：已于 2026-07-17 实施（`b0ba7e8`、`4ec62ef`）。现行规则以 `AGENTS.md` 与 `rules/02_智能体任务路由与完成协议.md` 为准；正文中的“待用户书面复核”等状态为当时记录。

状态：待用户书面复核
日期：2026-07-17
范围：`AGENTS.md`、根目录全局 agent rules 入口及其既有职能路由关系

## 1. 背景与问题

当前 `AGENTS.md` 同时承担开工入口、事实来源说明、角色手册、职能专项规则、Owner 工作流、完成协议和 Git 规范。内容完整，但职责层级混合，主要造成以下问题：

1. Agent 很难在开工后快速判断自己属于哪个任务角色、下一份必读文档是什么。
2. 各职能的必读文件、工作边界和完成回写在 `AGENTS.md`、`agent_status/*.md`、`知识库/views/*.md` 及职能事实文档中重复出现。
3. 美术后端选择、UGUI 约束、配置准入等专项规则写入根入口，导致根入口随专业规则演进频繁变化。
4. 当前状态、稳定规则和操作命令混在同一文件，难以判断一段内容应该由谁维护。
5. 完成协议较长，且与角色章节中的回写要求重复，修改时容易漏同步。

本次重构不以追求最短文件为目标，而以“Agent 能快速选对职责路径，并且同一规则只维护一次”为目标。

## 2. 设计目标

### 2.1 主要目标

- 让新 Agent 在约 30 秒内完成任务分类、角色选择和首读文档定位。
- 让 `AGENTS.md` 只维护全局入口与硬边界，不再复制职能手册。
- 将 Owner 工作流、验收边界和状态回写规则集中到一个稳定协议中。
- 保持现有 GDD、开发文档、美术文档、状态页和知识库视图的事实来源地位。
- 降低后续调整某个职能规则时的跨文件同步数量。

### 2.2 非目标

- 不重做项目知识库目录。
- 不新增一套角色状态页或进度表。
- 不把 `知识库/views/*.md` 升级为事实来源。
- 不把 `agent_status/*.md` 变成稳定规则手册。
- 不在本轮改变游戏导演、细案 Owner、实现 Owner和职能总监的责任关系。
- 不清理当前业务状态、T0 进度或历史验收记录。

## 3. 方案比较

### 3.1 方案 A：继续保持单文件，仅压缩和重排

优点是迁移成本低、链接最少。缺点是职能专项规则仍会持续进入根文件，长期会重新膨胀，重复维护问题只能缓解，不能解决。

### 3.2 方案 B：每个角色拆一份独立规则文件

优点是角色边界最直观。缺点是会与现有职能视图、状态页和事实文档形成第二套路由体系，新增文件多，双向关联和维护成本高。

### 3.3 方案 C：轻入口 + 单一全局协议 + 现有职能入口

根 `AGENTS.md` 只负责选择路径和声明硬边界；新增一个全局协议文件集中承接 Owner 工作流、验收与回写；职能细节继续由现有视图、状态页和事实文档承接。

本设计采用方案 C。它增加的稳定文档最少，同时能真正分离“路由、规则、状态、专业事实”四类内容。

## 4. 目标信息架构

```text
AGENTS.md
├─ 入口定位与事实优先级
├─ 30 秒开工流程
├─ 任务类型 -> 默认角色 -> 首读入口
├─ 全局不可违反边界
├─ 验证与完成摘要
└─ 详细协议链接
        ↓
rules/02_智能体任务路由与完成协议.md
├─ 任务角色定义
├─ 细案 Owner / 实现 Owner / 专工 / 总监关系
├─ 实现切片承接字段
├─ Owner 自验与外部验收边界
├─ 状态回写矩阵
├─ 验证受限与阻塞记录
└─ Git 与脏工作区完成要求

现有职能入口
├─ 知识库/views/*.md：阅读导航
├─ agent_status/*.md：当前状态与交接
├─ 设计文档/*：策划和配置事实
├─ 开发文档/*：程序契约和工程规则
├─ 美术文档/*：视觉规格和资产流水线事实
└─ tools/*/README.md：命令与工具操作说明
```

## 5. `AGENTS.md` 目标结构

目标长度建议为 120 至 180 行。长度是约束指标，不是验收目标；若删减会损害硬规则表达，可以适当超过。

### 5.1 元数据与入口声明

保留 YAML 元数据、文件定位和更新规则。正文开头只说明：

- 这是所有复制 Agent 的根入口。
- 先分类任务，再按路由读取，不要求所有 Agent 通读所有职能手册。
- 事实冲突时采用“更具体、更新、active、被当前入口引用”的来源。

### 5.2 30 秒开工流程

统一为五步：

1. 读取 `PROJECT_STATUS.md` 和 `agent_status/director.md`，确认阶段与全局阻塞。
2. 根据任务特征选择默认角色。
3. 读取对应职能视图和状态页。
4. 读取目标细案或领域事实文档及相关专项规则。
5. 实际改动前运行健康检查；长任务按 P3 Mission 路由。

### 5.3 任务职责路由表

| 任务特征 | 默认职责 | 首读入口 | 进一步读取 |
|---|---|---|---|
| 玩家体验、开放节奏、全局优先级 | 游戏导演 / 制作人 | `知识库/views/director.md` | `13`、`14`、目标细案、`09`、`11` |
| T0-T4 某个时长段的完整游戏设计 | 0-12 小时细案 Owner | `知识库/views/director.md` | `14`、目标细案、相关 GDD / 美术 / 开发事实 |
| 已完成细案中的单一玩家结果落地 | 实现 Owner | 目标细案 + 受影响职能视图 | 对应 GDD、配置、开发、美术事实文档 |
| GDD、数值、配置意图或配置源 | 主策 / 数值 | `知识库/views/design.md` | `agent_status/design.md` 和目标设计事实 |
| Unity、架构、领域服务、自动测试 | 主程 / Unity | `知识库/views/program.md` | `agent_status/program.md` 和开发规则 |
| UI、视觉、素材生产、运行时美术验收 | 主美 / UI | `知识库/views/art.md` | `agent_status/art.md` 和美术事实文档 |
| 纯 UGUI 表现层接入 | UI 程序职责 | 程序视图 + 美术视图 | 表现层、视觉资源和 UI handoff 规范 |
| 文档元数据、索引、关系网 | 知识库智能体 | `知识库/README.md` | `rules/01`、工具脚本和核心入口 |
| 长期、拆分、恢复或持续执行 | P3 Mission | `p3-mission` skill | 已批准的详细来源材料 |

路由表只决定“先去哪”，不复制目标文档中的稳定专业规则。

### 5.4 全局不可违反边界

根入口只保留下列跨职能硬边界：

- 新增、重写、拆分、归档文档前必须读取 `rules/01`。
- `配置表(JSON)` 是源，StreamingAssets 配置是生成副本。
- 运行时 UI 使用纯 UGUI；详细工程约束路由到开发规则。
- Approved、IncomingAI、generated 和 submodule 的写入边界。
- 不覆盖或回滚用户及其他 Agent 的无关改动。
- 没有验收证据不得标记完成。
- 实现 Owner 必须回写所有受影响职能状态页。

其余专业细节从根入口移出。

### 5.5 完成摘要

根入口只保留简短完成检查：

1. 验证结果和限制已记录。
2. 受影响事实文档已更新。
3. 受影响状态页已更新。
4. 跨职能交接或项目阻塞已同步 `PROJECT_STATUS.md`。
5. 只暂存本任务相关文件。

详细条件链接到 `rules/02_智能体任务路由与完成协议.md`。

## 6. 新增全局协议文件

新增 `rules/02_智能体任务路由与完成协议.md`，其职责是维护稳定的跨职能执行协议，不记录项目当前进度。

### 6.1 应迁入的内容

- “细案 Owner 统一设计 + 实现 Owner 纵切负责 + 职能总监验收”的完整定义。
- 实现切片承接所需字段。
- 证据审计到状态回写的责任流水。
- 专工只能交付指定产物、不得改变体验或规则方向的边界。
- Owner 自验与外部验收的区别。
- 不得重复派发、不得无证据完成的规则。
- 状态页、事实文档、`PROJECT_STATUS.md`、`13/14/09` 的回写判定矩阵。
- Git 脏工作区、暂存范围和 Unity `.meta` 的完成要求。

### 6.2 不应迁入的内容

- 当前 T0/T1 进展。
- 某个 UI 版本、图片后端或配置批次的当前状态。
- 各职能的完整必读文件清单。
- 具体工具命令说明。
- 领域实现细节。

## 7. 内容迁移映射

| 当前内容 | 目标位置 |
|---|---|
| 当前事实来源长列表 | `AGENTS.md` 的五步开工流程 + 路由表 |
| 当前开发文档关系图 | `知识库/views/director.md` 或版本规划 README；根入口只留优先级摘要 |
| 长任务协议 | 根入口保留触发条件，详细内容留在 P3 Mission skill / README |
| 角色总表 | 压缩为任务职责路由表 |
| 全局工作模式长说明 | `rules/02` |
| 实现切片承接字段 | `rules/02` |
| 游戏导演详细版本规划规则 | 导演视图、状态页和版本规划 README |
| 美术后端、UI 版本、流水线命令 | 美术文档和对应 skill / 工具 README |
| 策划需求文档与配置准入细则 | 设计文档、配置 gate 和设计视图 |
| 程序 / UI 程序详细工程规则 | `开发文档/rules/*` 和程序视图 |
| 知识库“本轮目标” | `PROJECT_STATUS.md` 或知识库状态记录，不留在稳定入口 |
| 完成长清单与 Git 规范 | `rules/02`；根入口留摘要 |

## 8. 路由冲突与兜底规则

当一个任务同时命中多个角色时，按玩家结果选择一个主责任角色，其他角色作为受影响职能：

1. 已有完成细案且目标是落地玩家结果：默认实现 Owner。
2. 目标是补齐时长段游戏设计：默认细案 Owner。
3. 目标是改变全局体验、系统开放或优先级：默认游戏导演 / 制作人。
4. 目标仅是专业验收或专项事实修订：默认对应职能总监。
5. 目标仅是耗时批处理：可以使用专工，但必须有 Owner 提供输入、输出和验收标准。

如果任务没有详细来源材料，不得直接创建实现 Mission 或进入大规模落地；先补对应设计或计划事实。

## 9. 状态与事实的数据流

```text
用户目标
  -> AGENTS 选择职责路径
  -> 职能视图定位必读材料
  -> 状态页确认当前进度与阻塞
  -> 领域事实文档决定规则和实现
  -> rules/02 约束执行、验收与回写
  -> 事实文档记录结果
  -> 状态页记录最新状态
  -> 必要时 PROJECT_STATUS / 13 / 14 / 09 记录全局变化
```

状态页不得反向覆盖领域事实；视图不得反向覆盖状态页或领域事实；根入口不得记录当前业务进度。

## 10. 实施顺序

1. 新增 `rules/02_智能体任务路由与完成协议.md`，先承接要迁出的稳定规则。
2. 更新 `rules/README.md`，登记新协议的职责。
3. 重写 `AGENTS.md` 为轻入口，并保留所有必要硬边界。
4. 检查 `知识库/views/*.md` 是否能完整承接各职能首读导航，仅补缺失路由，不复制规则。
5. 清除 `AGENTS.md` 中当前状态、专业命令和重复必读清单。
6. 更新必要的双向 `related`、元数据日期和同步规则。
7. 重新生成文档索引并运行文档校验。
8. 运行 Agent 健康检查，人工模拟典型任务路由。

实施时必须基于当时工作区重新检查 `AGENTS.md` 的未提交改动，不能覆盖本设计之外的新增规则。

## 11. 验证方案

### 11.1 自动验证

- `tools/docs/Generate-DocsIndex.ps1` 成功。
- `tools/docs/Validate-Docs.ps1` 成功。
- `tools/agent/Invoke-AgentHealthCheck.ps1` 不出现由本次重构新增的 ERROR。
- `rg` 检查 Owner 工作流、完成判定、配置源边界等关键规则在 active 文档中均有且只有一个详细承接位置。

### 11.2 人工路由样例

至少模拟以下任务，确认能在根入口快速找到正确路径：

1. “补 T2 2-5 小时完整设计。”
2. “实现 T0-01B 的浅缘遭遇玩家结果。”
3. “修复背包拖拽规则 bug。”
4. “生成并接入一批正式 CG。”
5. “调整经济配置并同步 Unity。”
6. “更新文档元数据和双向关联。”
7. “恢复一个中断的长期任务。”

每个样例应能明确回答：默认角色、首读入口、事实来源、允许修改范围、验证入口和状态回写位置。

## 12. 风险与控制

### 12.1 迁移时遗漏硬规则

控制方式：先建立 `rules/02`，再删减根入口；使用关键语句清单逐项核对，不直接从根入口大段删除。

### 12.2 新协议成为第二套事实来源

控制方式：`rules/02` 只定义跨职能工作方式，不定义游戏规则、程序实现、视觉规格或当前状态。

### 12.3 职能视图继续复制专业规则

控制方式：视图只维护阅读顺序和入口说明，详细内容必须链接到事实文档。

### 12.4 根入口再次膨胀

控制方式：新增内容进入 `AGENTS.md` 前必须满足“所有 Agent 都需要、属于跨职能硬边界、无法由现有规则入口承接”三个条件。

### 12.5 脏工作区覆盖他人改动

控制方式：实施前单独审计 `git diff -- AGENTS.md`，按语义迁移当前工作区版本，不以 HEAD 旧版本覆盖；只暂存本任务涉及文件。

## 13. 验收标准

设计实施完成需同时满足：

- `AGENTS.md` 能让 Agent 在一次阅读中完成任务分类和首读定位。
- `AGENTS.md` 不再包含当前业务进展和长篇职能专项细则。
- Owner 工作流、验收和回写规则集中在唯一全局协议中。
- 每个职能仍能通过现有视图、状态页和事实文档获得完整上下文。
- 不新增第二套状态页、进度表或角色手册体系。
- 文档索引、双向关联和健康检查通过。
- 七个典型任务路由样例均能得到唯一或有明确主次的职责路径。
- 当前工作区中已有的有效 AGENTS 新规则没有在重构中丢失。

## 14. 设计结论

采用“轻入口 + 单一全局协议 + 现有职能入口”。本轮结构重构的本质不是简单拆文件，而是明确四类信息的唯一归属：

- `AGENTS.md`：路由与全局硬边界。
- `rules/02`：稳定的跨职能执行协议。
- `知识库/views`：阅读导航。
- 状态页和领域文档：当前状态与专业事实。

该结构优先提升职责路由清晰度，同时通过唯一归属减少重复维护成本。
