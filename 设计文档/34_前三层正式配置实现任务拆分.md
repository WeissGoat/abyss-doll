# 前三层正式配置实现任务拆分

> **定位：** 本文把 `31` / `32` / `33` 的前三层配置落地设计拆成后续可派发的配置实现任务。它不直接修改 JSON，也不表示配置已经完成；它只定义后续进入配置实现时，每个任务应该改哪些源配置、引用哪些策划事实来源、按什么顺序执行、交付什么证据。具体 Validator 与固定 seed 样例见 `35_前三层正式配置Validator与固定Seed验收样例.md`。

---

## 1. 总原则

### 1.1 为什么需要本文件

`31` / `32` / `33` 已经完成“改 JSON 前的策划清单”，但它们仍是按层级写的设计文档。后续真正落配置时，如果直接从三份大文档派发任务，容易出现三个问题：

| 风险 | 后果 | 本文处理方式 |
|---|---|---|
| 把设计完成误判为配置完成 | 职能状态页错误收口。 | 每个任务单独记录“配置实现输出”和“验收证据”。 |
| 跨域引用断裂 | 怪物引用不存在的奖励，地图引用不存在的怪物。 | 先 Items，再 Rewards，再 Monsters，再 Dungeons，再 Orders / Events。 |
| 同一系统重复派发 | 不同 agent 重复改同一层同一配置域。 | 使用稳定 TaskID、`56` 准入门禁和 `agent_status/design.md` 状态防重复。 |

### 1.2 配置源边界

后续配置实现只允许修改 `配置表(JSON)` 源数据和必要的配置 README / Validator 文档；不要手写 `UnityClient/Assets/StreamingAssets/Configs` 运行时副本。

```text
配置事实来源：配置表(JSON)/
运行时副本：UnityClient/Assets/StreamingAssets/Configs/
同步方式：.\tools\config\Sync-Configs.ps1 -Clean
```

### 1.3 任务状态口径

本文任务状态不替代 `agent_status/design.md`、`09` 或 `PROJECT_STATUS.md`。后续执行任务时：

1. 先按 `56_正式配置源落地准入门禁.md` 确认对应任务是否达到 `设计准入`。
2. 配置 JSON 真正修改并通过校验后，才能在 `agent_status/design.md` 把对应任务标为 `配置完成` 或 `验收中`。
3. 只有程序、配置、表现和验收都达到节点门禁，才能在跨职能状态中称为 `已完成`；本文和 `09` 不维护详细执行分表。

## 2. 全局执行顺序

前三层正式配置实现按以下顺序推进：

| 顺序 | 批次 | 原因 |
|---:|---|---|
| 1 | `L1-ITEMS` -> `L2-ITEMS` -> `L3-ITEMS` | 物品是奖励、订单、事件、房间记忆和经济回流的基础引用。 |
| 2 | `L1-REWARDS` -> `L2-REWARDS` -> `L3-REWARDS` | 奖励表需要引用已存在物品。 |
| 3 | `L1-MONSTERS` -> `L2-MONSTERS` -> `L3-MONSTERS` | 怪物需要引用奖励表和 CombatVisualID。 |
| 4 | `L1-DUNGEONS` -> `L2-DUNGEONS` -> `L3-DUNGEONS` | 地图节点池需要引用怪物、奖励、Boss 和事件。 |
| 5 | `L2-ORDERS` -> `L3-ORDERS` | 订单依赖物品、奖励和层级目标。 |
| 6 | `L3-EVENTS-RUMORS-MEMORY` | 第三层路线侵蚀、污染提示、传闻和房间记忆依赖前面配置存在。 |
| 7 | `L1-SEED` -> `L2-SEED` -> `L3-SEED` | 固定 seed 验收必须在内容引用完整后补。 |

原则：允许同层内小范围并行，但不得在引用目标尚未存在时提交下游配置。

---

## 3. 交付证据格式

每个配置实现任务完成时，至少要留下以下证据：

| 证据 | 要求 |
|---|---|
| 修改文件 | 明确列出改动过的 `配置表(JSON)` 文件和 README / Validator 文档。 |
| 配置条目清单 | 列出新增、修改、废弃或迁移的 ID。 |
| 引用检查 | 说明 RewardID、MonsterID、ItemID、MapProfile、OrderID 是否能解析。 |
| 同步结果 | 运行 `.\tools\config\Sync-Configs.ps1 -Clean`，如未运行需写明原因。 |
| Validator / 验收 | 运行可用的配置校验、Unity smoke 或固定 seed 验收；如尚无工具，写明等待的 Validator 缺口。 |
| 状态回写 | 更新 `agent_status/design.md`；如影响长期节点门禁或跨职能交接，再通知 PM 更新 `版本规划/09_正式版核心纵切开发路线.md` 和 `PROJECT_STATUS.md`。 |

不接受的完成证据：

- 只说“已按文档补齐”但没有 ID 清单。
- 只更新 README，没有改配置 JSON，却标为配置完成。
- 只改 JSON，没有跑同步或解释为什么没跑。
- 只跑通单个界面或单个战斗，宣称前三层配置完成。

## 8. 推荐派发批次

### 8.1 第一批：第一层模板闭合

优先派发：

```text
L1-ITEMS -> L1-REWARDS -> L1-MONSTERS -> L1-DUNGEONS -> L1-SEED
```

```text
L2-ITEMS -> L2-REWARDS -> L2-MONSTERS -> L2-DUNGEONS -> L2-ORDERS -> L2-SEED
```

## 9. 完成判定

前三层正式配置实现任务全部完成，需要同时满足：

1. `L1`、`L2`、`L3` 所有任务均有配置源改动、ID 清单和引用检查证据。
2. `Items` / `Rewards` / `Monsters` / `Dungeons` 主干引用无断裂。
3. 第二层和第三层直达层逻辑在配置和 seed 验收中可复现。
4. 每层 Boss 保底成长材料挂在 Boss 奖励，不挂在精英奖励。
5. Boss 后 SafeZone 免费恢复 HP / SAN，但不清除背包取舍、订单、污染和探索账本。
6. 第三层路线侵蚀、污染物生命周期和订单互斥至少各有一条固定 seed 或手动验收路径。
7. `agent_status/design.md` 已更新策划 / 配置状态和证据；如影响长期节点门禁，PM 已同步 `09`。

只有上述条件全部满足，才能说“前三层正式配置实现任务完成”。在此之前，`31` / `32` / `33` / 本文 / `35` 都只代表策划交付，不代表配置 JSON 完成。
