# 正式配置设计与填充推进计划

> 本文只负责策划 / 配置侧计划：内容量目标、配置域审计、配置落地设计、配置实现前清单和配置验收样例。程序实现进度、美术交付进度和 PM 里程碑不写在本文，分别回到程序、美术和 PM 的状态页与事实文档。本文不是跨职能进度台账。

## 1. 职责边界

| 问题 | 事实来源 |
|---|---|
| 接下来系统优先级是什么？ | `版本规划/09_正式版核心纵切开发路线.md` |
| 某个需求是否有详细文档承接？ | `版本规划/11_纵切批次与需求文档承接矩阵.md` |
| 某项工作由哪个职能完成、当前状态是什么？ | 对应职能状态页：`agent_status/design.md`、`agent_status/program.md`、`agent_status/art.md`、`agent_status/pm.md` |
| 正式配置需要多少内容、先审计哪些配置域、怎么落到配置清单？ | 本文 |
| 具体系统规则是什么？ | 对应 GDD、规则卡、内容包、配置 README |
| 程序怎么实现？ | `开发文档/` |
| UI / 美术怎么交付？ | `美术文档/` |

本文中的“完成”只代表策划 / 配置设计层完成，不代表 JSON 已完成、程序已完成或美术已完成。字段说明、README 口径、审计结论、任务拆分和 JSON 修改前设计都不能直接标记为 `配置完成`；只有配置源落地并通过校验后，才可在策划状态页中标记 `配置完成`。进入正式纵切的实际工作完成后，必须回写对应职能状态页。

## 2. 核心判断

当前策划工作的重点不是继续扩写顶层概念，而是让正式版设计可以被配置、验证和后续内容生产承接。

| 主线 | 含义 | 对应工作 |
|---|---|---|
| 完善正式配置 | 让已有配置域、README、字段、标签、引用和 Validator 口径对齐正式版规则。 | 配置承接审计、字段补齐、约束定义、Validator 规则、验收样例。 |
| 补充正式配置 | 从整体可玩时长出发，补足物品、怪物、地图、奖励、成长、经济、订单、剧情和房间记忆等正式内容。 | 内容量规划、层级内容包、成长和经济内容池、长期循环目标、可玩时长验收。 |

简化表述：

```text
下一阶段策划工作 = 正式配置设计 + 配置验收标准 + 正式内容填充节奏
```

## 3. 目标容量

### 3.1 当前纵切候选目标

当前优先目标是让前三层和局外循环形成可持续扩展的正式配置骨架。

```text
第 1 层低压入门
  -> 第 2 层背包压力
  -> 第 3 层路线侵蚀 / 订单冲突
  -> 回城出售 / 制造 / 维护 / 成长
  -> 经济目标推动再次下潜
```

| 目标 | 时长口径 | 配置支撑 |
|---|---|---|
| 首次有效体验 | 30-60 分钟 | 第 1 层基础闭环，玩家理解背包、战斗、撤离和出售。 |
| 三层纵切体验 | 3-5 小时 | 第 1-3 层递进、局外成长、经济压力和至少一种路线目标。 |
| 反复构筑体验 | 6-10 小时 | 不同物品、怪物、订单和成长选择形成多轮下潜差异。 |

### 3.2 完整正式版容量预留

当前不要求立刻填满 5 层和终局内容，但所有配置设计要允许自然扩展到完整正式版。

| 目标 | 时长口径 | 内容支撑 |
|---|---|---|
| 主线首次通关 | 8-12 小时 | 5 个正式层级、局外成长、经济压力、订单目标和关键剧情事件。 |
| 深度构筑 / 多路线 | 15-25 小时 | 多义体构筑、势力订单、黑市背叛、房间记忆、事件分支和高层内容。 |
| 长尾收集 / 完成度 | 25 小时以上 | 更多遗物、义体、订单链、房间纪念物、剧情回收和挑战路线。 |

## 4. 内容量模型

### 4.1 每层基础容量

| 内容类型 | 每层基础量 | 设计目的 |
|---|---:|---|
| 普通怪 | 4-6 只 | 提供基础战斗节奏、层级主题和构筑检查。 |
| 精英怪 | 2 只 | 提供路线风险选择和关键材料来源。 |
| Boss | 1 只 | 提供层级终点、成长钥匙和剧情 / 经济推进点。 |
| 层级物品 | 10-14 件 | 支撑战斗、经济、材料、风险、订单和展示。 |
| 地图画像 / MapProfile | 2-3 个 | 支撑不同路线节奏和 seed 验收。 |
| 节点模板 | 10-18 个 | 组合 Combat、Elite、Event、Reward、SafeZone、Stairs、Boss。 |
| 层级订单 / 目标 | 2-4 个 | 让玩家带着目的下潜，而不只是刷随机收益。 |
| 传闻 / 价格波 | 2-3 条 | 让经济系统反向指导玩家捡什么。 |
| 剧情 / Lore / 房间记忆 | 3-5 条 | 让层级经历沉淀到局外和叙事。 |

当前已有 `19`、`20`、`25` 分别覆盖第 1、2、3 层。下一步不是扩第四层，而是确认前三层内容能真实落到配置、表现和验收。

### 4.2 全局内容池

| 内容域 | 当前纵切建议量 | 完整正式版建议量 | 说明 |
|---|---:|---:|---|
| Chassis | 3 | 6-8 | 当前先覆盖空间、战斗、续航三类方向。 |
| Prosthetics | 6-10 | 25-40 | 按槽位和构筑路线扩展。 |
| CraftingRecipes | 8-12 | 40-70 | 覆盖材料转化、义体制造、维护和特殊物品。 |
| 维护方案 | 4-6 | 10-16 | 覆盖 HP、SAN、磨损、侵蚀和高风险恢复。 |
| 特质 / 标签效果 | 8-12 | 40-80 | 当前先覆盖负面、转化、构筑触发和订单查询。 |
| 势力 | 3-5 | 5-7 | 当前已有 5 势力方向，可先落核心字段。 |
| 订单模板 | 12-20 | 80-150 | 按层级、势力、风险和背叛路线扩展。 |
| 经济传闻 | 8-12 | 40-80 | 支撑价格波、路线目标和订单预告。 |
| 剧情事件 | 12-20 | 80-150 | 当前先覆盖主干事件、债务事件和 Bond 事件。 |
| 房间纪念物 / 日记 | 12-20 | 80-150 | 支撑长期记忆、展示品和情感反馈。 |

这些不是立即配置完成量，而是用于校准正式配置最终需要支撑的游戏时长。

## 5. 推进阶段

### D0 配置承接审计

目标：确认当前配置域能否承接正式规则。

| 配置域 | 检查重点 | 事实来源 |
|---|---|---|
| `Items` | 形状、旋转、标签、售价、生命周期、VisualID、战斗 / 经济 / 材料职责。 | `02`、`15`、`18`、`19/20/25` |
| `Monsters` | 意图、AI 行为、对包干涉、掉落、CombatVisualID、层级归属。 | `03`、`15`、`19/20/25` |
| `Dungeons` | LayerConfig、MapProfile、节点池、路线主题、seed、安全区、楼梯、Boss。 | `GDD_02`、`15`、`19/20/25` |
| `Rewards` | 掉落、订单、材料、成长资源、金币和稀有奖励引用。 | `15`、`17`、内容包 |
| `Chassis / Prosthetics / CraftingRecipes` | 构筑方向、槽位、成本、材料缺口、维护和下潜许可。 | `05`、`16`、`21` |
| `Dolls / Effects` | SAN、Bond、情绪、特质、动态标签和反馈。 | `08`、`06`、`16` |

阶段产出：

1. 每个配置域的字段缺口。
2. 每个字段的合法值、引用关系和默认值建议。
3. 需要进入 Validator 的检查项。
4. 需要内容包补条目的空白内容池。

### D1 前三层正式配置填充

目标：让第 1-3 层内容支撑三层纵切体验。

执行顺序：

1. `Items`：先补每层 10-14 件正式物品的职责、标签、形状、来源和去向。
2. `Monsters`：补每层普通怪、精英、Boss 的教学目标、意图规律、反制方式和掉落逻辑。
3. `Dungeons`：补每层 MapProfile、节点池、路线主题、Boss / SafeZone / Stairs 规则。
4. `Rewards`：补物品、材料、金币、义体图纸、订单奖励的引用闭环。
5. 验收场景：补固定 seed 和玩家路径，确认配置能形成体验。

完成标准：

- 每层至少有一条低风险路线、一条高收益路线和一个明确 Boss 终点。
- 每层至少有两类背包取舍：空间形状、风险 / 价值、订单 / 经济取舍中的任意两类。
- 每层至少有一个局外回流点：制造材料、经济目标、订单推进、房间记忆或剧情触发。

### D2 局外成长与经济压力填充

目标：让玩家回城后有明确选择，而不是只清包和再下潜。

执行顺序：

1. `Chassis`：补三类底盘方向，分别服务空间、战斗、续航。
2. `Prosthetics`：按槽位补义体，保证每类至少 2 个不同策略选择。
3. `CraftingRecipes`：把第 1-3 层材料接到义体、维护、关键物品和订单。
4. 经济压力：补月租、维护费用、传闻价格波和至少一条订单目标链。
5. 人偶状态：补 SAN、磨损、侵蚀、情绪反馈和下潜许可检查。

完成标准：

- 玩家完成第 2 层后，至少能看到 2 条成长方向。
- 玩家完成第 3 层后，至少能形成 1 条中期目标链：制造、月租、订单或势力声望。
- 经济压力能驱动下潜目标，但不能在前三层阶段形成不可恢复死锁。

### D3 长期内容池规划

目标：为完整正式版时长预留内容生产结构。

| 内容池 | 近期动作 | 后续扩展 |
|---|---|---|
| 第 4-5 层 | 先定义层级主题、核心压力和内容量目标。 | 等前三层配置验收稳定后拆内容包。 |
| 订单链 | 先落 5 势力字段、订单状态机和首批模板。 | 扩展到 80+ 订单模板。 |
| 剧情事件 | 先落主干事件和系统指令结构。 | 扩展章节、Bond、债务和结局事件。 |
| 房间记忆 | 先落战败、Boss、赠礼、债务等关键纪念物。 | 扩展日记、窗外状态、家具和展示物。 |

## 6. 正式配置设计标准

### 6.1 每条配置都要有玩法职责

| 职责 | 说明 |
|---|---|
| 教学 | 帮玩家理解规则。 |
| 检验 | 检查玩家是否掌握规则。 |
| 取舍 | 迫使玩家在空间、金币、SAN、风险或时间之间选择。 |
| 回流 | 把局内收益带回局外成长、经济或叙事。 |
| 目标 | 给下一次下潜提供明确方向。 |

如果一条配置只是在数值上更高或更低，但没有职责，不应进入正式配置。

### 6.2 每个内容包都要闭环

一个正式内容包至少包含：

1. 内容来源：玩家从哪里遇到或获得它。
2. 玩家判断：玩家看到时能知道什么。
3. 玩法影响：它改变哪类选择。
4. 风险代价：它占用什么资源或带来什么后果。
5. 局外去向：出售、制造、展示、赠礼、交订单或触发剧情后的去向。
6. 验收路径：至少一条可复现玩家路径。

### 6.3 内容量不能替代节奏

增加物品、怪物和订单数量不是目的。正式配置填充应优先补齐以下节奏：

```text
看到目标 -> 选择路线 -> 付出风险 -> 带回资源 -> 转化成长 / 金币 / 关系 -> 再次下潜
```

如果新增内容不能进入这条链路，应降低优先级。

## 8. 配置源落地执行方案

从 2026-05-27 起，策划 / 配置侧下一阶段不再以新增设计文档为主，而是进入 `配置表(JSON)` 源数据落地。后续只在以下情况补文档：配置实现发现设计准入缺口、字段口径冲突、Validator 无法判定，或状态回写需要证据入口。

### 8.1 总执行流程

每个配置批次按固定流程执行：

```text
确认设计准入
  -> 修改 配置表(JSON) 源配置
  -> 运行 Sync-Configs
  -> 运行 ConfigValidator / 固定样例 / 必要 smoke test
  -> 修正字段、ID、引用和数值问题
  -> 回写 agent_status/design.md
  -> 单独提交本批配置变更
```

配置完成的判定必须同时满足：

1. `配置表(JSON)` 源数据已落地。
2. `UnityClient/Assets/StreamingAssets/Configs` 已由同步脚本生成，不手写维护。
3. 关键 ID、必填字段、跨表引用和层级引用没有阻塞性 error。
4. 已有 Validator、固定 seed、固定样例或人工复核证据。
5. `agent_status/design.md` 已记录本批配置完成范围、验证命令和剩余风险。

### 8.2 批次顺序

| 批次 | 目标 | 修改范围 | 完成标准 |
|---|---|---|---|
| C1 第一层正式配置落地 | 跑通第一层正式配置样板 | `Items`、`Rewards`、`Monsters`、`Dungeons` | 第一层战斗、掉落、拾取、撤离、出售、Boss、SafeZone、固定 seed 能形成闭环；同步和关键引用校验通过。 |
| C2 第二层直达与背包压力配置 | 支撑已通第一层后直达第二层 | `Items`、`Rewards`、`Monsters`、`Dungeons`、少量 `Orders` 引用 | 第二层直达不缺配置引用；背包压力物、订单占格、Boss 保底和 Boss 后 SafeZone 可验收。 |
| C3 第三层路线侵蚀配置 | 建立第三层风险收益和路线压力 | `Items`、`Rewards`、`Monsters`、`Dungeons`、必要 `Orders` / `Rumors` / 事件引用 | 第三层侵蚀 / 污染、路线取舍、Boss 奖励和至少一个局外回流点成立。 |

### 8.3 策划侧完整执行规划与状态总览

本节是策划 agent 防重复开发的总入口。它记录“策划侧自己负责的完整规划”，包括需求承接、设计准入、配置源落地、配置验收证据和后续内容池规划；程序实现、美术交付和 PM 里程碑不在本表标完成。

后续策划 agent 每次开始、完成或阻塞一个工作项，都必须先更新本节或 8.4 的子项台账，再同步 `agent_status/design.md`。如果只完成了 README、审计、任务拆分或 JSON 修改前设计，只能标为 `设计准入完成` 或 `策划证据完成`，不能标为 `配置完成`。

状态口径：

- `配置完成`：源 JSON 已落地，同步通过，并有 Validator / 固定样例 / 人工复核证据。
- `进行中`：当前正在修改源 JSON 或正在补齐该工作项的验证闭环。
- `设计准入完成`：需求、字段、ID、验收样例和任务拆分足够支持后续配置源落地，但源 JSON 尚未完成。
- `策划证据完成`：完成审计、README、ID 锁定、任务拆分或验收规格等策划证据，不等于配置完成。
- `未解锁`：前置批次未完成，当前不应开工。
- `后续批次`：属于长期内容池或第四层以后内容生产，不抢当前前三层与局外循环主线。
- `阻塞`：缺设计准入、字段口径、程序校验能力、跨表引用或验证证据，不能继续推进。

### 8.4.3 状态回写规则

1. 开始修改某个子项的源 JSON 时，把该子项和所属批次改为 `进行中`，并在 `agent_status/design.md` 写明开工子项、修改目录和准入依据。
2. 子项完成时，只能在源 JSON、同步、Validator / 固定样例或人工复核证据齐全后改为 `配置完成`。
3. 子项完成后，把所属批次的 `当前子项` 推进到下一个子项；如果该批次所有子项完成，再把批次改为 `配置完成`，并解锁下一批次为 `待开始`。
4. 如果发现字段、程序能力、跨表引用或设计准入缺口，把子项改为 `阻塞`，在 `agent_status/design.md` 写清阻塞原因、需要哪个职能处理、证据入口和恢复条件。

## 9. 执行原则

1. 先让已有前三层内容真实支撑 3-5 小时纵切体验。
2. 再补完整正式版 8-12 小时主线所需的第 4-5 层和长期系统内容。
