## 4. 结论

本轮 `GROWTH-ID-LOCK` 结论：

1. `ChassisID`、`ProstheticID`、`RecipeID`、`TraitID`、`FeedbackID`、`MementoID` 的正式目标 ID 在当前 JSON 主 ID 中均未发现直接冲突。
2. `MaintenanceID` 中 `maint_basic_patch`、`maint_purification_flush` 已在当前工作区 JSON 中存在，且与 `37/38` 设计方向一致；它们是已占用的正式 ID，不是冲突，但后续不能重复新建。
3. 旧 ID `chassis_lv1_basic`、`chassis_lv2_expanded`、`pros_power_arm`、`pros_cooling_system`、`craft_pros_power_arm`、`craft_pros_cooling_system` 仍属于 MVP / 原型命名，不能直接视为正式配置完成。
4. `doll_proto_0` 可继续作为基础人偶档案 ID，但当前 JSON 混有运行时状态与初始测试装备；后续 `GROWTH-DOLL-TRAIT-ROOM` 必须拆清静态配置和运行时实例。
5. README 中出现的正式 ID 只是字段口径和目标清单，不算 JSON 主 ID 冲突；冲突判断只以当前 JSON 主 ID 为准。

## 5. 后续执行规则

1. 后续进入 `GROWTH-CHASSIS`、`GROWTH-EFFECTS-TRAITS`、`GROWTH-PROSTHETICS`、`GROWTH-CRAFT-MAINT`、`GROWTH-DOLL-TRAIT-ROOM` 前，优先使用本文锁定 ID。
2. 如果实现时必须改名，先更新 `37`、`38`、本文、对应配置 README 和 `agent_status/design.md`；如影响长期节点门禁或跨职能交接，再通知 PM 更新 `09`，然后再改 JSON。
3. 对已存在的 `maint_basic_patch`、`maint_purification_flush`，后续任务只能补字段、引用、Validator 和验收证据，不能重复创建同 ID。
4. 对旧 MVP ID，后续需要二选一：
   - 迁移为正式 ID，并在配置实现证据中记录迁移关系。
   - 保留为兼容 / 测试 ID，并避免它们进入正式内容池。
5. 本文完成后，`38` 的 `GROWTH-ID-LOCK` 可视为策划证据完成；`DES-V3-002` 仍保持进行中，不能标记配置完成。
