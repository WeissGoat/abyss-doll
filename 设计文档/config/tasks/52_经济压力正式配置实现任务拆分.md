# 经济压力正式配置实现任务拆分

> 本文是 `26_正式配置设计与填充推进计划.md` 中 W3「局外成长与经济目标补齐」的经济压力配置实现派发层。它承接 `46` 到 `51` 的审计、字段级设计和验收规格。本文不直接修改 `配置表(JSON)`，不代表经济压力配置完成；它定义后续真正改 JSON 或等价配置结构时应该拆成哪些任务、按什么顺序执行、交付什么证据，以及如何回写策划状态页和必要的项目状态。

---

## 1. 任务边界

### 1.1 本文处理

| 范围 | 说明 |
|---|---|
| 配置实现任务拆分 | 把 `ECON-CORE`、`ECON-RUMORS`、`ECON-FACTIONS`、`ECON-ORDERS`、`ECON-VALIDATION` 拆成后续可派发任务。 |
| 依赖顺序 | 明确经济核心、传闻、势力、订单和跨域引用的落地顺序，避免订单、传闻或账单引用断链。 |
| 交付证据 | 规定每个任务完成时必须留下配置源文件列表、ID 清单、引用检查、同步结果、Validator / 固定样例结果和状态页回写。 |
| 验收样例 | 规定经济压力从静态检查到固定样例的验收顺序。 |
| 防误判口径 | 明确 README、审计、字段级设计、任务拆分、JSON、程序 Validator 和跨职能验收分别是什么状态。 |

### 1.2 本文不处理

| 范围外 | 原因 |
|---|---|
| 直接改 `配置表(JSON)` | 本文只拆任务，不执行 JSON 修改。 |
| 程序 Validator 实现 | 程序能力以开发文档、代码、测试报告和 `agent_status/program.md` 为准。 |
| 运行时 UI / 美术表现 | 经济界面、VisualID、Approved 资源和截图验收回到美术文档、开发文档、`agent_status/art.md` 和 `agent_status/program.md`。 |
| 第 4 层以后内容生产 | 当前经济压力先服务前三层和局外循环，后续层内容池另走内容生产批次。 |
| 经济数值最终调参 | 本文锁定首批正式配置结构和证据，不替代后续试玩调参。 |

## 3. 总依赖顺序

经济压力配置实现建议按以下顺序执行：

```text
ECON-ID-LOCK
  -> ECON-README-CHECK
  -> ECON-CORE-JSON
  -> ECON-FACTIONS-JSON
  -> ECON-RUMORS-JSON
  -> ECON-ORDERS-JSON
  -> ECON-CROSS-REFS
  -> ECON-VALIDATION-RUN
  -> ECON-STATUS-WRITEBACK
```

| 顺序 | 任务 | 依赖 | 产出 |
|---:|---|---|---|
| 1 | `ECON-ID-LOCK` | `47` / `48` / `49` / `50` ID 清单 | 经济、传闻、势力、订单 ID 与现有 JSON 无阻塞冲突。 |
| 2 | `ECON-README-CHECK` | 四个配置 README | 确认 README 字段口径足以支持后续 JSON；若不够，先补 README。 |
| 3 | `ECON-CORE-JSON` | `47` | 补 `Economy` 配置源或等价结构。 |
| 4 | `ECON-FACTIONS-JSON` | `49` | 补 5 个势力、声望 / 信任阶梯和订单池引用。 |
| 5 | `ECON-RUMORS-JSON` | `48`、`ECON-CORE-JSON`、`ECON-FACTIONS-JSON` | 补 8 条传闻、来源追踪、渠道和订单权重。 |
| 6 | `ECON-ORDERS-JSON` | `50`、`55`、`ECON-FACTIONS-JSON`、关联 Rewards / Items / Dungeons | 补 5 个订单池和 19 条订单模板。 |
| 7 | `ECON-CROSS-REFS` | 上述全部 | 补 Rewards / Items / Dungeons 的必要引用检查或记录迁移 warning。 |
| 8 | `ECON-VALIDATION-RUN` | `51`、配置同步 | 跑静态 Validator、跨域检查和固定验收样例。 |
| 9 | `ECON-STATUS-WRITEBACK` | 验收结果 | 回写 `agent_status/design.md` 和必要项目状态；若影响长期节点门禁，再通知 PM 更新 `09`。 |

不建议先补订单再补势力。订单依赖 FactionID、订单池、声望 / 信任变化和背叛裁决，先写订单容易产生不可解释的悬空引用。

## 4. `ECON-ID-LOCK`

目标：在任何 JSON 修改前锁定经济压力首批 ID，避免多表互引时反复改名。

| ID 类型 | 本轮锁定 |
|---|---|
| EconomyID | `economy_town_v1` |
| RumorID | `rumor_origin_stone_demand`、`rumor_slime_crash`、`rumor_scrap_workshop_shortage`、`rumor_corrosion_sample_premium`、`rumor_contraband_night_channel`、`rumor_faction_medical_request`、`rumor_weapon_collector_visit`、`rumor_low_layer_bulk_buy` |
| FactionID | `faction_adventurer_guild`、`faction_mechanic_workshop`、`faction_mage_tower`、`faction_alchemy_guild`、`faction_black_market` |
| OrderPoolID | `pool_guild_exploration`、`pool_workshop_engineering`、`pool_mage_relic`、`pool_alchemy_purification`、`pool_black_market_betrayal` |
| OrderID | 以 `55_经济压力订单ID最终锁定表.md` 锁定的 19 个 OrderID 为准。 |

交付证据：

1. 新增 ID 与当前 `配置表(JSON)` 无阻塞冲突。
2. 旧样例 ID 的迁移口径清楚，例如 `rumor_mechanical_price_up` 是迁移、保留样例还是废弃。
3. 如必须改名，先回写 `47` / `48` / `49` / `50` 和本文，再改 JSON。
4. ID 锁定结果作为 `DES-V4-001` 的策划 / 配置证据，但不等于配置完成。

当前证据：`53_经济压力正式配置ID锁定与冲突检查.md` 已完成当前工作区 ID 冲突检查；阻塞性 ID 冲突为 0，`economy_town_v1` 与 `faction_mechanic_workshop` 可复用扩展，`rumor_mechanical_price_up` 与 `order_mechanic_scrap_drive` 需在 JSON 实现时迁移或标记为旧样例。

|---|---|---|
| `Economy` | 日报、周报、月租、出售渠道、顾客、违禁、NightTax、DeadlockGuard。 | README 字段口径可覆盖 `47`。 |
| `Rumors` | 传闻类型、目标查询、价格倍率、来源追踪、渠道、订单权重、风险提示。 | README 字段口径可覆盖 `48`。 |
| `Factions` | 势力角色、声望阶梯、黑市信任、订单池、解锁引用、怀疑 / 背叛关系。 | README 字段口径可覆盖 `49`。 |
| `Orders` | 订单池、订单模板、需求表达、期限、奖励、失败、背叛、互斥唯一物。 | README 字段口径可覆盖 `50`。 |

交付证据：

1. README 已列出正式字段和迁移期 warning。
2. README 明确哪些字段当前程序未消费，但仍是正式配置目标。
3. README 更新不等于 JSON 完成，只能作为策划 / 配置字段口径证据。

## 6. `ECON-CORE-JSON`

目标：按 `47` 补 `Economy` 配置源或等价配置结构，让经济压力有日报、周报、月租、渠道、顾客、违禁、NightTax 和死锁保护的正式骨架。

| 子任务 | 内容 | 交付证据 |
|---|---|---|
| `ECON-CORE-01` | 补 `economy_town_v1` 的正式核心字段。 | `WeekLength`、`MonthLength`、月租、轻债、典当、日报 / 周报 / 月账单策略存在。 |
| `ECON-CORE-02` | 补出售渠道规则。 | `DumpBox`、`ShowcaseGrid`、`OrderSlot`、`PawnPool`，如有黑市则含 `BlackMarketSlot`。 |
| `ECON-CORE-03` | 补顾客池。 | 普通买方、高价值买方、工坊、医疗、武器藏家、黑市顾客职责清楚。 |
| `ECON-CORE-04` | 补违禁和 NightTax。 | 违禁目标标签、普通渠道拒收、黑市高价、隔夜代价和日报复盘字段存在。 |
| `ECON-CORE-05` | 补 DeadlockGuard。 | 前三层阶段至少有低层回刷、基础订单、典当、轻债或保底传闻之一。 |

最低验收：

- `CFG-ECON-*`、`CFG-CONTRA-*`、`CFG-NIGHT-*`、`CFG-DEADLOCK-*` 无 error。
- `V-PACK-ECON-DAILY-01`、`V-PACK-ECON-RENT-01` 可执行或有明确等待工具原因。

失败信号：

- 月租、维护和欠债同时加压，但没有补救路径。
- 黑市 / 违禁存在，但普通渠道和 NightTax 裁决互相冲突。
- 日报只显示金币变化，无法解释收入来源和压力来源。

## 10. `ECON-CROSS-REFS`

目标：补经济压力配置与 `Items`、`Rewards`、`Dungeons` 的跨域证据。该任务不要求本轮重写所有关联配置，但必须明确断链是 error、warning 还是后续批次。

| 关联域 | 必查内容 | 处理口径 |
|---|---|---|
| `Items` | 经济标签、违禁标签、订单绑定、Boss 核心、污染样本、武器、源石、低层材料。 | 当前开放层级必需来源缺失为 error；后续层来源缺失可 warning。 |
| `Rewards` | 订单奖励、图纸、势力解锁、服务解锁、黑市奖励。 | 当前订单引用的奖励缺失为 error；迁移期固定金币可 warning。 |
| `Dungeons` | 订单 / 传闻目标的层级、节点、怪物和路线来源。 | 当前层级目标不可达为 error。 |
| `CraftingRecipes` | 工坊短缺、维护、图纸、材料转化。 | 若只是后续局外成长扩展可 warning，但必须记录归属。 |
| `ScenarioEvents` | 债务、怀疑、黑市诱惑、账单危机。 | 可先 warning，不阻断经济基础配置完成，但不能标记跨职能已完成。 |

交付证据：

1. `CFG-ECON-X-*` 跨域检查结果。
2. error 必须归零后才能进入 `配置完成` 判断。
3. warning 必须记录责任职能和后续处理范围。

## 11. `ECON-VALIDATION-RUN`

目标：按 `51` 跑经济压力配置验收。

## 13. 状态回写口径

经济压力配置状态只能按证据推进：

| 证据状态 | 策划 / 配置状态建议 | 说明 |
|---|---|---|
| 只有 `46-52` 文档完成，未改 JSON。 | `进行中` | 策划 / 配置设计证据充分，但不是配置源完成。 |
| 只完成部分 JSON，例如只补 Economy 或 Rumors。 | `进行中` | 可在证据入口追加局部完成，不标 `配置完成`。 |
| JSON 已落地，Sync 通过，静态 Validator error 为 0，但固定样例未跑完。 | `验收中` | 配置源可进入验收，但不能标记 `配置完成`。 |
| JSON 已落地，Sync 通过，Validator error 为 0，核心固定样例通过，warning 有归属。 | `配置完成` | 仅代表策划 / 配置职能完成，不代表程序、UI 或美术全部完成。 |
| 程序服务、UI / 美术和配置验收全部满足 V4 门禁。 | `已完成` | 需要跨职能证据，不由策划单独标记。 |

## 14. 完成判定

本文完成只表示 `ECON-TASKS` 的派发层完成。经济压力配置仍不能标记为 `配置完成`，直到满足以下条件：

1. `ECON-ID-LOCK` 已核对当前工作区 ID 冲突；当前证据见 `53_经济压力正式配置ID锁定与冲突检查.md`。
2. `ECON-README-CHECK` 已确认四个配置 README 足够承接正式字段；当前证据见 `54_经济压力正式配置README字段口径检查.md`。
3. `ECON-CORE-JSON`、`ECON-FACTIONS-JSON`、`ECON-RUMORS-JSON`、`ECON-ORDERS-JSON` 的配置源均已落地。
4. `ECON-CROSS-REFS` 的跨域 error 已归零。
5. 配置同步成功，运行时副本不是手写维护。
6. `51` 中的 Validator 或等价人工验收覆盖核心字段、跨域引用和固定样例。
7. `V-PACK-ECON-DAILY-01`、`V-PACK-ECON-ROUTE-01`、`V-PACK-ECON-RENT-01`、`V-PACK-ECON-BLACK-01`、`V-PACK-ORDER-REFRESH-01`、`V-PACK-ORDER-BETRAYAL-01` 至少有核心通过证据或明确等待工具原因。
8. `agent_status/design.md` 和必要项目状态已回写；若影响长期节点门禁，已通知 PM 更新 `09`。

## 15. 下一步建议

优先派发顺序：

1. 若进入 JSON 实现，先按 `56` 确认设计准入，再按本文顺序补 `Economy` -> `Factions` -> `Rumors` -> `Orders` 配置源；`Orders` 使用 `55` 锁定的 5 个 OrderPoolID 和 19 个 OrderID，并按 `51` 留下 Validator / 固定样例 / 状态回写证据。
2. 若后续修改订单池或订单模板，必须先更新 `50` 和 `55`，再同步本文、`53`、`54`、`Orders/README.md` 与 `agent_status/design.md`。
3. 若程序 Validator 尚未覆盖经济压力，程序侧另按程序状态页和开发文档拆 Validator 实现，不把程序工作写入 `26` 或本文。

如果后续任务只完成单个配置域，例如只完成 `Economy` JSON，只能把该域记录为局部完成，不能把整个经济压力配置标为完成。
