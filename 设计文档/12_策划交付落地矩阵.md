# 策划交付落地矩阵

> **定位：** 本文档回答“`设计文档/` 已经写到可开发之后，后续应该如何把设计继续做实”。它不替代 GDD、规则卡、配置 README、开发文档或美术规格，而是把每个系统的事实来源、配置承接、表现承接和验收证据放在一张策划视角的交付矩阵里。

---

## 1. 使用原则

| 原则 | 说明 |
|---|---|
| GDD 不是半成品说明 | 当前 `GDD_00` 到 `GDD_12` 已有正式规则入口；后续不是重写方向，而是补承接材料。 |
| 纵切是顺序，不是质量降级 | 系统可以晚做，但进入批次时必须按正式规格处理。 |
| 配置和表现是设计延伸 | 配置 README、样例配置、UI / 美术规格和验收截图不是程序杂项，而是设计是否可落地的证据。 |
| 验收要可复现 | 每个系统至少要能给出输入状态、执行动作、期望输出和失败边界。 |
| 按交付包阅读 | 开发任务不应只读单份 GDD 正文；应同时读取对应 GDD、规则卡、配置承接、表现承接和验收场景。 |
| 内容按包生产 | 新增物品、怪物、订单、事件和房间记忆时，应按 `18_正式版内容生产规格.md` 说明玩家承诺、玩法职责、系统连接和验收路径；当前高优先级正式内容包为 `19` 到 `25`，第四层以后属于后续内容填充。 |

---

## 2. 交付状态定义

| 状态 | 含义 |
|---|---|
| `规则可开发` | GDD 和规则卡已经说明核心流程、字段、状态机、边界和验收样例。 |
| `待配置承接` | 需要把规则字段落到配置 README、样例 JSON、ID 规则和内容池说明。 |
| `待表现承接` | 需要把玩家可见信息、UI 状态、美术资源、反馈文案和截图验收写入对应规格。 |
| `待验证承接` | 需要补 Validator、手工验收脚本、自动化跑通或数值复盘表。 |
| `内容量扩展` | 规则已成立，但还需要更多怪物、物品、事件、家具、订单或剧情文本支撑完整体验。 |
| `内容包可拆分` | 已有正式内容包，能继续拆到配置、表现、验收和资源需求。 |

这些状态可以并存。例如一个系统可以同时是 `规则可开发`、`待配置承接` 和 `待表现承接`。

---

## 2.1 开发交付包口径

当前 `设计文档/` 的正式交付不是“每份 GDD 自带全部字段和算法”，而是“GDD 说明体验与系统定位，规则卡承接硬规则，矩阵与验收场景承接跨系统落地，正式内容包承接具体内容”。后续给程序、美术或配置 agent 派任务时，应按下表组合事实来源：

| 系统 | 必读交付包 | 不足时的风险 |
|---|---|---|
| 背包 / 物品生命周期 | `GDD_01`、`GDD_06`、`02_物品背包旋转与生命周期规则卡`、`A-01` 到 `A-04` 验收场景 | 只读 GDD 容易漏掉旋转合法性、容器迁移、绑定物和战败裁决。 |
| 战斗 / 怪物意图 | `GDD_01`、`03_战斗回合与怪物意图规则卡`、战斗 HUD 表现规格、`A-02` 验收场景 | 只读 GDD 容易把怪物做成无预告行为，破坏玩家可读性。 |
| 深渊地图 / 搜打撤 | `GDD_02` 第七节、`19`、`20`、`25`、`A-03` / `A-05` 验收场景、`Dungeons` 配置承接 | 只读早期流程说明容易退回单线节点，漏掉 seed、路线、迷雾、前三层内容递进、已通层直达和安全区账本规则。 |
| 时间 / 经济 | `GDD_07`、`GDD_04`、`01_局外时间与日程口径规则卡`、`04_小镇经济结算与压力链规则卡`、`A-06` 验收场景 | 容易把局外行为误写成 AP 消耗，或让账单 / 传闻 / 欠债缺少可复盘来源。 |
| 人偶状态 / 养成 / 交互 / 房间 | `GDD_03`、`GDD_08`、`GDD_11`、`GDD_12` 与 `05`、`08`、`09`、`11` 规则卡，`A-07` 到 `A-12` 验收场景 | 容易把情感系统做成表现层事件，缺少 SAN、Bond、维护、房间记忆和交互上限的统一裁决。 |
| 标签 / 特质 / 订单 / 剧情 | `GDD_09`、`GDD_10`、`GDD_05` 与 `06`、`07`、`10` 规则卡，`24` 势力订单内容包，`A-09` 到 `A-11` 验收场景 | 容易出现触发器、互斥、订单刷新、剧情队列和系统指令不可复现。 |

这意味着：GDD 正文偏叙述不是问题，但任务入口必须引用完整交付包；否则仍视为交接不完整。

### 2.2 内容包交付口径

规则卡回答“系统如何裁决”，内容包回答“第一批正式内容如何被玩家感知、如何进入配置池、如何验收”。当前首批正式内容包如下：

| 内容包 | 对应系统 | 配置落点 | 表现 / 验收重点 |
|---|---|---|---|
| `19_第一层正式核心内容包` | 第一层搜打撤 | `Items`、`Monsters`、`Dungeons`、经济传闻、事件、房间记忆 | 低压入口、背包旋转、怪物意图、Boss 后安全区、撤离回流。 |
| `20_第二层背包压力内容包` | 第二层背包压力 | `Items`、`Monsters`、`Dungeons`、Orders、Rewards、事件 | 背包干涉、精英可绕、订单占格、第二层直达、安全区恢复边界。 |
| `25_第三层路线侵蚀内容包` | 第三层路线侵蚀 | `Items`、`Monsters`、`Dungeons`、Orders、Rewards、事件、RoomMemory | 路线侵蚀、污染物品生命周期、多势力订单冲突、第三层 Boss、安全区止损。 |
| `设计文档/_archive/content_backlog/26_第四层组合压力内容包` | 第四层组合压力 | 后续层内容填充草案 | 当前暂不作为优先落地依据；待第四层进入内容生产批次时复审。 |
| `21_人偶成长修复内容包` | 人偶成长 / 修复 | `Dolls`、`Chassis`、`Prosthetics`、`Effects`、`CraftingRecipes`、交互 / 房间配置 | 底盘方向、义体槽位、维护代价、创伤转化、房间纪念物。 |
| `22_小镇经济月租内容包` | 经济 / 月租 | 经济配置、Rumors、Customers、Bills、Contraband、Orders、Rewards | 传闻改路线、账单复盘、违禁诱惑、月租预告、典当边界。 |
| `23_长期记忆剧情内容包` | 剧情 / 房间长期记忆 | ScenarioEvents、DialogueTrees、Flags、RoomMemory、Mementos、Diary、WindowState、IdleRules | 事件队列、跳过不丢指令、房间零时耗、经历留痕。 |
| `24_势力订单声望内容包` | 势力 / 订单 / 声望 | Factions、Orders、Rewards、Shops、Items、Dungeons、ScenarioEvents | 订单刷新、目标路线、委托物占格、声望解锁、黑市背叛、正规势力怀疑。 |

这些内容包足以支撑首批正式纵切继续拆到配置、表现和验收；深渊前三层已经形成正式递进。第四层和第 5 层以后属于后续层内容填充，完整正式版仍需要在同一质量标准下继续扩展更多敌人、物品、订单链、剧情文本、家具和结局内容。

## 4. 下一批策划补强优先级

### 4.1 配置承接优先级

| 优先级 | 目标 | 原因 |
|---|---|---|
| P0 | `Items`、`Monsters`、`Dungeons` | 背包战斗和深渊地图是当前主干，配置字段若不清楚，会直接影响玩法实现和验收。 |
| P1 | `Dolls`、`Effects`、`Chassis`、`Prosthetics`、`CraftingRecipes` | 人偶状态、养成和交互是 A3/A4 的长期承载，需要提前统一字段。 |
| P2 | 订单、经济、剧情、房间内容池 | 规则已可开发，但内容量和表现资源会随纵切批次逐步增加。 |

### 4.1.1 内容包落地优先级

| 优先级 | 目标 | 原因 |
|---|---|---|
| P0 | `19`、`20`、`25` 的物品 / 怪物 / 地图画像 / 订单落地 | 这三包直接决定前三层正式体验能否形成清晰递进。 |
| P1 | `21` 的底盘 / 义体 / 维护 / 特质落地 | 人偶成长是深渊收益的长期出口，也是再次下潜动机。 |
| P2 | `22`、`23`、`24` 的经济 / 剧情 / 房间记忆 / 势力订单落地 | 它们支撑正式版长线压力、情感沉淀和定向下潜目标，可随纵切批次分批实现。 |

### 4.2 表现承接优先级

| 优先级 | 目标 | 原因 |
|---|---|---|
| P0 | 战斗意图、背包干涉、拾取 / 撤离 / 战败结算 | 玩家必须读懂每次局内决策的后果。 |
| P1 | 深渊地图、层级入口、安全区、已通层直达 | 这是正式版搜打撤节奏成立的关键。 |
| P2 | 工坊人偶状态、交互反馈、房间视觉叙事 | 情感系统需要长期积累，但规则和资源需求已可提前对齐。 |

### 4.3 验收承接优先级

| 优先级 | 目标 | 原因 |
|---|---|---|
| P0 | 背包 / 物品生命周期、战斗回合、怪物意图、地图生成 | 这些系统一旦规则偏差，会直接破坏核心体验。 |
| P1 | 经济结算、成长维护、标签特质、人偶状态 | 它们决定长期循环是否稳定。 |
| P2 | 剧情调度、势力订单、房间视觉叙事 | 需要在内容量扩展时持续补验收样例。 |

## 5. 交付检查清单

后续任意系统进入正式纵切开发前，策划应检查：

1.  GDD 是否指向最新规则卡。
2.  规则卡是否有字段、状态机、边界和验收样例。
3.  配置 README 是否承接规则卡字段。
4.  UI / 美术规格是否承接玩家需要读懂的信息。
5.  Validator 或验收用例是否能覆盖主要失败边界。
6.  如果已有正式内容包，配置、表现和验收是否引用对应 `19` 到 `25`；`26` 当前不作为优先落地检查项。
7.  `00_策划文档开发交付审计.md` 是否仍准确反映交付状态。
8.  `agent_status/design.md` 是否记录最近完成和下一步建议。
