# 策划配置表现验收承接规格

> **定位：** 本文档定义“规则已经写清楚以后，策划如何把它交给配置、表现和验收”。它不替代 GDD、规则卡、配置 README、开发文档或美术规格，而是规定这些文档之间的承接粒度，避免系统进入正式纵切时只停留在体验描述。

---

## 1. 交付包结构

正式版核心纵切中，一个系统进入开发批次时，策划交付包至少由五层组成：

| 层级 | 作用 | 合格标准 |
|---|---|---|
| GDD | 说明系统定位、玩家体验、跨系统价值和边界。 | 玩家为什么要做、系统为什么存在、与其他系统如何交换资源已经清楚。 |
| 规则卡 | 承接字段、状态机、算法、边界和验收样例。 | 程序可以据此实现领域规则，不需要猜核心裁决。 |
| 配置承接 | 说明哪些内容由配置驱动、哪些是运行时实例状态。 | 配置 README 和样例 JSON 能找到字段来源、默认值、引用关系和内容池规则。 |
| 表现承接 | 说明玩家必须读懂的信息、反馈、失败原因和资源需求。 | UI / 美术可以知道哪些状态必须可见，哪些反馈不能省略。 |
| 验收承接 | 说明可复现输入、玩家动作、期望输出和失败信号。 | 人工验收、自动化测试和数值复盘能复现同一问题。 |

一个系统如果只有 GDD 和规则卡，可以判定为“规则可开发”；如果要进入完整纵切交付，还必须继续补配置、表现和验收承接。

具体内容条目和内容包的生产口径见 `18_正式版内容生产规格.md`：配置承接说明字段结构，内容生产规格说明每个条目为什么存在、服务哪条循环、玩家如何读懂以及如何验收。

---

## 2. 配置承接规格

配置承接不是把规则卡全文复制到配置 README，而是把“策划可调、内容可扩展、程序可校验”的字段整理出来。

### 2.1 通用字段要求

每个配置域至少要说明：

| 字段组 | 说明 |
|---|---|
| ID 规则 | ID 命名、唯一性、是否可被其他配置引用。 |
| 类型枚举 | 类型值、标签、状态、节点类型、意图类型等枚举来源。 |
| 数值字段 | 默认值、允许范围、是否受难度 / 层级 / 周期倍率影响。 |
| 引用字段 | 指向物品、怪物、奖励、事件、视觉资源、对话或效果的外键。 |
| 内容池 | 抽取池、权重、筛选条件、保底和不可生成条件。 |
| 运行时排除项 | 哪些字段只存在于实例状态，不能写进静态配置。 |
| Validator 要点 | 必填、范围、引用、互斥、权重、seed 复现或 fallback 校验。 |

### 2.2 P0 配置承接

| 配置域 | 规则来源 | 必须承接的设计字段 | 运行时字段边界 | 验收样例 |
|---|---|---|---|---|
| `Items` | `GDD_06`、`02_物品背包旋转与生命周期规则卡` | `ItemID`、尺寸 / 形状、可旋转角度、标签、基础售价、绑定规则、触发组件、空间干涉、掉落 / 制造 / 出售引用。 | `InstanceID`、当前容器、当前位置、当前旋转、耐久、侵蚀、动态标签、绑定实例状态。 | 旋转合法性、非法放置、战败丢失 / 保留、撤离回流、出售和制造消耗。 |
| `Monsters` | `GDD_01`、`03_战斗回合与怪物意图规则卡` | `MonsterID`、层级区间、基础属性、意图列表、意图权重、目标规则、对包干涉引用、掉落池、战斗视觉 ID。 | 当前 HP、当前护盾、本回合意图、蓄力计数、召唤物状态、临时效果。 | 攻击预告、护盾、塞包、封格、SAN 压力、多怪行动顺序。 |
| `Dungeons` | `GDD_02` | `LayerConfig`、`MapProfile`、`NodeTypeWeights`、`RouteThemes`、`RequiredNodes`、`EncounterPool`、`RewardPool`、`EventPool`、`FogRules`。 | 本轮 seed、已访问节点、当前节点、可见状态、探索账本、已通层解锁状态。 | 同 seed 复现、无孤岛、Boss 可达、精英可绕、已通层直达、安全区不清账本。 |

### 2.3 P1 配置承接

| `Effects` | `GDD_09`、`06_标签与特质规则卡` | 效果类型、触发事件、查询表达式、优先级、互斥组、叠加规则、持续时间。 | 已生效实例、剩余持续时间、触发计数、来源对象。 | 特质触发、互斥优先级、动态标签消除 / 转化。 |

## 3. 表现承接规格

表现承接的目标不是写 UI 布局细节，而是规定“玩家必须看懂什么”。如果玩家只能靠猜测理解收益、代价或失败原因，视为设计交付不完整。

| 场景 | 必须可见的信息 | 必须反馈的失败原因 | 关联验收 |
|---|---|---|---|
| 备战 / 下潜入口 | 当前层级、锁定原因、人偶 HP / SAN / 磨损 / 侵蚀、背包布局、委托物预留、已通层直达。 | 状态不允许下潜、层级未解锁、背包非法、委托物空间不足。 | `A-01` |
| 战斗 HUD | 玩家 AP、护盾、怪物 HP、怪物意图、目标、对包干涉预告、当前异常、可用物品。 | AP 不足、目标非法、格子被封锁、物品条件不满足、怪物行动来源。 | `A-02` |
| 战后拾取 / 背包整理 | 掉落来源、物品尺寸、旋转、可放置状态、丢弃后果、绑定 / 非绑定标识。 | 放不下、角度不合法、占用冲突、离开节点导致未拾取物丢失。 | `A-02`、`A-03` |
| 深渊地图 | 当前节点、可选节点、节点类型、连线、迷雾、路线风险、Boss 方向、安全区位置。 | 不可回头、节点不可达、锁定路线、已通层直达不可用原因。 | `A-05` |
| 安全区 / 撤离 | 免费全恢复、撤离 / 深入、探索账本、安全盒内容、继续深入风险。 | 安全盒容量不足、继续深入条件不足、撤离结算来源不明。 | `A-03`、`A-05` |
| 战败结算 | 丢失物、保留物、绑定物损坏、安全盒保留、人偶创伤、维修压力。 | 为什么丢失、为什么保留、创伤来源、后续修复入口。 | `A-04` |
| 营业 / 账单 | 售价来源、传闻倍率、成交 / 未售、维护费、租金倒计时、欠债风险。 | 物品不可售、违禁代价、账单不足、强制典当原因。 | `A-06` |
| 成长 / 维护 | 材料缺口、金币成本、槽位、装备前后变化、维护效果、下潜许可变化。 | 材料不足、槽位冲突、适应期限制、维护方案不可用。 | `A-07`、`A-08` |
| 人偶交互 / 房间 | 当前情绪、可用交互、每日上限、偏好反馈、房间纪念物、窗外状态、待机表现。 | 低 SAN 拒绝、上限已满、礼物无效、房间展示来源缺失。 | `A-08`、`A-12` |
| 订单 / 剧情 | 订单目标、期限、奖励、声望变化、剧情优先级、系统指令结果。 | 订单超期、目标物缺失、跳过不丢奖励、事件延后原因。 | `A-10`、`A-11` |

## 4. 验收承接规格

每个正式纵切系统至少要有一组策划验收样例。样例不要求替代程序测试，但必须让测试可以复现同一条玩家路径。

### 4.1 验收样例模板

```text
ID:
名称:
覆盖 GDD / 规则卡:
前置状态:
输入配置 / Seed:
玩家行为:
期望系统状态:
期望玩家反馈:
失败信号:
证据形式:
```

字段说明：

| 字段 | 说明 |
|---|---|
| `前置状态` | 存档、日期、人偶状态、背包、金币、订单、地图节点等起点。 |
| `输入配置 / Seed` | 涉及随机、抽取、生成时必须给出 seed 或固定配置引用。 |
| `玩家行为` | 玩家做了什么，不写程序调用细节。 |
| `期望系统状态` | 物品、HP、SAN、金币、标签、订单、地图、事件等如何变化。 |
| `期望玩家反馈` | UI / 文案 / 动画 / 日志必须让玩家理解什么。 |
| `失败信号` | 出现哪些现象说明设计或实现偏离。 |
| `证据形式` | 截图、日志、调试摘要、配置校验报告、人工验收记录或自动化测试输出。 |

### 4.2 P0 验收补强清单

| ID | 目标 | 最低证据 |
|---|---|---|
| `V-ITEM-ROTATE-01` | 物品旋转、非法放置和撤回。 | 背包格状态截图或日志，证明旋转后占格、冲突和回滚正确。 |
| `V-ITEM-LIFE-01` | 战败 / 撤离时物品生命周期迁移。 | 战前物品列表、结算列表、库存结果和丢失原因。 |
| `V-COMBAT-INTENT-01` | 怪物意图可读并按预告执行。 | 回合开始意图、玩家行动、怪物行动、结果日志。 |
| `V-COMBAT-BAG-01` | 怪物对包干涉按优先级处理。 | 塞包 / 封格 / 推移 / 弹出到 Inbox 的冲突记录。 |
| `V-MAP-SEED-01` | 同 seed 地图复现。 | 两次生成的节点、连线、绑定内容和检查摘要完全一致。 |
| `V-MAP-ROUTE-01` | 地图无孤岛、Boss 可达、精英可绕。 | 路线检查摘要和至少一条非精英通 Boss 路线。 |
| `V-SAFEZONE-01` | 安全区免费全恢复且不清探索账本。 | 进入安全区前后 HP / SAN、账本、背包和安全盒记录。 |

## 5. 内容量承接规格

规则可开发不等于内容量已经足够。内容量补充应按“能支撑一个体验判断”来做，而不是只堆数量。

| 内容域 | 首批正式样例最低要求 | 设计目的 |
|---|---:|---|
| 物品 | 每个核心类型至少 2-3 个：武器、防具、消耗品、贸易品、材料、两栖物品。 | 让背包空间、出售、制造和战斗构筑都有真实取舍。 |
| 怪物 | 至少 4 个普通、2 个精英、1 个 Boss；覆盖攻击、护盾、塞包、封格、SAN 压力。 | 验证怪物意图和对包干涉不是单一数值怪。 |
| 深渊节点 | 至少覆盖普通战斗、精英、宝箱、事件、营地、Boss、安全区。 | 验证地图路线选择和搜打撤节奏。 |
| 经济事件 | 至少 3 个传闻、2 类顾客偏好、1 个违禁品代价、1 个月租账单。 | 验证经营压力能回流到下潜目标。 |
| 人偶反馈 | 每个核心情绪至少 2 条反馈：稳定、低 SAN、高 Bond、战败后、满载撤离后。 | 验证人偶状态不是静态面板。 |
| 订单 | 至少 3 类：交付物品、带回委托物、限期素材订单。 | 验证订单会改变路线和背包取舍。 |
| 房间记忆 | 至少 3 个纪念物：首次战败、首次 Boss 胜利、关键赠礼。 | 验证房间作为视觉日记成立。 |

## 6. 推进顺序

下一步策划补强建议按以下顺序：

1. 先补 `Items`、`Monsters`、`Dungeons` 的配置承接和 P0 验收样例，因为它们决定背包战斗和深渊地图主干。
2. 再补 `Dolls`、`Effects`、`Chassis`、`Prosthetics`、`CraftingRecipes` 的承接，因为它们决定人偶状态、养成和再挑战。
3. 然后补经济、订单、剧情和房间内容样例，让长期循环和情感回路有内容可测。
4. 每补一个配置域，都要回看对应 GDD、规则卡、`12_策划交付落地矩阵.md` 和 `13_策划跨系统验收场景矩阵.md` 是否仍一致。

---

## 7. 完成判定

一个系统的策划设计达到“正式纵切可交付”时，必须同时满足：

1.  GDD 和规则卡没有口径冲突。
2.  配置承接字段能解释内容如何扩展。
3.  表现承接能解释玩家如何读懂收益、代价和失败原因。
4.  验收样例能复现至少一条完整玩家路径。
5.  相关跨系统场景在 `13_策划跨系统验收场景矩阵.md` 中有覆盖。
6.  状态页记录当前系统已交付到哪一层，不把“规则可开发”误写成“配置 / 表现 / 验收全部完成”。
