# 策划文档开发交付审计

> **定位：** 本文档用于回答“`设计文档/` 是否已经达到可交付开发程度”。它不替代各 GDD 的事实来源，而是标记每份 GDD 当前能否直接交给程序、还缺哪些硬规格，以及下一步策划应先补什么。

---

## 1. 审计标准

一份 GDD 达到“可交付开发”至少需要满足以下条件：

| 维度 | 交付要求 |
|---|---|
| 规则闭环 | 说明核心流程、玩家输入、系统输出、成功/失败条件和边界情况。 |
| 数据契约 | 明确运行时需要的实体、状态字段、配置字段、ID 引用和跨系统数据流。 |
| 算法 / 状态机 | 涉及生成、刷新、抽取、判定、优先级、触发器时，需要给出步骤、约束和失败处理。 |
| 配置落点 | 说明应落到哪个配置目录、哪些字段由配置驱动、哪些字段是运行时实例状态。 |
| 验收用例 | 给出程序可复现的测试场景，例如 seed、输入状态、期望输出、边界 case。 |
| 当前口径一致 | 与 `GDD_07` 的天数轮转、`09` 正式纵切路线、配置源和程序边界不冲突。 |

结论分级：

| 等级 | 含义 |
|---|---|
| 可开发 | 程序可以开工，但仍建议在开发中补细节样例和测试。 |
| 需规则卡 | 方向成立，但缺少硬规格；进入开发前应先补一张系统规则卡。 |
| 暂不交付 | 目前更像体验设想或后续系统蓝图，不应直接作为程序实现依据。 |

---

## 2. 总判断

当前 `设计文档/` 已从“GDD 规则补齐”推进到“规则卡 + 承接层 + 首批内容包”的阶段。按“GDD + 对应规则卡 + 配置 / 表现 / 验收承接 + 已进入批次的正式内容包”的文档组口径，`GDD_00` 到 `GDD_12` 均已具备可交付开发的规则入口；P0 / P1 / P2 的首批正式内容也已经有可拆配置、表现和验收的内容包。

需要特别说明：部分 GDD 正文仍保留体验叙述和设计哲学写法，硬规格被拆到对应规则卡中承接。因此开发接单时不应只读单份 GDD，而应按本文第 3 节的“事实来源组合”阅读。若一个系统进入正式纵切批次，策划交付物至少应包括：对应 GDD、规则卡、配置承接说明、表现承接说明和验收场景。

当前剩余问题不再是 GDD 规则缺失，也不再是首批内容完全空白，而是规则和内容向实际配置、表现和机械校验落地时还需要继续对齐：

*   配置字段和运行时字段还没有在所有配置 README 中逐项分离。
*   部分配置 README 尚未承接 `15` 到 `25` 的承接清单和高优先级内容包字段、内容池与验收路径。
*   Validator 尚未覆盖全部 ID 引用、必填字段、状态机、触发器、内容包引用和 seed 复现样例。
*   UI / 美术表达仍需要按规则卡和内容包逐步形成 active 规格、资源清单和截图验收。
*   局外时间口径已通过 `01_局外时间与日程口径规则卡` 完成正式统一：局外使用 Day / Week / Month，局内 AP 只用于战斗回合。
*   战斗回合和怪物意图已通过 `03_战斗回合与怪物意图规则卡` 补齐基础状态机、意图字段、目标选择和验收样例。
*   小镇经济已通过 `04_小镇经济结算与压力链规则卡` 补齐每日营业状态机、售价公式、传闻价格波、违禁品隔夜代价、月租账单和欠债裁决。
*   局外成长已通过 `05_局外成长与维护规则卡` 补齐底盘、义体、心智天赋、维护、换装、成长实例字段和下潜许可检查。
*   标签与特质已通过 `06_标签与特质规则卡` 补齐标签命名、动态标签生命周期、查询表达、特质触发器、事件监听白名单、互斥 / 优先级 / 叠加、消除转化和持久化规则。
*   势力声望与订单已通过 `07_势力声望与订单规则卡` 补齐势力字段、订单定义 / 实例字段、刷新算法、截止日状态机、奖励引用、声望阈值、黑市背叛和委托物绑定规则。
*   人偶核心状态与好感双轨已通过 `08_人偶核心状态与好感双轨规则卡` 补齐人偶实例字段、SAN / Bond 阈值、情绪状态机、奇迹裁决、崩溃处置、特质输入事件和与交互系统的分工。
*   人偶交互已通过 `09_人偶交互事件与反馈规则卡` 补齐交互事件结构、触摸 / 对话 / 赠礼 / 保养 / 特殊交互、每日上限、偏好、反馈选择、对话池抽取和验收样例。
*   剧本调度已通过 `10_剧本调度与事件队列规则卡` 补齐剧本事件字段、触发器表达式、事件队列优先级、对话节点结构、系统指令、跳过 / 重入和存档旗标。
*   人偶房间已通过 `11_人偶房间布局与视觉叙事规则卡` 补齐房间布局数据、家具槽、展示品、纪念物、窗外状态、待机表现、资源 fallback、Validator 和验收样例。
*   P0 / P1 / P2 承接层已通过 `15`、`16`、`17` 明确配置字段、玩家可见信息、首批内容和联合验收路径。
*   正式内容生产口径已通过 `18` 统一，新增内容必须说明玩家承诺、玩法职责、系统连接、风险代价、表现需求和验收路径。
*   当前高优先级正式内容包已覆盖第一层、第二层、第三层路线侵蚀、人偶成长修复、小镇经济月租、长期记忆剧情和势力订单声望，分别见 `19` 到 `25`。`26_第四层组合压力内容包` 已作为后续层内容草案保留，但不列入当前优先推进范围。

正式纵切阶段可以有优先级，但不能把进入批次的系统按半成品标准设计。当前 GDD 层、规则卡层、承接层和首批内容包层已经完成这一轮策划补齐；下一步应按开发优先级把这些规则和内容包落到配置 README、样例配置、Validator、表现规格和可运行验收。

因此，当前“策划设计是否能交付开发”的结论应拆成两层：

1. **首批正式纵切：可交付。** 规则和内容包已经足够支持配置、表现和程序验收继续推进。
2. **完整正式版全量内容：未完成。** 后续仍要继续按 `18_正式版内容生产规格.md` 扩更多层级、更多人偶成长项、更多经济 / 订单 / 剧情 / 房间内容。

这不是 MVP 或 Alpha 口径，也不是先做半成品。当前已经按正式版设计质量处理进入纵切批次的系统；剩余工作是扩大正式内容覆盖面和落地验证。

## 4. P0 必补规则卡

这些规则卡会直接影响当前正式纵切能否继续开发，优先级最高。

### P0-1：局外时间口径统一规则卡（已完成正式口径统一）

涉及：`GDD_00`、`GDD_03`、`GDD_07`、`GDD_08`、`GDD_11`、`GDD_12`

事实来源：`01_局外时间与日程口径规则卡`

必须明确：

*   局内 AP 只用于战斗回合，不用于局外日程。
*   局外时间以 Day / Week / Month 为单位。
*   零时耗维护、交互、整理、购物、势力拜访不会推进天数。
*   每天只有一个推进时间的核心抉择：下深渊或休息 / 疗愈。
*   旧文档中“消耗 1AP / 夜晚 AP / 每天三次机会”的表述已从规则正文清理，只在禁止用语清单或审计说明中出现。

验收标准：

*   全 `设计文档/` 不再出现把局外行动写成 AP 消耗的规则。
*   程序只需要实现一套局外时间状态机。

### P0-2：物品与背包开发规则卡（已完成正式规则）

涉及：`GDD_01`、`GDD_06`

事实来源：`02_物品背包旋转与生命周期规则卡`

必须明确：

*   物品配置字段：形状、旋转、标签、触发组件、空间干涉、售价、掉落引用。
*   物品实例字段：InstanceID、Rotation、Durability、CorruptionLevel、DynamicTags、IsBinding、当前位置。
*   放置 / 旋转 / 拾取 / 丢弃 / 战败 / 撤离 / 出售 / 制造消耗的状态迁移。
*   对包干涉的统一规则：封锁格、侵占物、推移、交换、弹出到 Inbox 的优先级。

验收标准：

*   程序能按规则实现背包服务和配置 Validator。
*   自动化用例能覆盖旋转放置、非法放置、战败丢失、撤离保留和安全盒保留。

剩余对接项：
*   把规则卡中的定义字段同步到 `配置表(JSON)/Items/README.md` 和现有物品配置。
*   补物品 / 背包 Validator：形状合法性、旋转步长、标签引用、触发组件、容器状态和实例字段。

### P0-3：战斗与怪物意图规则卡（已完成正式规则）

涉及：`GDD_01`、`开发文档/11_怪物AI与行动系统(MonsterActionAI).md`

事实来源：`03_战斗回合与怪物意图规则卡`

必须明确：

*   战斗回合状态机：玩家回合、物品使用、结束回合、怪物行动、胜负结算。
*   怪物意图数据结构：伤害、防御、对包干涉、蓄力、未知意图。
*   多怪行动顺序、同回合多个对包干涉冲突处理。
*   典型怪物行为最小集合：普通攻击、护盾、塞包、封格、SAN 压力。

验收标准：

*   程序能配置至少 3 个行为差异明确的怪物。
*   玩家能在 UI 上看懂下一回合会发生什么。

剩余对接项：
*   把怪物意图字段同步到 `配置表(JSON)/Monsters/README.md` 和现有怪物配置。
*   补怪物 / 战斗 Validator：意图类型合法性、数值字段必填、目标规则合法、对包干涉引用合法、多怪行动顺序可复现。
*   UI 侧需要保证攻击、防御、塞包、封格、SAN 压力、蓄力和未知意图都有可读表达。

### P0-4：深渊地图生成开发规则卡（已并入 `GDD_02`）

涉及：`GDD_02`

当前 `GDD_02` 已经把正式节点网络规则补成程序可实现规格，可作为地图生成器当前纵切开发依据。

必须明确：

*   `LayerConfig` 字段：LayerID、RowCount、MinWidth、MaxWidth、BossEncounterID、BossRewardID、EncounterPool、RewardPool、EventPool。
*   `MapProfile` 字段：NodeTypeWeights、RouteThemes、RequiredNodes、Constraints、FogRules。
*   输出数据结构：NodeID、RowIndex、ColumnIndex、NodeType、Theme、BoundContentID、VisibleState、OutgoingEdgeIDs。
*   连线生成算法：候选列范围、交叉线限制、无孤岛校验、Boss 可达校验。
*   约束失败策略：局部替换次数、整层重生成次数、失败 fallback 规则。
*   Seed 验收样例：给定 `LayerID + RunSeed + MapProfileID`，输出固定节点摘要和检查结果。

剩余对接项：
*   把 `LayerConfig` / `MapProfile` 字段同步到 `配置表(JSON)/Dungeons/README.md`。
*   为地图配置补 Validator：必填字段、权重合法性、节点池引用、Boss / SafeZone 固定性、seed 复现测试。

验收标准：

*   同 seed 生成完全一致。
*   所有节点可达且可通 Boss。
*   第 1 层精英可绕开。
*   第 2 层至少出现一种机制压力。
*   已通层直达不会重复打一遍前置层。
*   安全区继续深入不会清空本轮探索账本。

## 7. 建议推进顺序

下一步不建议继续泛泛扩写所有 GDD，而应按当前纵切优先级补配置和验证落点：

1. 将 `02_物品背包旋转与生命周期规则卡.md` 同步到 `配置表(JSON)/Items/README.md` 和物品 / 背包 Validator。
2. 将 `03_战斗回合与怪物意图规则卡.md` 同步到 `配置表(JSON)/Monsters/README.md`、怪物配置、意图 UI 和战斗 Validator。
3. 把 `GDD_02` 的地图生成规则同步到 `配置表(JSON)/Dungeons/README.md` 和 Validator。
4. 将 `11_人偶房间布局与视觉叙事规则卡.md` 同步到 `配置表(JSON)/Dolls/README.md`、房间资源清单、UI / 美术规格和 Validator。
5. 将 `19` 到 `25` 的高优先级正式内容包拆到对应配置 README、样例 JSON、UI / 美术需求和验收脚本；`26` 暂作为后续层内容草案保留。
6. 回头清点各规则卡剩余配置 README / Validator 对接项，按当前开发优先级拆到配置与开发文档。

这条顺序符合正式纵切原则：不是把后续系统做成半成品，而是先让当前主干系统达到可开发、可验证、可维护的正式规格。
