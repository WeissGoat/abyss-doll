# 正式配置源落地准入门禁

> 本文用于判断“某个策划配置工作包是否可以进入 `配置表(JSON)` 源数据实现”。它不直接修改 JSON，不替代 `34` / `38` / `52` 的任务拆分，也不代表配置完成。它只定义进入配置源实现前必须具备的设计证据、实现中必须留下的证据、以及什么情况下不能标记为 `配置完成`。

---

## 1. 适用范围

本文覆盖 `26_正式配置设计与填充推进计划.md` 中已经进入正式配置推进的三类工作包：

| 工作包 | 任务拆分事实来源 | 准入目标 |
|---|---|---|
| 前三层正式配置 | `34_前三层正式配置实现任务拆分.md` | 判断 `L1/L2/L3` 的 Items、Rewards、Monsters、Dungeons、Orders、Events、Rumors、RoomMemory 是否可以开始改配置源。 |
| 局外成长正式配置 | `38_局外成长正式配置实现任务拆分.md` | 判断 `GROWTH-*` 是否可以开始改 Chassis、Effects、Prosthetics、CraftingRecipes、Dolls 等配置源。 |
| 经济压力正式配置 | `52_经济压力正式配置实现任务拆分.md` | 判断 `ECON-*` 是否可以开始改 Economy、Factions、Rumors、Orders 等配置源。 |

本文不处理程序实现、美术 UI 接入或运行时表现完成口径。那些状态分别回到 `agent_status/program.md`、`agent_status/art.md` 和对应事实文档。

---

## 2. 准入状态定义

| 状态 | 含义 | 可执行动作 |
|---|---|---|
| `未准入` | 只有概念、内容包或一句功能名，没有完整配置任务拆分。 | 先补 GDD、规则卡、配置承接审计、落地设计或任务拆分。 |
| `设计准入` | 已有 JSON 修改前策划清单、ID 口径、依赖顺序和验收样例。 | 可以派发配置源实现任务，但不能标记配置完成。 |
| `实现中` | 已开始修改配置源，仍未完成同步、引用检查或 Validator。 | 记录局部完成证据，保持 `进行中`。 |
| `验收中` | 配置源已落地，配置同步通过，静态引用 error 为 0，但固定样例或程序 Validator 尚未完全覆盖。 | 可以进入人工复核或程序工具补强。 |
| `配置完成` | 配置源已落地，同步通过，核心 Validator / 固定样例通过，warning 有归属。 | 只代表策划 / 配置职能完成，不代表程序、UI、美术全部完成。 |
| `跨职能完成` | 配置、程序服务、UI / 美术表现和验收门禁均有证据。 | 由相关职能状态页共同支撑，策划不能单独标记。 |

---

## 3. 设计准入门禁

任一配置源实现任务开工前，必须满足以下条件。

| 门禁 | 证据要求 | 不满足时处理 |
|---|---|---|
| 设计事实来源明确 | 能追到 GDD、规则卡、内容包、配置承接审计和配置落地设计。 | 回到对应设计文档补齐。 |
| 任务 ID 稳定 | 已在 `34`、`38` 或 `52` 中拆成稳定 TaskID。 | 先补任务拆分，不直接改 JSON。 |
| ID 口径清楚 | 新增、迁移、废弃 ID 有清单；局外成长看 `39`，经济压力看 `53` / `55`。 | 先补 ID 锁定或冲突检查。 |
| 配置域 README 可承接 | README 已说明正式字段、枚举、引用、迁移 warning 和当前程序未消费字段。 | 先补 README，不把缺字段压给 JSON 实现者猜。 |
| 依赖顺序清楚 | 上游配置存在后再写下游引用，例如 Items 先于 Rewards，Factions 先于 Orders。 | 按任务拆分重排派发顺序。 |
| 验收样例存在 | 至少有 Validator 建议、固定 seed、人工复核路径或等待工具原因。 | 先补验收样例，不允许无验收落地。 |
| 状态页无重复派发 | `agent_status/design.md` 未显示同名任务已配置完成或正在由其他 agent 执行。 | 合并证据或转为验收补强，不重复派发基础任务。 |

达到以上条件后，任务可标记为 `设计准入`，允许进入配置源实现。

---

## 4. 配置源实现证据

配置实现 agent 每完成一个任务，必须留下以下证据。缺任一项时，不能标记为 `配置完成`。

| 证据 | 最低要求 |
|---|---|
| 配置源文件 | 列出修改过的 `配置表(JSON)` 文件；不得只列运行时副本。 |
| ID 清单 | 列出新增、修改、迁移、废弃 ID。 |
| 引用检查 | 说明 ItemID、RewardID、MonsterID、LayerID、OrderID、EffectID、TraitID 等引用是否可解析。 |
| 同步结果 | 运行 `.\tools\config\Sync-Configs.ps1 -Clean`；无法运行时写明原因。 |
| Validator / 固定样例 | 运行已有 Validator、固定 seed 或人工复核；程序工具缺失时记录等待项和影响。 |
| 状态回写 | 更新 `agent_status/design.md`；如影响项目阶段、跨职能交接或长期节点门禁，再通知 PM 更新 `PROJECT_STATUS.md` / `09`。 |

不接受的证据：

- 只补 README 或设计文档，声称配置完成。
- 只改 JSON，没有 ID 清单和引用检查。
- 只同步配置，没有说明源 JSON 改了什么。
- 只跑一个局部 smoke test，声称整个系统配置完成。
- 程序 UI 能显示某个条目，就声称策划配置全部完成。

## 5. 三类工作包准入表

### 5.1 前三层正式配置

| 批次 | 设计准入证据 | 当前结论 | 下一步 |
|---|---|---|---|
| `L1-ITEMS` 到 `L1-SEED` | `31`、`34`、`35` | 设计准入 | 可从 `L1-ITEMS` 开始实现配置源。 |
| `L2-ITEMS` 到 `L2-SEED` | `32`、`34`、`35` | 设计准入 | 等 L1 方法跑通后推进；订单任务需要确认 Orders 配置源结构。 |
| `L3-ITEMS` 到 `L3-SEED` | `33`、`34`、`35` | 设计准入 | 等 L1/L2 引用链稳定后推进；路线侵蚀和订单互斥需额外验收。 |

准入限制：

1. 不建议跳过 L1 直接实现 L3。
2. 不得先写 Dungeons 引用不存在的 Monsters / Rewards。
3. Boss 成长材料保底必须挂在 Boss 奖励，不挂在精英奖励。

### 5.2 局外成长正式配置

| 批次 | 设计准入证据 | 当前结论 | 下一步 |
|---|---|---|---|
| `GROWTH-CHASSIS` | `39`、`40` | 设计准入 | 可实现 3 个底盘配置源。 |
| `GROWTH-EFFECTS-TRAITS` | `39`、`41` | 设计准入 | 可先实现效果、动态标签和特质字典。 |
| `GROWTH-PROSTHETICS` | `39`、`41`、`42` | 设计准入 | 等效果 / 特质可引用后实现义体。 |
| `GROWTH-CRAFT-MAINT` | `42`、`43` | 设计准入 | 等义体 ID 稳定后实现配方和维护方案。 |
| `GROWTH-DOLL-TRAIT-ROOM` | `41`、`44` | 设计准入 | 可实现人偶静态档案、反馈、特质和房间记忆配置。 |
| `GROWTH-VALIDATION` | `45` | 设计准入 | 配置源落地后执行 Validator / 固定样例。 |

准入限制：

1. `Dolls` 静态配置不得写入 HP、SAN、Bond、磨损、侵蚀等运行时状态。
2. 高收益义体必须有维护、磨损、槽位冲突、适应期或其他长期代价。
3. 负面特质必须有修复、转化或归档路径。

### 5.3 经济压力正式配置

| 批次 | 设计准入证据 | 当前结论 | 下一步 |
|---|---|---|---|
| `ECON-CORE-JSON` | `47`、`54` | 设计准入 | 可实现 Economy 核心配置源。 |
| `ECON-FACTIONS-JSON` | `49`、`53`、`54` | 设计准入 | 可实现 5 个势力、声望 / 信任阶梯和订单池引用。 |
| `ECON-RUMORS-JSON` | `48`、`53`、`54` | 设计准入 | 等 Economy / Factions 可引用后实现 8 条传闻。 |
| `ECON-ORDERS-JSON` | `50`、`52`、`53`、`54`、`55` | 设计准入 | 等 Factions / Rewards / Items / Dungeons 引用稳定后实现 5 池 19 单。 |
| `ECON-CROSS-REFS` | `51`、`52` | 设计准入 | 配置源落地后检查跨域引用。 |
| `ECON-VALIDATION-RUN` | `51`、`52` | 设计准入 | 配置同步后执行 Validator / 固定样例。 |

准入限制：

1. 订单不得先于势力落地。
2. `Orders` 使用 `55` 锁定的 5 个 OrderPoolID 和 19 个 OrderID。
3. 旧 `order_mechanic_scrap_drive` 不进入正式订单池，必须迁移或标记为 deprecated / test sample。
4. 经济压力不能在前三层阶段形成不可恢复死锁。

## 6. 状态回写规则

配置源实现后的状态回写只写事实，不写聊天过程。

| 场景 | 回写位置 | 写法 |
|---|---|---|
| 设计准入完成 | `agent_status/design.md` | 记录准入文档和可派发任务，不写配置完成。 |
| 单个配置域 JSON 完成 | `agent_status/design.md` | 记录任务 ID、修改文件、同步 / Validator 结果，状态仍可为 `进行中`。 |
| 某工作包进入验收 | `agent_status/design.md`，必要时 `PROJECT_STATUS.md` | 记录 error=0、warning 归属、固定样例缺口。 |
| 配置职能完成 | `agent_status/design.md` | 只有配置源、同步、Validator / 样例证据齐全时才写 `配置完成`。 |
| 影响长期节点门禁 | 通知 PM 更新 `版本规划/09_正式版核心纵切开发路线.md` | 只更新节点门禁或入口，不写详细执行表。 |
| 需要程序 Validator | `agent_status/program.md` 或开发文档 | 由程序职能承接，不写入 `26` 的策划执行表。 |
| 需要 UI / 美术表现 | `agent_status/art.md` 或美术文档 | 由美术 / UI 职能承接，不写入 `26` 的策划执行表。 |

---

## 7. 完成判定

本文完成后，只能说明“正式配置源落地准入门禁已定义”。它不表示任何 JSON 已经完成。

后续某个配置工作包要标记为 `配置完成`，必须逐项证明：

1. 设计准入门禁已满足。
2. 配置源 JSON 已修改。
3. 运行时配置副本由同步脚本生成，不是手写维护。
4. 关键引用 error 为 0。
5. Validator / 固定 seed / 人工复核至少覆盖核心路径。
6. warning 有归属和后续处理口径。
7. `agent_status/design.md` 已回写证据。
8. 如果影响长期节点门禁，PM 已同步 `09` 或确认无需同步。

在这些证据齐全前，任何 README、任务拆分、ID 锁定、字段级设计、验收样例或本文本身，都只能算策划 / 配置设计证据。
