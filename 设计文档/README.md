# 设计文档阅读入口

> **定位：** 本文件只说明 `设计文档/` 的文档层级和阅读顺序，不替代任何 GDD、规则卡、交付矩阵或内容包。后续 agent 进入策划工作前，应先用本文判断“该读哪一层文档”，再进入具体事实来源。

---

## 1. 当前目录为什么看起来像两套编号

`设计文档/` 里现在有两套编号：

| 文件组 | 层级 | 作用 |
|---|---|---|
| `GDD_00` 到 `GDD_12` | 系统设计母文档 | 定义系统存在理由、体验目标、核心循环、跨系统关系和设计边界。 |
| `00_` 到 `26_` | 策划交付辅助文档 | 把 GDD 拆成规则卡、交付矩阵、验收场景、内容生产规格和具体内容包。 |

它们不是同一层级，也不是互相替代关系。`GDD_xx` 是系统设计源头；普通数字编号文件是为了让系统能被开发、配置、表现和验收继续承接。

---

## 2. 文档层级

### 2.1 GDD：系统设计母文档

阅读目的：理解“这个系统是什么、为什么存在、和其他系统怎么连”。

代表文件：

- `GDD_00_系统关联总图.md`
- `GDD_01_背包战斗与局内网格机制.md`
- `GDD_02_深渊地图遍历与搜打撤抉择.md`
- `GDD_03` 到 `GDD_12` 各系统 GDD

GDD 是最高层策划事实来源。系统方向、体验目标和跨系统关系以 GDD 为准。

### 2.2 规则卡：可开发裁决层

阅读目的：理解“程序遇到边界情况时怎么判定”。

代表文件：

- `01_局外时间与日程口径规则卡.md`
- `02_物品背包旋转与生命周期规则卡.md`
- `03_战斗回合与怪物意图规则卡.md`
- `04_小镇经济结算与压力链规则卡.md`
- `05_局外成长与维护规则卡.md`
- `06_标签与特质规则卡.md`
- `07_势力声望与订单规则卡.md`
- `08_人偶核心状态与好感双轨规则卡.md`
- `09_人偶交互事件与反馈规则卡.md`
- `10_剧本调度与事件队列规则卡.md`
- `11_人偶房间布局与视觉叙事规则卡.md`

规则卡不取代 GDD。它们把 GDD 中分散的字段、状态机、算法、边界和验收样例提炼出来，服务程序实现、配置校验和自动化验收。

### 2.3 交付与验收矩阵：承接层

阅读目的：理解“设计如何拆给配置、UI / 美术、程序和验收”。

代表文件：

- `00_策划文档开发交付审计.md`
- `12_策划交付落地矩阵.md`
- `13_策划跨系统验收场景矩阵.md`
- `14_策划配置表现验收承接规格.md`
- `15_P0主干配置表现验收承接清单.md`
- `16_P1人偶成长情感承接清单.md`
- `17_P2长期循环叙事承接清单.md`

这一层不是新的玩法设计，而是策划交付管理层。它回答配置字段、表现信息、Validator、验收路径和跨职能交接要如何承接。

### 2.4 内容生产规格：内容标准层

阅读目的：理解“物品、怪物、订单、事件、房间记忆等内容怎么写才算正式版质量”。

代表文件：

- `18_正式版内容生产规格.md`
- `26_正式配置设计与填充推进计划.md`

`18` 不定义某个系统规则，而是定义内容条目的质量标准：玩家承诺、玩法职责、系统连接、风险代价、表现需求和验收路径。

`26` 不写具体内容条目，而是定义下一阶段正式配置设计与填充的推进顺序、内容量目标、可玩时长目标和从整体到局部的工作包。

### 2.5 内容包：具体内容填充层

阅读目的：理解“某一层副本、某个长期系统或某批内容具体有哪些条目”。

当前已有内容包：

- `19_第一层正式核心内容包.md`
- `20_第二层背包压力内容包.md`
- `21_人偶成长修复内容包.md`
- `22_小镇经济月租内容包.md`
- `23_长期记忆剧情内容包.md`
- `24_势力订单声望内容包.md`
- `25_第三层路线侵蚀内容包.md`

内容包是内容填充资料，不是当前顶层开发路线。后续每层副本、更多订单链、更多剧情和房间记忆都可以继续按 `18` 的标准扩展。

低优先级后续层内容草案已移入 `设计文档/_archive/content_backlog/`。`26_第四层组合压力内容包.md` 暂不列入当前优先推进范围；待第四层进入正式内容生产批次时，再从归档区复审并恢复到主目录或拆分为新的 active 内容包。

5. 对应内容包，如已经进入本轮开发

### 3.3 新增一批内容

1. `18_正式版内容生产规格.md`
2. `26_正式配置设计与填充推进计划.md`
3. 对应系统 GDD
4. 对应规则卡
5. 已有同类内容包
6. 对应配置 README、表现规格和验收矩阵

## 4. 当前优先级口径

当前不继续横向扩写更多层副本内容包。近期策划优先级是：

1. 稳定文档层级和阅读入口。
2. 让 `GDD_00` 到 `GDD_12`、规则卡和交付矩阵形成清晰事实来源关系。
3. 按 `26_正式配置设计与填充推进计划.md` 先做正式配置承接审计，再补前三层正式配置和局外成长 / 经济目标。
4. 把背包、战斗、深渊地图这条主干对应到配置 README、表现规格和 Validator。
5. 继续按正式版标准处理进入批次的系统，但不把“内容包数量”当作当前进度核心。

正式纵切仍然表示开发顺序，不表示质量降级。系统可以晚做；一旦进入批次，就按正式版完整标准设计。

## 5. 系统需求文档门禁

后续任何系统进入开发、配置、表现或自动验收前，不能只停留在 `09` 路线、状态页、优先级列表或聊天结论中的一句话。策划智能体必须先确认它已经有详细需求文档承接。

可接受的承接文档包括：

- 对应系统 GDD。
- 对应规则卡。
- 交付 / 验收承接清单。
- 具体内容包。
- 配置 README。
- 面向程序或美术的专项需求文档。

如果现有文档已经足够详细，交接时必须引用完整交付包，而不是只引用单句功能项。如果现有文档不足，先补文档再推动开发。

详细需求文档至少应覆盖：

1. 设计目标和玩家可见体验。
2. 范围外和暂不处理内容。
3. 核心规则、状态机、算法或生成约束。
4. 关键配置字段、枚举、ID 引用和默认值。
5. 跨系统关系和数据流。
6. UI / 美术表现需求。
7. Validator、自动验收或手动验收样例。
8. 完成判定和失败 / 阻塞条件。
