# 设计文档阅读入口

> **定位：** 本文件只说明 `设计文档/` 的文档层级和阅读顺序，不替代任何 GDD、规则卡、交付矩阵或内容包。后续 agent 进入策划工作前，应先用本文判断“该读哪一层文档”，再进入具体事实来源。

---

## 1. 当前目录为什么看起来像两套编号

`设计文档/` 里现在有两套编号：

| 文件组 | 层级 | 作用 |
|---|---|---|
| `GDD_00` 到 `GDD_12` | 系统设计母文档 | 定义系统存在理由、体验目标、核心循环、跨系统关系和设计边界。 |
| `00_` 到当前数字编号文档 | 策划交付辅助文档 | 把 GDD 拆成规则卡、交付矩阵、验收场景、内容生产规格、具体内容包、配置承接审计、任务拆分和验收样例。 |

它们不是同一层级，也不是互相替代关系。`GDD_xx` 是系统设计源头；普通数字编号文件是为了让系统能被开发、配置、表现和验收继续承接。

---

## 2. 文档层级

### 2.1 GDD：系统设计母文档

阅读目的：理解“这个系统是什么、为什么存在、和其他系统怎么连”。

代表文件：

- `GDD_00_系统关联总图.md`
- `GDD_01_背包战斗与局内网格机制.md`
- `GDD_02_深渊地图遍历与搜打撤抉择.md`
- `GDD_03` 到 `GDD_12` 各系统 GDD

GDD 是最高层策划事实来源。系统方向、体验目标和跨系统关系以 GDD 为准。

### 2.2 规则卡：可开发裁决层

阅读目的：理解“程序遇到边界情况时怎么判定”。

代表文件：

- `01_局外时间与日程口径规则卡.md`
- `02_物品背包旋转与生命周期规则卡.md`
- `03_战斗回合与怪物意图规则卡.md`
- `04_小镇经济结算与压力链规则卡.md`
- `05_局外成长与维护规则卡.md`
- `06_标签与特质规则卡.md`
- `07_势力声望与订单规则卡.md`
- `08_人偶核心状态与好感双轨规则卡.md`
- `09_人偶交互事件与反馈规则卡.md`
- `10_剧本调度与事件队列规则卡.md`
- `11_人偶房间布局与视觉叙事规则卡.md`

规则卡不取代 GDD。它们把 GDD 中分散的字段、状态机、算法、边界和验收样例提炼出来，服务程序实现、配置校验和自动化验收。

### 2.3 交付与验收矩阵：承接层

阅读目的：理解“设计如何拆给配置、UI / 美术、程序和验收”。

代表文件：

- `00_策划文档开发交付审计.md`
- `12_策划交付落地矩阵.md`
- `13_策划跨系统验收场景矩阵.md`
- `14_策划配置表现验收承接规格.md`
- `15_P0主干配置表现验收承接清单.md`
- `16_P1人偶成长情感承接清单.md`
- `17_P2长期循环叙事承接清单.md`

这一层不是新的玩法设计，而是策划交付管理层。它回答配置字段、表现信息、Validator、验收路径和跨职能交接要如何承接。

### 2.4 内容生产规格：内容标准层

阅读目的：理解“物品、怪物、订单、事件、房间记忆等内容怎么写才算正式版质量”。

代表文件：

- `18_正式版内容生产规格.md`
- `26_正式配置设计与填充推进计划.md`

`18` 不定义某个系统规则，而是定义内容条目的质量标准：玩家承诺、玩法职责、系统连接、风险代价、表现需求和验收路径。

`26` 不写具体内容条目，而是定义下一阶段正式配置设计与填充的推进顺序、内容量目标、可玩时长目标和从整体到局部的工作包。

### 2.5 配置承接审计：配置落地检查层

阅读目的：理解“现有配置源是否已经能承接正式规则和内容包”。

代表文件：

- `27_Items正式配置承接审计.md`
- `28_Monsters正式配置承接审计.md`
- `29_Dungeons正式配置承接审计.md`
- `30_Rewards正式配置承接审计.md`
- `36_局外成长正式配置承接审计.md`
- `46_经济压力正式配置承接审计.md`

配置承接审计不是新的玩法规则，也不是已完成的配置落地。它负责把规则卡、内容包、配置 README 和现有 JSON 对照起来，输出字段缺口、内容缺口、Validator 建议和下一步配置任务。

### 2.7 配置实现任务拆分：派发与证据层

阅读目的：理解“前三层正式配置后续真正改 JSON 时，应该拆成哪些任务、按什么顺序派发、交付什么证据、如何防止重复派发”。

当前已有任务拆分：

- `34_前三层正式配置实现任务拆分.md`
- `38_局外成长正式配置实现任务拆分.md`
- `39_局外成长正式配置ID锁定与冲突检查.md`
- `52_经济压力正式配置实现任务拆分.md`

任务拆分、ID 锁定、README 字段口径检查、字段级设计和准入门禁不直接修改 JSON，也不表示配置完成。`34` 把 `31` / `32` / `33` 的策划清单拆成 `L1-ITEMS`、`L1-REWARDS`、`L1-MONSTERS`、`L1-DUNGEONS`、`L1-SEED` 等可执行批次；`38` 把 `37` 的局外成长清单拆成 `GROWTH-ID-LOCK`、`GROWTH-CHASSIS`、`GROWTH-EFFECTS-TRAITS`、`GROWTH-PROSTHETICS`、`GROWTH-CRAFT-MAINT`、`GROWTH-DOLL-TRAIT-ROOM`、`GROWTH-VALIDATION`；`39` 记录 `GROWTH-ID-LOCK` 的当前工作区 ID 冲突检查证据；`40` 记录 `GROWTH-CHASSIS` 的底盘 JSON 修改前字段级设计；`41` 记录 `GROWTH-EFFECTS-TRAITS` 的效果、动态标签和特质 JSON 修改前字段级设计；`42` 记录 `GROWTH-PROSTHETICS` 的 6 个正式义体 JSON 修改前字段级设计；`43` 记录 `GROWTH-CRAFT-MAINT` 的制造配方、底盘解锁、维护方案和材料来源 JSON 修改前字段级设计；`44` 记录 `GROWTH-DOLL-TRAIT-ROOM` 的人偶静态档案、运行时拆分、特质、反馈和房间纪念物 JSON 修改前字段级设计；`45` 记录 `GROWTH-VALIDATION` 的 Validator 覆盖、固定样例、warning / error 分级和状态回写证据模板；`52` 记录经济压力 `ECON-ID-LOCK`、`ECON-README-CHECK`、`ECON-CORE-JSON`、`ECON-FACTIONS-JSON`、`ECON-RUMORS-JSON`、`ECON-ORDERS-JSON`、`ECON-CROSS-REFS`、`ECON-VALIDATION-RUN` 和 `ECON-STATUS-WRITEBACK` 的派发顺序与证据模板；`53` 记录 `ECON-ID-LOCK` 的当前工作区 ID 冲突检查证据；`54` 记录 `ECON-README-CHECK` 的四个经济压力配置 README 字段口径检查证据；`55` 记录经济压力首批 5 个订单池和 19 个订单模板的最终 ID 锁定证据；`56` 统一定义前三层、局外成长和经济压力进入配置源 JSON 实现前的设计准入、实现证据和状态回写口径。后续配置实现必须先按 `56` 检查准入，再留下 ID 清单、引用检查、同步结果、Validator / seed 验收和 `agent_status/design.md` 回写；如影响长期节点门禁，再通知 PM 更新 `09`。

### 2.8 配置验收样例：Validator 与固定 seed 层

阅读目的：理解“前三层正式配置完成后，应该用哪些 Validator、固定 seed 和人工复核路径证明它真的可玩、可回归、可回写台账”。

## 4. 当前优先级口径

当前不继续横向扩写更多层副本内容包。近期策划优先级是：

1. 稳定文档层级和阅读入口。
2. 让 `GDD_00` 到 `GDD_12`、规则卡和交付矩阵形成清晰事实来源关系。
3. 按 `26_正式配置设计与填充推进计划.md` 先做正式配置承接审计；`Items` / `Monsters` / `Dungeons` / `Rewards` 首轮审计见 `27_Items正式配置承接审计.md`、`28_Monsters正式配置承接审计.md`、`29_Dungeons正式配置承接审计.md`、`30_Rewards正式配置承接审计.md`。

## 5. 系统需求文档门禁

后续任何系统进入开发、配置、表现或自动验收前，不能只停留在 `09` 路线、状态页、优先级列表或聊天结论中的一句话。策划智能体必须先确认它已经有详细需求文档承接。

可接受的承接文档包括：

- 对应系统 GDD。
- 对应规则卡。
- 交付 / 验收承接清单。
- 具体内容包。
- 配置 README。
- 面向程序或美术的专项需求文档。

如果现有文档已经足够详细，交接时必须引用完整交付包，而不是只引用单句功能项。如果现有文档不足，先补文档再推动开发。

详细需求文档至少应覆盖：

1. 设计目标和玩家可见体验。
2. 范围外和暂不处理内容。
3. 核心规则、状态机、算法或生成约束。
4. 关键配置字段、枚举、ID 引用和默认值。
5. 跨系统关系和数据流。
6. UI / 美术表现需求。
7. Validator、自动验收或手动验收样例。
8. 完成判定和失败 / 阻塞条件。
