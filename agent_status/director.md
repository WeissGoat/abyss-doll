# 游戏导演 / 制作人 状态

## 最后更新

2026-07-04

## 当前关注

本状态页取代旧 `PM / 版本规划` 活跃入口。当前顶层角色偏主策 / 游戏导演，同时兼管制作推进：先定义玩家体验主线、系统开放节奏、深渊包装、当前版本目标和完成口径，再把工作拆成可执行的玩家结果。

当前宏观设计重点已从“8-12 小时候选版主循环”推进到“全游戏宏观大纲 + 全系统体验归位 + 全游戏模块宏观设计矩阵”：8-12 小时只作为候选版主循环门槛，不再作为完整游戏范围上限。现有 `GDD_01` 到 `GDD_12` 全部保留并纳入完整游戏大纲，后续只区分核心主线、阶段开放、表现 / 记忆层、制作门禁和制作冗余压缩。

`13` 现已补齐模块总谱：全局美术 / UI 体验语言、深渊层级、小镇、人偶、战斗 / 背包、经济 / 订单 / 势力、日程、叙事 / 房间和配置 / 验收都有宏观职责、包装关键词、玩法压力、模块连接、主负责设计、细化验收与实现接入口径。后续实现切片不只标注时长段和玩家结果，还必须引用对应模块宏观设计行。

2026-06-12 已修正全局美术 / UI 体验语言：正式主轴为“日系二次元地底奇幻冒险 + 低信息密度”。机械、工坊和旧工具只作为局部系统语义；黄铜、铜件、暖灯和蒸汽朋克不再作为全局风格关键词，也不作为实现切片默认美术验收方向或正向生图提示词方向。

剧情母线已有独立设计入口：`设计文档/剧情/00_剧情大纲.md` 将草稿中的没落工匠、零号魔偶、晶化病、记忆拼图、债务压力和多结局收束为 active 叙事母版。后续 T0-T4 细案、长期记忆内容包和实现切片都应把它作为“写什么故事”的上层参考，但具体事件触发、字段和验收仍回到 GDD / 规则卡 / 内容包。

后续开发节点已改为按玩家游玩时长横向切分：0-30 分钟、30 分钟-2 小时、2-5 小时、5-8 小时、8-12 小时、12-20 小时、20-35 小时、35 小时以后。每个时长段都包含深渊、战斗 / 背包、小镇、人偶状态 / 养成、日程、叙事反馈、UI / 美术和验证门禁，只是开放深度不同；当前最近实际目标是补齐 0-12 小时候选主循环。

0-12 小时候选主循环现在按游戏时长横向切分回到设计稿口径。`14` 维护的是 T0-T4 时长段设计索引和承接规则；具体细案存放在 `版本规划/0-12小时细案/`。当前 `T0` 已改写为 `0-30 分钟` 的序章首次循环设计稿，`T1` 已补为 `30 分钟-2 小时` 的第一层搜打撤成形设计稿，`T2..T4` 仍是待设计队列，未完成设计前不作为正式实现依据。

项目工作模式从“按职能分包”调整为“细案 Owner 统一设计 + 实现 Owner 纵切负责”。0-12 小时细案 Owner 先按时长段完善设计细案，保证前后体验融合；实现 Owner 再围绕单一玩家结果按 `证据审计 -> 阅读细案 -> 本切片具体方案设计 -> 配置源落地 -> UI/UX 与美术接入方案 -> 程序接入 -> Owner 自验 -> 职能总监验收 -> 状态回写` 串完，减少多 agent 之间传话造成的损耗。

Owner 自验只证明本切片已按玩家路径整理证据，不等于最终完成；最终完成仍需要对应主策、主程、主美 / UI 视觉总监或游戏导演 / 制作人的外部验收。

职能 agent 后续默认作为主策、主程、主美 / UI 视觉总监参与：负责规则审定、架构验收、视觉方向和质量门禁，不再作为常规执行分包的默认承接者。图片生成、大批量素材处理、大规模配置填充等耗时工作可以单独拆给专门 agent，但必须由细案 Owner 或实现 Owner 提供明确输入、输出和验收标准。

当前导演判断：下一步应继续补 0-12 小时的游戏设计，而不是把设计稿继续拆成验收点。`T0` 序章首次循环和 `T1` 第一层搜打撤成形已经写回；下一步优先完善 `T2 2-5 小时：小镇压力与下潜目标成形`。

## 工作边界

- 游戏导演 / 制作人负责全局体验、开放节奏、优先级、细案 / 实现切片拆分和最终玩家结果判断。
- 0-12 小时细案 Owner 负责维护 `14` 的 T0-T4 时长段设计索引与承接规则，并在 `版本规划/0-12小时细案/` 中逐段完善具体设计细案；未完成设计的时长段不作为实现 Owner 正式开工依据。
- 具体系统规则仍回写 GDD / 规则卡；程序契约仍回写开发文档；视觉规格仍回写美术文档；配置源仍以 `配置表(JSON)` 为准。
- 实现 Owner 可以跨职能改动，但必须遵守细案、各职能事实来源和工程边界，并在完成时同步所有受影响状态页。
- 实现 Owner 自验是第一层证据整理，不替代主策 / 主程 / 主美 / 游戏导演的外部验收。
- 主策 / 主程 / 主美默认做验收和总体设计把关；只有用户明确派为任务 Owner 或耗时专工时，才承担具体实现。
- 旧 `agent_status/pm.md` 仅作为兼容入口保留，不再作为活跃派发角色。
