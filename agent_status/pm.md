# PM / 版本规划 状态

## 最后更新

2026-05-25

## 当前关注

作为 PM 智能体管理正式版核心纵切的版本规划，维护 `09` 宏观总线、`11` 纵切批次与需求文档承接矩阵、项目总状态、系统纵切优先级和跨职能交接闭环。当前重点是让版本规划目录职责清晰，并把 P0 验收底座、P1 背包 / 物品生命周期、P1 战斗、P2/P3 深渊与成长、P4 经济压力纳入长期节点节奏。

新增门禁：`09` / `11` 中提到的需求必须能在 `11_纵切批次与需求文档承接矩阵.md` 中追到详细文档；不能只有一句功能名就进入当前开发范围。长期节点、节点门禁、职能进度入口、状态标记规则和防重复派发规则已并入 `09`。

新增执行规则：详细进度按职能回写状态页和事实文档。策划 / 配置看 `agent_status/design.md`、`设计文档/config/26_正式配置设计与填充推进计划.md` 和 `设计文档/config/gates/56_正式配置源落地准入门禁.md`；程序看 `agent_status/program.md` 与开发文档；美术 / UI 看 `agent_status/art.md` 与美术文档；PM 看本文件和 `PROJECT_STATUS.md`。同一系统涉及多个职能时拆开记录，不写跨职能混合执行表。需要挂钩进度时，按 `09` 的职能入口和状态口径写入对应职能事实来源。字段说明、README、审计结论、任务拆分、ID 锁定、准入门禁和 JSON 修改前设计不等于配置源完成，不能直接标记为 `配置完成`。

## 工作边界

- PM 负责版本路线、阶段判断、里程碑拆分、优先级排序、跨职能交接和完成标准。
- PM 不替代策划、程序或美术事实来源；系统规则写入 GDD，程序边界写入开发文档，美术交付写入美术文档。
- 版本规划变更应同步 `版本规划/09_正式版核心纵切开发路线.md`、`PROJECT_STATUS.md`、本文件和受影响的职能状态页。
- 旧 MVP 规划文档只作为历史验证资料；当前阶段以 `09` 路线和当前 GDD 为准。
- PM 拆分工作包时应写清目标、范围外、涉及事实来源、职能交接和验收方式。

## 当前版本判断

项目处于正式版核心纵切阶段。这里的纵切是开发顺序，不是质量降级：被选中的系统按正式版标准完整处理。当前程序正式版本完成口径已经校准为：仅 P0 自动验收底座、P1 背包 / 物品生命周期完成；P1 战斗、P2 深渊、P3 局外成长、P4 经济压力和 P5 表现支撑均按未开始处理。

## 下一步建议

1. 后续派发任何 P0-P5 工作前，先查对应职能状态页，确认不是已完成或进行中的同名工作。
2. 新增需求先走 `11` 查详细文档承接；新增长期节点、节点门禁、职能入口或状态标记规则才更新 `09`。
3. 下一轮 PM 拆任务时，应从职能状态页和事实文档确认具体缺口：P1 战斗 / 怪物意图、P2 深渊地图、P3 局外成长、P4 经济压力和 P5 表现支撑；P0 / P1 已完成项只做验收补强或缺口修复。
4. 每次开发、配置、美术或验收完成后，先回写对应职能状态页；同一系统的策划、程序、美术工作拆开记录，详细方案回到对应职能文档；通用状态口径按 `09` 执行。
5. 策划 / 配置侧进入 JSON 实现时，先按 `56` 检查设计准入，再在 `agent_status/design.md` 和配置事实文档记录配置源、配置同步证据、Validator 需求和固定验收样例；程序 Validator 实现、Unity 测试和 UI 表现分别回写程序 / 美术状态页。
