# 纵切批次与需求文档承接矩阵

> **定位：** 本文合并原 `11` 的 GDD 纵切批次矩阵和原 `12` 的需求文档承接审计。它回答两个问题：每个系统何时进入正式纵切；进入后是否已有足够详细的需求文档支撑。具体工作项是否已开发、是否可重复派发，以对应职能状态页和事实文档为准；长期节点、职能入口和防重复派发规则见 `09`。

---

## 1. 使用规则

`09_正式版核心纵切开发路线.md` 只定义宏观优先级。任何功能、系统、工具或验收门禁进入当前开发范围前，必须在本文确认：

1. 属于哪个功能优先级或纵切批次。
2. 对应哪些 GDD / 规则卡 / 承接清单 / 内容包 / 开发文档 / 美术规格 / 配置 README。
3. 是否已经达到可沟通、可开发、可验收的详细程度。

合格的需求文档至少应覆盖：

- 设计目标和玩家可见体验。
- 范围外。
- 核心规则、状态机、算法或生成约束。
- 关键配置字段、枚举、ID 引用或资源引用。
- 跨系统关系。
- UI / 美术表现需求。
- Validator、自动化验收或人工验收样例。
- 完成判定。

状态定义：

| 状态 | 含义 | 处理方式 |
|---|---|---|
| `通过` | 已有详细文档承接，可继续拆任务。 | 后续变更时同步维护。 |
| `观察` | 已有规则文档，但实现前还要同步配置 README、active UI 规格或 Validator。 | 不阻塞规划，派任务时必须带上缺口。 |
| `缺口` | 只有路线中的一句话或泛泛描述，无法独立交付。 | 先补需求文档，再进入开发。 |

## 4. 实现状态归属

本文不再维护“当前实现进度”表。原因是实现状态会按职能变化，如果同时写在本文和版本总线中，很容易出现重复和冲突。

后续判断方式：

1. 本文只回答“需求是否已有详细文档承接”。
2. 具体工作项状态、证据入口、防重复派发口径，统一查看对应职能状态页和事实文档：PM 看 `agent_status/pm.md`，策划 / 配置看 `agent_status/design.md` 与 `设计文档/config/26_正式配置设计与填充推进计划.md`，程序看 `agent_status/program.md` 与开发文档，美术 / UI 看 `agent_status/art.md` 与美术文档。
3. 如果 `09` 的节点判断与代码事实、验收报告或职能状态页冲突，先核对证据，再更新 `09` 的节点门禁或职能入口说明，不要在本文新增第二张实现进度表。

| 第四层以后内容包 | 已降优先级，不属于当前功能开发主线。 | 进入后续层内容生产批次时，按 `18_正式版内容生产规格.md` 重新审计。 |

## 6. 后续维护门禁

后续修改 `09` 或本文时必须同步检查：

1. 新增功能方向是否已有详细需求文档。
2. 新增 GDD 批次职责是否能追到规则卡、承接清单、配置 README、开发文档或美术规格。
3. 如果只是新增一句功能名，先补详细需求文档，再列入当前开发范围。
4. 如果需求已有文档，只更新承接表和状态。
5. 如果需求改为后续批次，在本文标记为非当前门禁项，避免误导开发。

当前结论：截至 2026-05-24，版本规划 active 文档中提到的当前需求项均已有详细需求文档承接，未发现需要立即补文档的阻塞项。
