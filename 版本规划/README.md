## 已移除的重复文档

`10_正式版核心纵切版本节点规划.md` 已删除，不再维护。

删除原因：旧 `10` 和 `09` 的阶段 / 优先级、`11` 的 GDD 批次关系高度重复，容易造成版本规划互相抢事实来源。后续需要判断宏观优先级、长期节点、节点门禁、职能入口和防重复派发规则时维护 `09`；需要判断某份 GDD 的批次、完成口径和需求承接时维护 `11`。

旧 `13_跨职能工作项进度台账.md` 不再单独维护，也不再以 active 进度台账形式恢复。当前新的 `13_正式版全局体验总线与开放节奏.md` 是游戏导演 / 制作人层体验总线，不记录实现进度。`14_0-12小时候选主循环细案设计.md` 承接 T0-T4 细案索引和承接规则，具体细案在 `0-12小时细案/` 中一案一文，不记录实现进度。后续详细进度由实现 Owner 回写所有受影响状态页和事实文档：全局体验 / 细案写 `agent_status/director.md`，策划 / 配置写 `agent_status/design.md` 与 `设计文档/config/26_正式配置设计与填充推进计划.md`，程序写 `agent_status/program.md` 与开发文档，美术 / UI 写 `agent_status/art.md` 与美术文档。

## 判断顺序

如果文档之间发生冲突，按以下顺序判断：

```text
当前 GDD 具体规则 > 13 全局体验总线与开放节奏 > 14 0-12 小时细案索引与目标细案文档 > 09 正式版宏观路线与长期节点 > 11 批次与需求承接矩阵 > 状态页 > 归档 MVP 文档
```

状态页用于记录当前事实和交接，不承载完整系统规则；具体规则仍回到 GDD、开发文档、美术文档或配置 README。

`11` 不维护实现状态；各职能详细进度以对应状态页和事实文档为准。如果 `09` 的长期节点判断与代码事实、验收报告或对应职能状态页冲突，应先核对证据，再更新 `09` 的节点门禁、职能入口或状态标记规则。

`设计文档/config/26_正式配置设计与填充推进计划.md` 是策划 / 配置职能计划，负责正式配置内容量、填充顺序和配置审计方法；程序实现、美术交付和游戏导演 / 制作人里程碑不写进 `26`。字段说明、README、审计结论和 JSON 修改前设计不等于配置源完成，不能直接标记为 `配置完成`。

## 精简维护规则

- `13` 只维护体验总线、模块宏观设计、时长切分、任务 Owner 工作流和包装方向；不记录实现流水，也不维护 0-12 小时旧派发表。
- `14` 只维护 0-12 小时 T0-T4 细案索引、推进规则和实现切片入口；具体细案一案一文，不记录实现进度。
- `09` 只维护开发宏观路线、长期节点、职能入口和防重复派发规则；不复述 `13` 的体验表或 `14` 的细案，也不记录实现切片完成状态。
- `PROJECT_STATUS.md` 只保留近期全局摘要、跨职能交接和阻塞；历史执行细项回到 `agent_status/*`、事实文档和 `DOCS_INDEX.md` 追溯。
- 已归档或兼容入口只保留迁移说明，不再新增 active 内容；如确需物理移动旧文档，先更新 `related` 链接并通过文档校验。
