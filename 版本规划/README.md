## 已移除的重复文档

`10_正式版核心纵切版本节点规划.md` 已删除，不再维护。

删除原因：旧 `10` 和 `09` 的阶段 / 优先级、`11` 的 GDD 批次关系高度重复，容易造成版本规划互相抢事实来源。后续需要判断宏观优先级、长期节点、节点门禁、职能入口和防重复派发规则时维护 `09`；需要判断某份 GDD 的批次、完成口径和需求承接时维护 `11`。

`13_跨职能工作项进度台账.md` 不再单独维护，也不再以 active 版本规划文档形式恢复。后续详细进度按职能回到状态页和事实文档：PM 写 `agent_status/pm.md`，策划 / 配置写 `agent_status/design.md` 与 `设计文档/26_正式配置设计与填充推进计划.md`，程序写 `agent_status/program.md` 与开发文档，美术 / UI 写 `agent_status/art.md` 与美术文档。

原 `12_版本规划需求文档承接审计.md` 已合并进 `11_纵切批次与需求文档承接矩阵.md`，不再单独维护。后续不再新增 active `12` 执行层文档；长期里程碑和通用派发规则统一维护在 `09`。

## 判断顺序

如果文档之间发生冲突，按以下顺序判断：

```text
当前 GDD 具体规则 > 09 正式版宏观路线与长期节点 > 11 批次与需求承接矩阵 > 状态页 > 归档 MVP 文档
```

状态页用于记录当前事实和交接，不承载完整系统规则；具体规则仍回到 GDD、开发文档、美术文档或配置 README。

`11` 不维护实现状态；各职能详细进度以对应状态页和事实文档为准。如果 `09` 的长期节点判断与代码事实、验收报告或对应职能状态页冲突，应先核对证据，再更新 `09` 的节点门禁、职能入口或状态标记规则。

`设计文档/26_正式配置设计与填充推进计划.md` 是策划 / 配置职能计划，负责正式配置内容量、填充顺序和配置审计方法；程序实现、美术交付和 PM 里程碑不写进 `26`。字段说明、README、审计结论和 JSON 修改前设计不等于配置源完成，不能直接标记为 `配置完成`。
