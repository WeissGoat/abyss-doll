# T0-01 开局人偶状态到首次下潜许可

> 归档说明：本文是 2026-06-14 的早期拆分稿，已被 `版本规划/0-12小时细案/T0-01_序章首次循环.md` 合并替代，不再作为实现 Owner 开工依据。

## 1. 细案状态

`T0-01` 细案完成，下一步由实现 Owner 读取本文后做证据审计和本切片具体落地方案。

## 2. 玩家结果

玩家在开局 0-30 分钟内看到三件事：

1. 人偶是脆弱但可行动的，不是普通角色面板。
2. 小镇和日程说明现在处于第一次下潜前的准备状态。
3. 点击下潜会经过真实许可检查；允许时进入第一层入口，不允许时给出可理解原因和下一步行动。

本切片完成后，玩家应该能回答：“为什么要下去、她现在能不能下去、不能下去时该先做什么。”

## 3. 前后关系

输入状态：

- 新开局或候选主循环第一天。
- 至少存在一个可出战人偶。
- 第一层入口已在宏观上解锁，但仍需要通过出战许可检查。
- 小镇主界面、日程显示和人偶状态显示可通过正常 UI 进入。

输出状态：

- 允许下潜时，创建或进入第一层入口上下文，交给 `T0-02` 处理首次下潜、基础战斗 / 事件和第一笔战利品。
- 不允许下潜时，留在小镇准备状态，并显示阻断原因与建议行动；不推进到第一层。

## 4. 玩家路径

1. 玩家进入小镇主界面。
2. 主界面显示当前日程、第一天状态、人偶摘要和深渊入口。
3. 人偶摘要显示 HP、SAN、维护 / 磨损提示和一句短反馈。
4. 深渊入口显示第一层入口、预计风险和是否允许下潜。
5. 玩家点击下潜。
6. 系统调用真实下潜许可检查。
7. 如果允许，进入第一层入口确认或第一层起点。
8. 如果不允许，显示明确阻断原因，并引导到维护、休整或选择可出战人偶。

## 5. 系统开放深度

| 系统 | 本切片开放深度 | 不开放内容 |
|---|---|---|
| 小镇 | 只开放主界面、深渊入口、维护 / 休整入口的轻提示。 | 完整商店、橱窗、黑市、典当、完整订单板。 |
| 人偶状态 | 显示 HP、SAN、维护 / 磨损、可出战状态和一句情绪反馈。 | 完整养成树、完整好感、完整房间互动。 |
| 日程 | 显示第 1 天和准备状态，用于解释当前处于第一次下潜前。 | 周期账单、月租、订单期限、复杂时间段消耗。 |
| 深渊入口 | 显示第一层入口和下潜许可。 | 多层选择、直达、安全区、路线网络。 |
| 叙事反馈 | 用一条短文案建立人偶脆弱感和下潜理由。 | 长剧情播片、完整事件队列、分支剧情。 |
| 验证 | 要求正常 UI 可达、真实许可检查、状态变化或阻断原因可验证。 | 不要求完整 3-5 轮回归。 |

## 6. 下潜许可规则

首次下潜默认应尽量允许，避免开局被维护规则卡死。阻断只用于明确不可行动状态。

允许条件：

- 存在被选中的可出战人偶。
- 人偶未处于 `无法行动`、`维修中`、`重伤待处理` 或等价硬阻断状态。
- HP 和 SAN 高于硬阻断阈值。
- 第一层入口在当前存档中可进入。

警告但不阻断：

- HP / SAN 偏低但未到硬阻断阈值。
- 存在轻度磨损、轻度维护需求或情绪不稳。
- 玩家尚未查看维护入口。

阻断原因必须可读：

| 阻断类型 | 玩家可见原因 | 建议行动 |
|---|---|---|
| 无可出战人偶 | 没有人偶可以下潜。 | 选择或修复一名人偶。 |
| HP 硬阻断 | 她的身体撑不住这次下潜。 | 先维护或休整。 |
| SAN 硬阻断 | 她无法保持稳定意识。 | 先休整。 |
| 入口未解锁 | 第一层入口尚未稳定。 | 完成前置引导或检查当前日程。 |
| 服务 / 配置异常 | 下潜许可无法确认。 | 记录为阻塞，不用假成功进入深渊。 |

## 7. UI / UX 表达

小镇主界面需要让玩家在一眼内看到三个焦点：

- 左侧或主焦点：当前人偶状态。
- 中央或主要行动：下潜入口。
- 次级信息：日程 / 第一天 / 准备状态。

下潜按钮不只显示“进入”，而要带许可反馈：

- 允许：显示可下潜状态和第一层入口。
- 警告：允许点击，但旁边显示风险提示。
- 阻断：按钮不可进入或点击后弹出原因；不能静默无反应。

所有文字保持短句，不在 UI 内解释系统教程。玩家应通过状态、按钮可用性和反馈文案理解规则。

## 8. 美术与氛围

本切片服务“日系二次元地底奇幻冒险 + 低信息密度”的第一印象。

- 人偶表现应偏脆弱、被修复过、仍愿意行动。
- 小镇入口应是奇幻地下小镇，不走黄铜、暖灯、蒸汽朋克或棕金机械主轴。
- 深渊入口要有未知和吸引力，但不压过人偶状态。
- UI 图标应优先表达 HP、SAN、维护、下潜许可和日程，不堆装饰。

## 9. 配置与数据意图

实现 Owner 需要审计现有配置源，确认是否已有以下意图。如果没有，应先补配置设计再落源：

- 初始人偶状态：HP、SAN、维护 / 磨损、可出战标记。
- 第一层入口：入口 ID、显示名、默认解锁状态、风险提示。
- 下潜许可阈值：HP 硬阻断、SAN 硬阻断、维修中 / 无法行动状态。
- 引导文案：允许、警告、阻断原因和建议行动。
- UI VisualID：人偶状态、SAN、HP、维护、第一层入口、许可状态。

配置源必须是 `配置表(JSON)`；运行时副本只通过同步生成。

## 10. 程序接入意图

实现 Owner 需要把 UI 行为接到真实领域服务或等价运行时规则，不允许 UI Controller 直接伪造许可结果。

关键接入点：

- 读取当前人偶状态和当前日程。
- 调用下潜许可检查。
- 根据许可结果更新 UI 状态。
- 允许时创建或进入第一层入口上下文。
- 阻断时保留小镇上下文，并展示原因。

如果当前工程已有服务，只补绑定和缺口；如果只有静态 UI 或 debug 入口，本切片按真实服务接入补强处理。

## 11. 实现切片边界

实现 Owner 可在本切片内处理：

- 小镇主界面到第一层入口的正常 UI 路径。
- 人偶状态摘要、日程摘要和下潜许可反馈。
- 第一层入口的最小上下文创建 / 进入。
- 下潜许可配置、文案、VisualID 和验证样例。

实现 Owner 不在本切片内处理：

- 第一场战斗、战利品拾取和背包取舍；这些属于 `T0-02`。
- 回城出售、金币结算、维护消费和日程推进闭环；这些属于 `T0-03`。
- 完整订单、账单、月租、黑市、房间记忆和完整养成树。

## 12. 验收样例

固定样例 A：允许首次下潜。

```text
给定：第 1 天，存在可出战人偶，HP / SAN 高于硬阻断阈值，第一层入口解锁
当：玩家从小镇主界面点击下潜
则：系统调用真实许可检查，返回允许，并进入第一层入口上下文
```

固定样例 B：HP 硬阻断。

```text
给定：当前人偶 HP 低于硬阻断阈值
当：玩家点击下潜
则：系统不进入深渊，显示身体撑不住的原因，并引导维护或休整
```

固定样例 C：警告但允许。

```text
给定：当前人偶存在轻度磨损或 SAN 偏低，但未达到硬阻断
当：玩家点击下潜
则：UI 显示风险提示，许可检查仍允许进入第一层入口
```

## 13. 完成口径

`T0-01` 只有同时满足以下条件，才算实现完成：

- 玩家能通过正常 UI 从小镇主界面看到人偶状态、日程和深渊入口。
- 点击下潜调用真实许可检查，不由 UI 直接伪造进入。
- 允许路径能进入第一层入口上下文，并为 `T0-02` 留下可读取状态。
- 至少一个阻断样例能显示明确原因和建议行动。
- 相关 UI / 美术表达符合日系二次元地底奇幻冒险主轴，不回到黄铜 / 暖灯 / 蒸汽朋克默认风格。
- 有 smoke、P0、人工流程、截图验收或 `validation_limited:*` 证据。
- 实现 Owner 已回写受影响状态页；外部主策 / 主程 / 主美或游戏导演验收结论已记录。
