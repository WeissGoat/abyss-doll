# 正式版核心纵切版本节点规划

> **更新时间：** 2026-05-24
> **定位：** 本文档是 `版本规划/09_正式版核心纵切开发路线.md` 的 PM 执行层。`09` 定义方向和阶段边界，本文定义版本节点、三线交付、依赖顺序和完成标准。本文不替代 GDD、开发文档或美术文档的事实来源。

---

## 1. 三线当前进度判断

| 职能线 | 当前规划重点 | 当前进度 | 主要缺口 |
|---|---|---|---|
| 美术 / UI | 从 MVP UI 骨架验收转向 Formal V1 正式结构；active `screen_layouts.json` 才是程序接入口。 | P0 `workshop_main`、`combat_hud`、`inventory_loot` 的 MVP Baseline 已运行时验收；Formal V1 已有 `combat_hud`、`workshop_main`、`inventory_loot`、`dungeon_map`、`settlement` 结构草案。 | 先确认 `combat_hud` Formal V1，并更新 active 规格；再决定新增 VisualID、Manifest 与素材缺口。 |
| 程序 / Unity | Alpha 1 核心边界收口，避免新功能继续堆进流程控制器和 UI Controller。 | `ItemUseService`、`InventoryInteractionService`、`InventoryPresentationController` 已完成第一阶段拆分；配置同步和基础测试链路可用。 | 继续拆 `GameFlowController`，集中 runtime fallback UI，强化 `ConfigValidator` 和启动健康检查。 |
| 策划 / 数值 | 保持正式版 Alpha 规则、GDD、数值模型和配置意图一致，优先纵向闭环。 | 已建立 `版本规划/11_设计文档Alpha覆盖矩阵.md`，明确 `GDD_00` 到 `GDD_12` 哪些进入 Alpha、哪些局部进入、哪些暂缓。 | A2 启动前需要冻结背包与物品生命周期、战斗可读性、典型怪物行为的验收口径。 |

结论：

```text
当前不是继续横向补内容。
先完成 Alpha 1 核心边界收口，再进入 Alpha 2 背包 + 战斗正式纵切。
```

## 2. 版本节点原则

1. **节点按门禁流转，不按自然日流转。** 没有通过完成标准的节点不能视为完成。
2. **每个节点都要有三线交付。** 即使某线只做确认或验收，也要明确责任。
3. **设计规则先于程序扩展。** 系统规则变更先写 GDD / 配置意图，再进入实现。
4. **active UI 规格先于程序 UI 接入。** Formal V1 文档确认后，必须更新 active `screen_layouts.json` 并通过校验。
5. **验证是节点出口，不是附加项。** 自动化测试、配置校验、UI 校验、运行时截图验收至少命中相关项。
6. **旧 MVP 文档只作历史参考。** 当前口径以 `09` 路线、GDD、开发文档、美术路线和本节点规划为准。

## 4. A1：核心边界收口

### 4.1 目标

降低后续纵切开发的冲突风险，让策划规则、程序边界和 UI 交付口径先稳定下来。

### 4.2 范围外

- 不新增大量物品、怪物、层级或剧情内容。
- 不追求所有 UI 最终品质。
- 不把 Formal V1 的所有界面一次性接入 Unity。

### 4.3 三线交付

| 职能线 | 交付 |
|---|---|
| 策划 / 数值 | 完成 GDD Alpha 覆盖矩阵；为 A2 预先冻结背包与物品生命周期、战斗反馈可读性、典型怪物行为的验收口径；明确哪些规则落 GDD、哪些落配置 README。 |
| 程序 / Unity | 继续收口 `GameFlowController`、runtime fallback UI、`ConfigValidator`、`tools/agent` 健康检查；保持核心闭环和现有 smoke test 可运行。 |
| 美术 / UI | 确认 `combat_hud` Formal V1，更新 active `screen_layouts.json` 并通过 `Validate-UIDesign.ps1`；暂不要求最终立绘、动画和 VFX。 |

### 4.4 完成标准

- `combat_hud` active 规格已更新并通过 UI 设计校验。
- 程序边界收口任务至少完成一轮可验证提交，且不扩大 UI Controller 规则职责。
- `版本规划/11_设计文档Alpha覆盖矩阵.md` 已建立，GDD 进入范围不再含混。
- A2 的策划规则入口、配置影响和验证需求已明确。
- 文档状态同步到 `PROJECT_STATUS.md` 和相关职能状态页。

### 4.5 A1 出口门禁

| 门禁 | 通过条件 |
|---|---|
| 设计门禁 | GDD 覆盖矩阵存在；A2 不会误拉好感、剧情、房间、势力等完整支线系统。 |
| 程序门禁 | 核心边界收口不破坏现有闭环；新逻辑不继续堆入 UI Controller 或流程总控。 |
| UI 门禁 | active UI 规格是程序接入口；Formal V1 草案不直接变成实现事实。 |
| 验证门禁 | smoke test、配置校验或运行时验收至少覆盖本轮改动相关路径。 |

## 5. A2：背包与战斗正式纵切

### 5.1 目标

让玩家能清楚理解背包和战斗中的每一次收益、损失、使用、丢弃、异常状态和资源变化。

### 5.2 子节点

| 子节点 | 主题 | 三线重点 |
|---|---|---|
| A2.1 | 背包与物品生命周期 | 策划冻结拾取、携带、使用、丢弃、撤离、战败、出售、制造消耗规则；程序覆盖背包交互和物品使用测试；美术补齐拾取、丢弃、收益、损失的 UI 状态。 |
| A2.2 | 战斗与怪物可读性 | 策划定义典型怪物行为、意图和异常状态；程序整理 `CombatSystem` / `MonsterActionAI` / 目标选择；美术完成 `combat_hud` Formal V1 接入与运行时验收。 |
| A2.3 | A2 验收与回归 | 策划按玩家路径走查，程序补自动化或 smoke test，美术跑截图验收并记录残留问题。 |

### 5.3 范围外

- 不铺大量怪物和装备。
- 不做完整商业化数值曲线。
- 不一次性完成所有战斗动画和 VFX。

### 5.4 完成标准

- 自动化测试覆盖关键物品生命周期和典型怪物行为。
- 战斗 HUD 能表达 HP、AP、护盾、SAN、敌人意图、异常状态和失败原因。
- 背包交互、战利品拾取、出售和制造消耗不绕过领域服务。
- A2 相关 GDD、开发文档、美术文档和状态页已同步。

### 5.5 A2 策划冻结项

进入 A2 前，策划侧必须冻结以下验收口径：

| 冻结项 | 最小口径 |
|---|---|
| 背包操作 | 拖拽、旋转、放置、取消、丢弃、拾取、整理在不同界面中规则一致。 |
| 生命周期 | 局前带入、本轮拾取、撤离带出、战败损失、出售、制造消耗各有明确流向。 |
| 战斗反馈 | 玩家能读懂伤害、护盾、AP、SAN、异常、诅咒、腐蚀和失败原因。 |
| 怪物行为 | 至少保留“普通攻击”“武器干涉”“塞包 / 占格”三类典型行为。 |
| 配置影响 | 物品标签、形状、旋转、怪物 Action、奖励表和 VisualID 需要被校验。 |

## 6. A3：深渊与局外成长纵切

### 6.1 目标

把“下潜 -> 回来变强 -> 继续深入”的正式版脊梁做稳，让玩家能理解当前目标、下一层入口、升级路径和资源缺口。

### 6.2 子节点

| 子节点 | 主题 | 三线重点 |
|---|---|---|
| A3.1 | 深渊层级、撤离与失败节奏 | 策划确认层级入口、继续深入、撤离、失败和节点职责；程序推进地图生成策略配置化；美术推进 `dungeon_map`、`layer_select`、`settlement` Formal V1。 |
| A3.2 | 局外成长与构筑方向 | 策划确认义体、底盘、配方和材料缺口；程序整理工坊制造、升级和资源扣除链路；美术推进 `workshop_main`、`prosthetic_panel` 和制造/升级反馈。 |
| A3.3 | A3 验收与回归 | 完成从指定层出发、撤离 / 战败、回工坊成长、再次下潜的玩家路径验收。 |

### 6.3 范围外

- 不做网状大地图完整版。
- 不铺大量义体、底盘和配方。
- 不做完整剧情、势力订单或好感内容量。

### 6.4 完成标准

- 玩家能在 UI 中看懂“去哪里、为什么去、回来后能变强什么”。
- 深渊层级入口、撤离、战败和结算流程稳定。
- 局外成长明确改变下一次下潜的战斗、空间或续航策略。

### 6.5 A3 策划冻结项

| 冻结项 | 最小口径 |
|---|---|
| 层级入口 | 新档从 1 层出发；已通层可从小镇选择；阶梯继续深入保留本轮账本。 |
| 搜打撤节奏 | 安全区、撤离、继续深入、战败结算各自职责清晰。 |
| 局外成长 | 底盘和义体至少各有一个可感知方向：空间、输出、防御或续航。 |
| 缺口展示 | 玩家能看懂升级还缺什么材料、金币或前置条件。 |

## 7. A4：经济压力与 Alpha 候选

### 7.1 目标

加入让玩家持续下深渊的长期动机，并把当前纵切提升为可验收 Alpha 候选。

### 7.2 三线交付

| 职能线 | 交付 |
|---|---|
| 策划 / 数值 | 建立至少一条中期经济压力链：出售收入、维护支出、制造消耗、租金或等价压力。 |
| 程序 / Unity | 强化配置校验、经济结算测试、Alpha 全流程 smoke test 和错误日志。 |
| 美术 / UI | 结算、出售、经营压力和资源缺口具备可读 UI 表达；运行时截图验收成为常规门禁。 |

### 7.2.1 子节点

| 子节点 | 主题 | 三线重点 |
|---|---|---|
| A4.1 | 中期经济压力 | 策划冻结经济压力链，程序接结算与校验，美术表达账单 / 缺口 / 收益。 |
| A4.2 | 轻量目标导向 | 可以是账单、订单、商店目标或下一层材料目标，不要求完整势力系统。 |
| A4.3 | Alpha 候选门禁 | 全流程 smoke、配置校验、运行时截图验收与人工走查收束。 |

### 7.3 完成标准

- 玩家开始面对“今天做什么”的局外决策，而不仅是重复打怪。
- Alpha 纵切可以从正式开局跑到第二层压力、回到局外成长，再进入更深层入口。
- 自动化验证和运行时美术验收可以作为 Alpha 候选门禁。

### 7.4 A4 策划冻结项

| 冻结项 | 最小口径 |
|---|---|
| 收入 | 战利品出售和材料保留形成清晰取舍。 |
| 支出 | 制造、维护、账单、治疗或等价压力至少一条进入可玩。 |
| 目标 | 玩家知道为什么今天要下深渊，而不是只为测试功能。 |
| 强度 | 经济压力不压死早期体验，但能推动中期选择。 |

## 8. 当前立即执行顺序

1. **A1 策划前置：** 使用 `版本规划/11_设计文档Alpha覆盖矩阵.md` 锁定 GDD 进入范围，避免支线系统抢跑。
2. **A1 美术前置：** 审查并确认 `combat_hud` Formal V1，更新 active UI 规格并校验。
3. **A1 程序前置：** 收口 `GameFlowController`、runtime fallback UI 和配置 / agent 健康检查。
4. **A2 启动准备：** 冻结背包生命周期、战斗可读性和典型怪物行为的验收口径。
5. **PM 同步：** 每完成一个前置项，更新 `agent_status/pm.md`、目标职能状态页和必要的事实来源文档。

## 10. 风险与控制

| 风险 | 控制方式 |
|---|---|
| UI 设计和程序接入口径分离 | 程序只认 active `screen_layouts.json`，Formal V1 确认后再 handoff。 |
| 程序重构影响已跑通闭环 | 每个边界收口任务必须保留自动化测试和核心闭环回归。 |
| 策划规则滞后于实现 | A2 开始前先输出规则卡、配置影响和验证需求。 |
| 内容铺量挤压系统收口 | A1 / A2 阶段只做典型内容，不做大量装备、怪物和层级。 |
| 生成物和脏文件混入提交 | 每次提交前按任务范围查看 `git status --short`，只暂存当前节点相关文件。 |
