# 0-12 小时候选主循环细案设计

> 本文由 0-12 小时细案 Owner 维护，是 0-12 小时按游戏时长推进的设计入口。后续 T0-T4 统一采用三层文档关系：`细案 -> Owner 具体设计 -> 开发方案`。细案首先是游戏设计稿：回答玩家在这个时长段经历什么、为什么继续、系统如何自然开放、剧情和情绪如何推进；Owner 具体设计再把其中一个可交付切片写成具体体验方案；开发方案最后根据 Owner 具体设计拆策划、美术 / UI、程序、配置、联调和验证工作。

## 1. 文档定位

0-12 小时细案不是验收点清单，也不是按功能模块纵切的执行表。它承接 `13` 第 12 节“按游戏时长的横向内容切分”，按玩家实际游玩时间设计体验推进。

细案 Owner 当前要先做游戏设计，而不是替实现 Owner 预先拆验收项。每一段细案应优先回答：

- 这一段玩家正在追什么目标。
- 玩家如何从上一段自然进入这一段。
- 深渊、战斗 / 背包、小镇、人偶、日程、叙事反馈、UI / 美术在这一段各自露出到什么程度。
- 玩家为什么愿意继续下一轮。
- 这一段结束时，留给下一段什么悬念、压力、资源状态或关系变化。

实现、配置字段、测试入口、截图验收和外部验收只放在“实现承接提示”里，作为后续 Owner 拆方案时的参考，不作为本文主体。

当前分工：

```text
游戏导演 / 制作人：定义全局体验、系统开放顺序和完成口径
0-12 小时细案 Owner：按游戏时长逐段写游戏设计，保证剧情、新手、系统开放和主循环融合
实现 Owner：先写 Owner 具体设计，再基于具体设计另拆开发方案，接配置 / UI / 美术 / 程序并自验
职能总监：主策 / 主程 / 主美 / 游戏导演做方向把关和最终验收
```

细案 Owner 负责锁定体验方向、玩家动机、叙事节奏、系统开放边界、关键状态变化和 UI / 美术表达方向。实现 Owner 先负责把细案中的一个玩家结果细化成 Owner 具体设计，再由开发方案把这个设计落成具体功能、配置、界面、素材和验证。

## 2. 三层文档关系

后续进入开发前必须先确认三层文档归属，避免把体验设计、具体方案和执行拆分写在同一份文档里。

| 层级 | 文档职责 | 写什么 | 不写什么 |
|---|---|---|---|
| 细案 | 按游戏时长写玩家体验段。 | 玩家旅程、剧情 / 情绪节奏、系统自然开放、UI / 美术方向、段末钩子。 | 不写职能任务表、配置字段清单、程序类名、验收脚本和开发排期。 |
| Owner 具体设计 | 把细案中的一个可交付玩家结果细化成具体体验方案。 | 镜头 / 场景顺序、玩家输入点、关键 UI 状态、对白节奏、状态变化、阻断反馈、转场节奏。 | 不写大段策划 / 美术 / 程序执行包，不替开发方案拆任务。 |
| 开发方案 | 根据 Owner 具体设计拆落地工作。 | 策划工作、美术 / UI 工作、程序工作、配置 / 文案、联调顺序、验证证据、状态回写。 | 不重新改体验方向，不推翻细案和 Owner 具体设计。 |

命名口径：

```text
T0-01_序章首次循环.md                 -> 细案
T0-01_序章首次循环开发总方案.md         -> 完整 T0 开发总入口
T0-01A_*                              -> A 段 Owner 具体设计 / 开发方案
T0-01B_*                              -> B 段 Owner 具体设计 / 开发方案
T0-01C_*                              -> C 段 Owner 具体设计 / 开发方案
T0-VAL-01_*                           -> A 段运行时验收记录
T0-VAL-02_*                           -> 完整 T0 验收文档，待 A/B/C 可跑后新增
```

`开发方案` 只在 Owner 具体设计被确认后新增；新增时再补 `related` 双向互链和状态页，不提前创建空文档。

## 3. 细案设计规则

1. 细案按 `13` 第 12 节的游戏时长段推进，而不是按模块、功能点或验收点拆。
2. 0-12 小时当前只保留五个主细案段：`T0`、`T1`、`T2`、`T3`、`T4`。
3. 一个时长段可以包含多个系统，但只对应一个主设计命题；实现 Owner 后续可在该命题下先拆 Owner 具体设计，再拆开发方案。
4. 每个细案主体应写游戏体验：玩家旅程、情绪曲线、剧情包装、系统自然露出、关键选择、阶段结尾。
5. 细案末尾可以保留很短的实现承接提示，但不能让验收项、字段、测试、状态回写压过设计主体。
6. 未完成设计细案的时长段只作为设计队列，不作为实现 Owner 正式开工依据。
7. 如果实现反馈导致细案修订，必须先保证时长段体验连续，再调整具体实现边界。

## 5. 单篇细案建议结构

每篇时长段细案优先使用以下结构：

1. **时长定位**：这一段在 0-12 小时里承担什么体验任务。
2. **玩家旅程**：玩家从哪里来、经历哪些连续片段、以什么状态离开。
3. **核心设计命题**：这一段最重要的玩家问题是什么。
4. **系统自然开放**：深渊、战斗 / 背包、小镇、人偶、日程、叙事、UI / 美术分别如何露出。
5. **关键选择与压力**：玩家在哪些地方开始做真正选择，而不是点下一步。
6. **剧情与情绪节奏**：这一段如何包装世界、人偶和深渊。
7. **留给下一段的钩子**：资源、状态、目标、关系或悬念如何把玩家推向下一段。
8. **实现承接提示**：只记录实现 Owner 需要注意的边界、已有系统可复用点和不可改变的设计意图。

## 6. 实现 Owner 承接原则

实现 Owner 承接的是设计意图，不是逐条验收任务。Owner 具体设计先回答“这一段具体怎么玩”，开发方案再回答“各职能怎么把它做出来”。承接时仍按完整纵切流程工作：

```text
证据审计 -> 阅读目标细案 -> Owner 具体设计 -> 开发方案 -> 配置源落地 -> UI/UX 与美术接入 -> 程序接入 -> Owner 自验 -> 职能总监验收 -> 状态回写
```

实现 Owner 可以拆：

- Owner 具体设计。
- 开发方案。
- 配置字段、服务、类、Prefab、VisualID、文案 Key、测试入口和接入顺序。
- 已有实现覆盖点、真实缺口和工程现实下的局部方案。

实现 Owner 不可以自行改变：

- 目标时长段的核心玩家体验。
- T0-T4 的系统开放节奏。
- 剧情 / 新手 /系统融合的上层设计意图。
- 是否需要真实服务、状态变化和外部验收的完成口径。
- 全局美术 / UI 主轴。

每个实现切片开工前至少读取：

- 本文的细案队列和承接规则。
- 目标时长段设计细案。
- `版本规划/13_正式版全局体验总线与开放节奏.md` 中对应模块宏观设计行。
- 当前任务涉及的 GDD、开发文档、美术规格、配置 README 和职能状态页。

## 7. 下一步细案

`T1 30 分钟-2 小时：第一层搜打撤成形` 已有设计稿 V1。它把第一层编排为玩家学习路线、战斗意图、背包取舍、撤离 / 深入和第二层露出的完整体验段，而不是拆成节点网络、Boss、安全区等验收点清单。

下一轮细案 Owner 优先完善 `T2 2-5 小时：小镇压力与下潜目标成形`。

该细案应承接 `T1 第一层搜打撤成形` 留下的第一层路线经验、战利品差异、人偶状态变化、撤离 / 深入判断和第二层好奇心。设计重点不是先列“出售、账单、维护、订单、传闻”的验收点，而是写清楚小镇如何从回城菜单逐渐变成下一轮下潜理由的生成器：

- 出售不只是换钱，而是让玩家理解物品去向和收益差异。
- 账单 / 维护不只是扣资源，而是把深渊结果转成人偶照看压力。
- 传闻 / 基础订单不只是任务列表，而是把下一轮路线目标说清楚。
- 第二层不只是新层级，而是被小镇目标和第一层经验共同推开的新风险。

本轮新增 `T1 第一层搜打撤成形` 前已检索 `版本规划/` active 路径，未发现 `T1-01 / T1-02 / T1-03` 的实体旧细案文档；这些名称只作为废弃拆分口径出现在状态说明、mission 记录或已归档 T0 历史稿中，因此本轮不产生新的物理归档动作。
