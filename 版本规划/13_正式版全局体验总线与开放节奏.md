# 正式版全局体验总线与全系统宏观大纲

> **定位：** 本文是游戏导演 / 制作人层的 active 顶层文档，回答“整个游戏最终由哪些系统组成、每个系统在玩家体验里承担什么、从开局到长线循环如何串起来、系统为什么在此时开放、深渊如何包装、一个任务应该由谁纵切负责”。`14` 承接 0-12 小时 T0-T4 逐个完善的细案设计；`09` 继续负责开发宏观路线、长期节点和防重复派发；`11` 继续负责 GDD / 需求文档承接门禁。

---

## 1. 顶层判断

当前项目不再把 PM 作为独立活跃角色。旧 PM 的排期、阶段判断和交接职责并入游戏导演 / 制作人角色，但优先级发生变化：先判断玩家体验是否成立，再决定制作推进顺序。

项目后续采用任务 Owner 纵切负责制。一个任务不再默认拆成策划、程序、美术、UI 多个 agent 互相交接，而是由一个任务 Owner agent 对完整玩家结果负责：先做证据审计和策划详细设计，再落配置源、做 UI/UX 与美术 / 素材接入、接真实程序功能，最后完成 Owner 自验和状态回写。职能 agent 保留为主策、主程、主美 / UI 视觉总监，主要负责总体设计、规范和外部验收；Owner 自验不替代职能总监验收。

后续开发节点按玩家游玩时长横向切分：每个时长段都包含深渊、战斗 / 背包、小镇经济、人偶状态 / 养成、日程、叙事反馈、UI / 美术和验证门禁，只是开放深度不同。不能把某个模块整体推迟到中后期，也不能把横向切分理解成按模块纵切。

当前宏观设计结论：现有 GDD 与规则卡中的游戏系统全部保留，不在本轮砍掉任何一个正式系统。后续只区分：

| 判断 | 含义 |
|---|---|
| 核心主线 | 必须进入完整游戏体验，否则游戏主循环不成立。 |
| 阶段开放 | 系统保留，但在玩家产生对应问题后再开放，不抢早期认知。 |
| 表现 / 记忆层 | 不强行变成数值压力，但负责让玩家经历留下痕迹。 |
| 制作门禁 | 不属于玩家玩法系统，但必须作为开发完成口径和质量门禁。 |
| 砍线 / 压缩 | 当前只针对旧 PM 路由、debug-only 伪完成、重复职能分包等制作冗余；不针对现有正式 GDD 系统。 |

## 2. 全游戏核心承诺

Project P3 的完整体验不是“刷副本 + 回城菜单”，而是：

```text
在有限时间里，把一个脆弱人偶一次次送进深渊。
玩家从深渊带回战利品、素材、污染、伤痛和记忆；
在小镇中把这些东西转化成金币、维护、构筑、订单、关系和房间痕迹；
再用新的压力和新的理由决定下一次下潜。
```

完整游戏由六条主线共同驱动：

| 主线 | 体验问题 | 系统承载 |
|---|---|---|
| 深渊线 | 我这次要走哪条路，什么时候该撤？ | 深渊地图、节点网络、层级入口、雾、直达、阶梯、安全区、路线侵蚀。 |
| 战斗 / 背包线 | 我能不能打赢，值不值得拿？ | 背包网格、物品生命周期、战斗回合、怪物意图、战利品、订单物占格。 |
| 小镇经济线 | 我为什么必须再下去？ | 出售、橱窗、传闻、顾客、日结、月租、债务、典当、黑市。 |
| 人偶成长线 | 这次冒险让她变成了什么样？ | HP / SAN、磨损、侵蚀、维护、底盘、义体、特质、Bond、交互。 |
| 社会目标线 | 谁在利用我的冒险，我要站在哪边？ | 势力、订单、声望、信任、黑市背叛、解锁、商店 / 图纸。 |
| 叙事记忆线 | 世界和房间如何记住我的选择？ | 剧本事件队列、对话、旗标、房间、纪念物、日记、窗外状态、长期记忆。 |

这些主线共享同一条循环：

```text
准备 -> 下潜 -> 战斗 / 事件 -> 战利品取舍 -> 撤离 / 深入
-> 回城结算 -> 出售 / 订单 / 维护 / 成长 / 交互 / 记忆沉淀
-> 新目标 -> 再次下潜
```

## 3. 全游戏阶段大纲

8-12 小时不再作为宏观设计终点，只作为“候选版主循环稳定”的阶段门槛。完整游戏按以下体验阶段组织：

| 阶段 | 玩家核心问题 | 体验目标 | 系统开放重点 | 完成信号 |
|---|---|---|---|---|
| 序章：捡回坏掉的人偶 | 我为什么要下去？她为什么脆弱？ | 建立人偶状态、小镇压力和深渊收益的第一印象。 | 小镇主界面、下潜入口、基础背包、第一层、基础出售 / 维护。 | 玩家完成一次下潜、出售、维护，并理解状态会影响再次下潜。 |
| 第一幕：学会搜打撤 | 我该带什么、捡什么、什么时候撤？ | 玩家把深渊理解成风险空间，而不是线性清图。 | 节点网络、战斗、怪物意图、战利品、阶梯、安全区、撤离 / 深入。 | 玩家主动放弃、撤离、绕路或深入，并能解释原因。 |
| 第二幕：小镇变成压力机器 | 我为什么必须再下去？ | 回城不只是结算，而是产生账单、订单、维护和材料目标。 | 出售渠道、传闻、顾客、月租预告、基础订单、维护消耗、材料缺口。 | 玩家能带着订单、账单、材料或维护目标规划下一轮。 |
| 第三幕：构筑与路线互相绑定 | 我这局养成方向是什么？ | 底盘、义体、特质和背包形状开始改变路线选择。 | 底盘、义体、制造、装备、特质、效果、下潜许可、第二 / 三层直达。 | 玩家为了某个构筑方向主动选择层级、路线和材料。 |
| 第四幕：深渊开始反过来污染世界 | 为什么路线和小镇开始回应我？ | 第三层路线侵蚀、污染物、订单冲突和 SAN 压力带来长期后果。 | 第三层主题、污染物品、路线侵蚀、多势力订单冲突、房间第一批记忆。 | 玩家能预判某些路线会留下长期代价或机会。 |
| 第五幕：候选版主循环稳定 | 下一轮我为什么冒险？ | 形成可重复、可解释、可验证的 8-12 小时主循环。 | 前三层、经济压力、人偶成长、维护、订单 / 传闻、房间 / 反馈最小闭环。 | 玩家可以自然循环 3-5 轮，并在不同轮次为了不同目标下潜。 |
| 第六幕：正式版中盘展开 | 我要和谁交易、背叛或结盟？ | 势力、黑市、月租、房间记忆和剧情事件从辅助信息变成长期路线。 | 声望 / 信任阶梯、黑市背叛、月租 / 典当、剧本事件队列、房间纪念物。 | 玩家开始在金币、声望、黑市、Bond 和房间记忆之间做不可完全兼得的选择。 |
| 第七幕：高层深渊与终局压力 | 我愿意为了结局付出什么？ | 高层内容把经济、构筑、关系、污染和剧情旗标压到同一张终局账单上。 | 第四 / 五层、组合压力、订单链、剧情终局、房间结局前夜、长期债务或终局裁决。 | 玩家进入结局分歧或挑战长尾时，能看见此前选择如何结算。 |

## 4. 全系统宏观归位

所有 active GDD 系统都进入完整游戏大纲。当前不砍系统，只调整开放顺序和阶段权重。

| 系统 | 宏观身份 | 玩家问题 | 首次开放 | 完整游戏职责 |
|---|---|---|---|---|
| `GDD_01` 背包战斗与局内网格 | 局内核心玩法 | 我如何用有限空间活下来？ | 第一幕 | 通过网格、AP、怪物意图、格子干涉和战利品取舍制造每轮局内决策。 |
| `GDD_02` 深渊地图与搜打撤 | 风险空间与路线结构 | 我该走哪条路，何时撤？ | 第一幕 | 承担层级推进、节点网络、路线主题、雾、直达、阶梯、安全区、路线侵蚀。 |
| `GDD_03` 人偶实体与好感双轨 | 情感对象与状态核心 | 她现在还能继续吗？她怎么看我？ | 序章 | 承担 HP / SAN / Bond、情绪、奇迹、崩溃、反馈差异和长期关系基础。 |
| `GDD_04` 小镇经济与物价波浪 | 局外压力机器 | 我为什么必须再下去赚钱？ | 序章 / 第二幕 | 承担出售、传闻、顾客、橱窗、违禁品、月租、欠债、典当和经济复盘。 |
| `GDD_05` 剧本调度引擎 | 系统事件编排层 | 世界为什么在回应我？ | 第四幕轻露出，第六幕展开 | 承担剧情触发、事件队列、对话树、系统指令、旗标、跳过 / 重入和终局事件。 |
| `GDD_06` 物品系统与生命周期 | 所有资源的实体基础 | 这个东西从哪来，要去哪？ | 序章 | 承担来源、容器、旋转、损坏、污染、出售、制造、展示、赠礼、订单绑定和战败损失。 |
| `GDD_07` 时间日程系统 | 单向压力时钟 | 今天下去，还是停下来？ | 第二幕 | 承担 Day / Week / Month、订单期限、传闻有效期、月租周期、休息日和结局收束。 |
| `GDD_08` 人偶养成 | 构筑与回城成长 | 我这局养成方向是什么？ | 第二 / 三幕 | 承担底盘、义体、制造、维护、换装、材料缺口、下潜许可和长期构筑。 |
| `GDD_09` 标签与特质 | 规则改写层 | 为什么同一件事这次不一样？ | 第三幕 | 承担动态标签、特质触发、互斥、叠加、消除转化、订单查询和构筑差异。 |
| `GDD_10` 势力声望与订单 | 社会目标与长期选择 | 我该替谁冒险，能不能背叛？ | 第二幕轻露出，第六幕展开 | 承担订单池、声望 / 信任、委托物占格、奖励解锁、黑市背叛和势力怀疑。 |
| `GDD_11` 人偶房间与视觉叙事 | 长期记忆容器 | 这段经历留下了什么？ | 第四幕轻露出，第六幕展开 | 承担房间布局、纪念物、展示品、日记、窗外状态、待机动作和结局前夜氛围。 |
| `GDD_12` 人偶交互管理器 | 情感动作入口 | 我怎样安抚、陪伴或修复她？ | 序章轻触发，第三幕展开 | 承担触摸、对话、赠礼、保养、特殊交互、每日上限、偏好和反馈。 |
| UI / 美术系统 | 规则可读性与情绪呈现 | 我看得懂现在发生什么吗？ | 全程 | 承担 HUD、地图、小镇、工坊、结算、房间、图标、角色 / 怪物表现和运行时美术验收。 |
| 配置 / Validator / 自动验收 | 制作门禁 | 这个系统真的可持续扩展吗？ | 开发全程 | 不作为玩家玩法系统，但作为配置正确性、固定 seed、P0 报告、ArtAcceptance 和完成判定门禁。 |

## 5. 系统开放原则

系统不按功能清单一次性展开，而在玩家产生问题时开放。完整游戏所有系统都保留，但必须让开放时机服务体验理解。

| 玩家问题 | 对应开放 | 完整版后续扩展 |
|---|---|---|
| 我怎么赚钱？ | 出售、基础价格、第一批可卖战利品。 | 橱窗、顾客、传闻、黑市、订单收益、日结复盘。 |
| 我为什么不能再下去？ | HP / SAN、维护、磨损、下潜许可原因。 | 侵蚀、特质、底盘限制、时间代价、休息日 / 深度疗愈。 |
| 我该带什么回来？ | 材料目标、订单目标、回城用途提示。 | 多势力订单、委托物占格、Boss 核心互斥、黑市背叛。 |
| 我该走哪条路？ | 节点网络、雾、节点类型、阶梯 / 撤离。 | 路线侵蚀、路线主题、订单目标路线、高层组合压力。 |
| 我该怎样战斗？ | 怪物意图、AP、背包格子、物品使用。 | 构筑流派、格子干涉、特质改写、Boss 阶段和高级反制。 |
| 我这局养成方向是什么？ | 底盘、义体、维护反馈和人偶状态变化。 | 特质组合、心智天赋、换装、稀有义体、构筑路线。 |
| 小镇为什么不是菜单？ | 账单预告、维护支出、传闻目标。 | 月租、欠债、典当、黑市渠道、顾客预算、经营日报。 |
| 我该相信谁？ | 基础订单和势力来源。 | 声望阶梯、信任、背叛、怀疑、势力商店、专属图纸。 |
| 这些经历留下了什么？ | 人偶反馈、房间第一批纪念物。 | 日记、展示品、窗外状态、长期剧情事件、结局前夜。 |
| 世界为什么在回应我？ | 第三层路线侵蚀和订单冲突。 | 剧本事件队列、债务事件、Bond 事件、深渊 lore 和终局旗标。 |

## 6. 全游戏模块宏观设计矩阵

本节是游戏导演 / 制作人层的“模块总谱”。它不替代 GDD、程序开发文档或美术规格，而是先回答每个模块在完整体验里负责制造什么感受、承担什么压力、和哪些模块互相咬合，以及后续该由谁细化和验收。

后续 0-12 小时细案和实现切片在承接时，必须同时标注服务的游戏时长段、对应细案切片 ID，以及本节中的模块行。职能总监依据本节做方向验收：主策看规则和节奏是否服务体验，主程看实现边界和验证门禁是否成立，主美 / UI 视觉总监看视觉语言和界面表达是否把玩家问题说清楚。

| 模块 | 宏观体验职责 | 视觉 / 包装关键词 | 玩法压力 | 与其他模块的连接 | 主负责设计 | 细化 / 验收 | 实现接入方式 |
|---|---|---|---|---|---|---|---|
| 全局美术 / UI 体验语言 | 让玩家始终处在“日系二次元地底奇幻冒险”的世界里，并能读懂当前状态。 | 日系二次元、地底奇幻、童话式好奇与危险并存、明亮但不轻飘的色彩、低噪声 UI、可读图标。机械、工坊和旧工具只作为局部系统语义；黄铜 / 铜件 / 暖灯 / 蒸汽朋克不作为全局主轴。 | 信息过载、按钮菜单感、规则不可读、棕金机械风压过奇幻二次元主轴。 | 所有模块共享 UI 皮肤、图标、背景、角色反馈和 ArtAcceptance。 | 游戏导演定义世界气质和优先级。 | 主美 / UI 视觉总监细化视觉系统并验收；主程验收 UGUI / VisualID 接入。 | 每个实现切片必须说明涉及哪些界面、VisualID、截图验收或 `validation_limited:*`，并按美术风格基准验收是否偏离奇幻二次元主轴。 |
| 深渊层级 | 承担每轮下潜的风险空间和长期推进感，让“走哪条路、何时撤、是否深入”成为核心问题。 | 每层生态差异明显，但都保留巨大地底空间、可推进路线、节点长在地貌上。 | 路线风险、层级解锁、撤离失败、污染和 SAN 压力。 | 战斗 / 背包提供局内代价；小镇 / 订单提供下潜理由；人偶状态决定可持续性。 | 游戏导演定义层级功能和完整包装；主策细化规则。 | 主策验收路线 / 节奏；主美验收层级视觉；主程验收 seed、节点、撤离和层级状态。 | 实现切片引用目标层级、玩家时长段和层级完成信号，不以“做一张地图”命名。 |
| 小镇 | 把深渊结果转换成压力、目标和下一轮理由，而不是菜单集合。 | 奇幻地下小镇、旧木、布料、账本、橱窗、顾客、传闻板、黑市暗门；工坊道具只在维护 / 义体语义中局部出现。 | 金币缺口、账单预告、顾客偏好、订单期限、黑市诱惑。 | 连接战利品、物品生命周期、人偶维护、日程、势力和剧情事件。 | 游戏导演定义小镇作为压力转换器的节奏。 | 主策细化经济规则；主美验收场景与 UI；主程验收服务调用和状态回写。 | 实现切片必须证明“回城后产生下一轮目标”，不能只做静态面板。 |
| 人偶 | 同时承载冒险代价、构筑方向和情感责任。 | 脆弱、修复痕迹、义体工艺、表情差异、房间痕迹、纪念物。 | HP / SAN、磨损、侵蚀、维护成本、Bond、构筑取舍。 | 深渊消耗人偶，小镇修复人偶，房间记录人偶，战斗 / 背包由人偶状态改写。 | 游戏导演定义人偶在循环中的情感与系统位置。 | 主策验收状态 / 成长规则；主美验收角色与房间反馈；主程验收领域服务。 | 实现切片必须让玩家看到状态变化或可操作结果，不能只写数值说明。 |
| 战斗 / 背包 | 把局内选择压缩到有限格子、有限 AP 和可读敌意图中。 | 网格、物品轮廓、怪物意图、战利品、伤害反馈、背包取舍。 | 背包空间、HP / SAN 消耗、AP、敌方意图、战利品取舍。 | 接深渊节点、物品生命周期、战利品出售、订单物占格和构筑特质。 | 游戏导演定义战斗在主循环中的手感目标。 | 主策验收规则可读性；主程验收服务 / 测试；主美验收 HUD 和反馈。 | 实现切片以“玩家能读懂并完成一次选择”为结果，不以“补一个战斗功能”为结果。 |
| 经济 / 订单 / 势力 | 给持续下潜提供社会目标和长期压力。 | 账本、订单章、势力徽记、传闻纸条、黑市暗色入口。 | 月租、债务、期限、声望、信任、背叛、违禁收益。 | 小镇负责入口，深渊提供目标，背包承担占格，人偶 / 房间记录代价。 | 游戏导演定义何时从轻目标转成长期路线。 | 主策验收经济循环和数值压力；主美验收徽记 / 信息层级；主程验收机器可判定。 | 实现切片必须保证订单 / 传闻能指向可兑现目标，并有成功 / 失败判定。 |

| 配置 / Validator / 自动验收 | 作为制作门禁，保证系统能扩展、可复现、可回归。 | 对玩家不可见；在工具层体现为报告、固定 seed、截图和状态页证据。 | 数据漂移、引用断裂、假完成、截图通过但玩家不可达。 | 所有模块完成口径都要接入验证证据。 | 游戏导演定义完成口径和证据要求。 | 主程维护验证工具；主策 / 主美提供规则和验收样例。 | 实现切片必须列出 smoke、P0、配置校验、ArtAcceptance 或受限验证原因。 |

### 6.1 深渊层级美术与玩法总谱

深渊层级的视觉差异不是单纯换皮。每一层都要让玩家预感到新的风险类型，同时仍服务“路线选择 -> 战斗 / 事件 -> 战利品取舍 -> 撤离 / 深入”的主循环。

| 层级 | 宏观功能 | 视觉方向 | 节奏关键词 | 首要连接 |
|---|---|---|---|---|
| 第一层 | 教会搜打撤和第一次收益闭环。 | 入口废墟、失落矿道、浅层遗迹、发光洞穴植物、少量旧工具和浅层腐蚀。 | 可理解、可回头、风险低但代价真实。 | 基础战斗、战利品、出售、维护。 |
| 第二层 | 放大背包压力，并让直达 / 阶梯成为策略。 | 孢子工坊、潮湿机械遗迹、发光菌类、锈蚀管线。 | 分叉、取舍、补给压力。 | 直达条件、订单占格、材料目标、义体制造。 |
| 第三层 | 让路线开始留下后果。 | 地下森林、菌丝神谕、被生态侵蚀的道路网络。 | 长期代价、污染、订单冲突、SAN 压力。 | 路线侵蚀、污染物、多势力订单、房间记忆。 |
| 第四层 | 组合污染、订单链、黑市诱惑和背叛。 | 菌冠巢、培养舱、净化池、黑市捷径。 | 高收益诱惑、不可完全兼得、路线替换。 | 黑市、信任 / 声望、典当 / 债务、剧情旗标。 |
| 第五层 | 把构筑、关系、经济和剧情压到终局账单。 | 深渊核心、旧王遗构、人偶记忆回声、终局门。 | 不可逆选择、最终检验、结局分歧。 | 终局订单、房间结局前夜、最终构筑、Bond / SAN 裁决。 |

### 6.2 模块串联规则

1. 深渊只负责制造风险和收益，不单独解释玩家为什么要下潜；下潜理由必须来自小镇、订单、人偶维护、构筑材料或剧情旗标。
2. 小镇只负责把结果转成下一轮目标，不应成为独立经营小游戏；所有经济压力都要能回到“下一次下潜怎么规划”。
3. 人偶不是单独养成菜单；每次成长、维护、交互或房间记忆都要能回看某次深渊 / 小镇 / 日程选择。
4. 战斗 / 背包不只是局内胜负；它要决定哪些物品能带回、哪些订单会失败、哪些状态会压到下一轮。
5. 叙事不抢主循环控制权；剧情事件只在系统状态已经产生变化时成为回声、解释或裁决。
6. UI / 美术不是最后贴皮；每个玩家结果在被称为完成前，都要有足够的运行时表达让玩家理解当前问题、可选行动和结果。
7. Validator 和状态回写是制作门禁；没有证据的“设计完成”“截图完成”不能替代玩家正常路径可达。

## 7. 深渊包装推进口径

深渊不是单纯关卡列表，而是玩家每轮决策的风险空间。层级美术、玩法节奏和系统连接以第 6.1 节 `深渊层级美术与玩法总谱` 为准，本节只保留制作推进口径，避免重复维护两张层级表。

前三层负责让核心循环成立：第一层教会基础搜打撤，第二层放大背包压力和直达选择，第三层引入路线侵蚀和订单冲突。第四 / 五层负责把污染、订单链、黑市、构筑、关系、经济和剧情组合成高压长期选择。

第四 / 五层当前不抢正式版核心纵切实现优先级，但不再从宏观设计中排除。它们是完整游戏大纲的一部分，等前三层和局外主循环稳定后进入内容包和任务 Owner 拆分。

## 8. 小镇完整包装方向

小镇不是菜单集合，而是玩家每次深渊结果的压力转换器。

| 子系统 | 早期职责 | 中后期职责 | 设计边界 |
|---|---|---|---|
| 出售 / 倾倒箱 | 让玩家第一次赚到钱。 | 成为低决策、低收益的兜底出口。 | 不替代订单、橱窗和黑市的策略价值。 |
| 橱窗 / 顾客 | 让玩家理解“卖给谁”会改变收益。 | 支撑高价值物、套装、顾客预算和特殊偏好。 | 不做讨价还价小游戏。 |
| 传闻 / 周报 | 让玩家知道下一轮该捡什么。 | 影响价格、订单权重、黑市窗口和路线目标。 | 传闻必须指向可兑现目标。 |
| 日结 / 月租 | 把一次冒险转成长期账本。 | 形成账单倒排、欠债、典当和债务事件。 | 压力要可预告、可补救、可复盘。 |
| 订单 / 势力 | 给下潜目标和社会选择。 | 形成声望、信任、背叛、商店 / 图纸解锁。 | 订单必须能被机器判断，不能只写描述。 |
| 黑市 | 提供短期高收益诱惑。 | 承担背叛、违禁、怀疑和高风险路线。 | 黑市不是普通高倍率出售，必须有长期代价。 |

## 9. 人偶完整包装方向

人偶不是数值容器，而是冒险代价、构筑方向和情感记忆的共同承载者。

| 子系统 | 早期职责 | 中后期职责 | 完整游戏职责 |
|---|---|---|---|
| HP / SAN / 磨损 / 侵蚀 | 解释为什么不能无限下潜。 | 与维护、路线、污染物和房间状态联动。 | 成为深渊可持续性的主计时器之一。 |
| 维护 / 保养 | 让玩家第一次把钱和材料花回人偶身上。 | 形成恢复、净化、磨损控制和许可检查。 | 在经济压力和情感责任之间制造取舍。 |
| 底盘 / 义体 | 给玩家“回来变强”的直接反馈。 | 改变背包空间、战斗能力、续航和路线选择。 | 支撑构筑流派和高层路线适配。 |
| 标签 / 特质 | 让经历改变规则。 | 影响订单、战斗、交互、经济和房间反馈。 | 形成多轮游玩的个体差异。 |
| Bond / 交互 | 让玩家在压力外有照顾对象。 | 解锁反馈、对话、奇迹、崩溃与安抚。 | 支撑情感结局和房间长期记忆。 |
| 房间 / 纪念物 | 早期只做轻量反馈。 | 记录 Boss、战败、赠礼、债务、路线和 Bond 事件。 | 成为玩家经历的视觉日记，不替代核心战力系统。 |

## 10. 叙事与长期记忆方向

剧情不以章节播放器压过主循环，而是作为系统状态的回声。

| 叙事入口 | 触发来源 | 玩家作用 | 完整游戏职责 |
|---|---|---|---|
| 主线事件 | 层级首达、Boss、月租节点、关键旗标。 | 告诉玩家世界目标和终局压力。 | 串起正式主线和结局分歧。 |
| Bond 事件 | 好感、SAN、崩溃、维护、赠礼。 | 让人偶关系不只是数值。 | 支撑情感线和奇迹 / 崩溃裁决。 |
| 债务事件 | 月租缺口、欠债、典当、重违约。 | 把经济失败转成剧情压力。 | 支撑小镇压迫感和结局风险。 |
| 深渊 lore | 特殊物品、事件节点、房间展示。 | 让深渊不是随机素材池。 | 支撑世界观、势力动机和终局解释。 |
| 房间日记 | 撤离、战败、赠礼、订单、Boss、背叛。 | 让玩家看见选择留下痕迹。 | 成为长期记忆和结局前夜回看入口。 |

## 11. 候选版 8-12 小时口径

8-12 小时是完整游戏的候选版门槛，不是完整游戏范围上限。它的任务是证明主循环能稳定运转，并给后续全系统展开留下入口。

候选版内容不再单独维护一套“五幕蓝图”表，避免与第 12 节的按游戏时长横向切分重复。后续判断 0-12 小时体验时，以第 12 节 `0-30 分钟` 到 `8-12 小时` 的时长段为体验坐标，以 `版本规划/14_0-12小时候选主循环细案设计.md` 的逐个细案为实现坐标。

## 12. 按游戏时长的横向内容切分

横向切分以玩家实际游玩时长为主轴。每一段都不是“只做某个模块”，而是在同一段里让深渊、战斗 / 背包、小镇、人偶、日程、叙事反馈、UI / 美术和验证同时存在；区别只在于从基础可理解逐步开放到策略压力、长期记忆和终局结算。

| 时长段 | 阶段定位 | 玩家核心问题 | 全系统开放深度 | 完成信号 |
|---|---|---|---|---|
| 0-30 分钟 | 捡回坏掉的人偶，完成第一次完整循环。 | 我为什么要下去？她为什么脆弱？我怎么赚第一笔钱？ | 小镇、日程、人偶状态、下潜入口、第一层入口、基础战斗 / 背包、战利品、出售、维护和轻量反馈全部出现；只开放最少规则。 | 玩家完成一次下潜、回城、出售、维护或休整，并理解人偶状态会影响下一次下潜。 |
| 30 分钟-2 小时 | 学会搜打撤，而不是清图。 | 我该走哪条路、捡什么、什么时候撤？ | 第一层完整展开，第二层入口露出；节点网络、战斗意图、背包取舍、阶梯 / 安全区、撤离 / 战败结算、基础日程推进和人偶状态反馈形成手感。 | 玩家主动放弃、绕路、撤离或深入，并能把选择原因说清楚。 |
| 2-5 小时 | 小镇开始给下一轮下潜理由。 | 我为什么必须再下去？这次要带回什么？ | 第二层、直达条件、基础订单 / 传闻、出售渠道、账单预告、维护消耗、基础成长、材料缺口和轻量势力来源同时开放。 | 玩家能为了订单、材料、维护、账单或成长目标规划下一轮路线。 |
| 5-8 小时 | 构筑、路线和后果开始绑定。 | 我这局人偶要往什么方向养？哪些路线会留下代价？ | 第三层、路线侵蚀、污染物、订单冲突、底盘 / 义体 / 特质选择、人偶交互反馈、房间第一批记忆和周 / 月节奏轻压同时加深。 | 玩家开始形成构筑倾向和风险偏好，并能预判某些路线的长期代价或机会。 |
| 8-12 小时 | 候选版主循环稳定。 | 下一轮我为什么冒险？不同轮次为什么不一样？ | 前三层、经济压力、人偶成长、维护、订单 / 传闻、基础势力、房间 / 反馈、日程推进和 FormalV2 核心 UI 全部形成最小闭环。 | 玩家可以自然循环 3-5 轮，并在不同轮次为了不同目标下潜。 |
| 12-20 小时 | 正式中盘展开。 | 我要和谁交易、背叛或结盟？我能承担什么账单？ | 月租、债务、典当、势力声望 / 信任、黑市入口、Bond 事件、房间纪念物、剧本事件队列和第四层前置压力开始成为长期路线。 | 玩家在金币、声望、黑市、Bond、时间和房间记忆之间做不可完全兼得的选择。 |
| 20-35 小时 | 高层深渊与组合压力。 | 我愿意为了高层收益承受哪些不可逆代价？ | 第四 / 五层、订单链、污染扩散、黑市背叛、路线替换、高阶构筑检验、SAN / Bond 风险和剧情旗标组合起来。 | 高层不是单纯加数值，玩家能看见经济、构筑、关系和污染互相挤压。 |
| 35 小时以后 | 终局、回看和长尾。 | 我此前的选择最终如何结算？还有什么值得重开或挑战？ | 终局事件、结局条件、最终账单、房间终局展示、挑战 seed、长尾订单 / 物品 / 义体 / 纪念物和构筑复盘。 | 主线首通、结局分歧、回归测试、运行时美术验收和配置门禁稳定；长尾内容不破坏主循环节奏。 |

阶段推进规则：

1. 每个时长段都必须保留基础的“小镇 -> 人偶 / 日程 -> 下潜 -> 战斗 / 事件 -> 回城 -> 结算 / 维护 -> 再下潜”循环。
2. 新系统不应在某个时长点突然整块出现，而应先轻露出，再随着玩家问题逐步开放策略层。
3. 早期也必须有基础人偶养成、日程切换、深渊、战斗、出售和维护；后期是在这些基础上增加压力、代价、记忆和终局裁决。
4. 具体开发按 `14` 中已完成的细案实现切片派发；实现切片必须标注服务哪个时长段、补齐该时长段内哪条玩家结果链。
5. 时长是设计锚点，不是硬性数值；后续可以根据实测节奏微调，但不能改回按模块切阶段。

## 13. 0-12 小时细案设计入口

0-12 小时候选主循环不再在本文维护旧派发表。后续由 `版本规划/14_0-12小时候选主循环细案设计.md` 作为细案索引与承接规则，具体细案在 `版本规划/0-12小时细案/` 中一案一文。

细案必须承接第 12 节的游戏时长横向切分，而不是再按模块、功能点或验收点纵切。0-12 小时当前只保留五个主设计段：

| 细案段 | 时长 | 设计主题 |
|---|---|---|
| `T0` | 0-30 分钟 | 序章首次循环。 |
| `T1` | 30 分钟-2 小时 | 第一层搜打撤成形。 |
| `T2` | 2-5 小时 | 小镇压力与下潜目标成形。 |
| `T3` | 5-8 小时 | 第二 / 三层与构筑后果成形。 |
| `T4` | 8-12 小时 | 候选主循环稳定。 |

细案主体首先是游戏设计稿：写玩家旅程、情绪节奏、剧情包装、系统自然开放、关键选择和下一段钩子。实现 Owner 后续再基于设计细案拆具体实现方案、配置、UI / 美术、程序接入和验证。

细案工作流：

1. 游戏导演 / 制作人用本文定义宏观体验、模块职责、系统开放节奏和完成口径。
2. 0-12 小时细案 Owner 维护 `14` 的细案索引，并在 `版本规划/0-12小时细案/` 中按 T0-T4 逐段完善设计细案，保证前后体验融合。
3. 实现 Owner 只承接已经完成设计的目标时长段，并根据当前工程事实拆本切片具体方案、开发、接入、验证和回写。
4. 如果实现 Owner 发现细案与工程、配置或美术现实冲突，应回提细案变更，不得私自改变玩家结果、系统开放顺序或完成口径。

当前细案状态：

- `T0 序章首次循环` 已有设计稿 V2，对应 `版本规划/0-12小时细案/T0-01_序章首次循环.md`；完整开发入口为 `版本规划/0-12小时细案/T0-01_序章首次循环开发总方案.md`。该文件名保留旧兼容命名，但内容口径是 0-30 分钟时长段设计稿；实现侧按 `T0-01A / T0-01B / T0-01C` 分段承接，不以进入第一层作为完整 T0 结束点。
- `T1 第一层搜打撤成形` 已有设计稿 V1，对应 `版本规划/0-12小时细案/T1_第一层搜打撤成形.md`。该细案口径是 30 分钟-2 小时时长段设计稿，回答玩家如何学习路线、战斗意图、背包取舍、撤离 / 深入和第二层露出。
- `T2` 到 `T4` 仍是待设计队列。未完成设计细案前，不作为实现 Owner 的正式开工依据。

## 14. 系统保留 / 砍线判断

当前结论：不砍现有正式 GDD 系统。需要压缩或移出主线的，是制作层冗余和非玩家结果。

| 对象 | 判断 | 处理方式 |
|---|---|---|
| `GDD_01` 到 `GDD_12` | 全部保留。 | 纳入完整游戏宏观大纲，按阶段开放。 |
| 第四 / 五层内容 | 保留。 | 当前不抢核心纵切实现优先级，先作为完整游戏层级预留。 |
| 完整势力线 / 黑市背叛 | 保留。 | 不再只作为“后续铺量”，而是正式中盘主线之一。 |
| 完整房间 / 日记 / 纪念物 | 保留。 | 定位为长期记忆容器，避免做成强制数值经营系统。 |
| 完整好感 / 赠礼 / 特殊交互 | 保留。 | 早期轻触发，中后期随 Bond、房间和剧情事件展开。 |
| 剧本事件队列 | 保留。 | 不做章节播放器，作为系统状态触发和终局旗标调度层。 |
| 旧 PM 路由 | 压缩。 | 保留兼容入口，active 工作流转为游戏导演 / 制作人 + 任务 Owner。 |

| 按职能横切分包的默认工作流 | 砍掉默认模式。 | 改为任务 Owner 纵切负责，职能 agent 做总监验收。 |

## 15. 任务 Owner 工作流

实现切片必须按玩家结果命名，不按职能命名。

合格示例：

- `首次下潜到回城维护闭环`
- `第一层 Boss 后安全区与第二层解锁`
- `小镇出售到账单压力第一条链`
- `战斗意图到结算反馈可读性`
- `订单接取到背包占格目标链`
- `月租缺口到典当 / 欠债裁决`
- `第三层路线侵蚀到房间记忆`

不合格示例：

- `程序接 P3`
- `美术补图`
- `策划写经济`
- `UI 调整一批按钮`

### 15.1 Owner 责任流水

Owner 不是四个职能 agent 的简单叠加，而是围绕同一个玩家结果按阶段戴不同帽子。标准流水如下：

```text
证据审计 -> 策划详细设计 -> 配置源落地 -> UI/UX 与美术设计 / 素材 -> 程序功能与素材接入 -> Owner 自验 -> 职能总监验收 -> 状态回写
```

- 证据审计：先核对现有实现、配置、UI、美术和状态页证据；已有同名能力时转为缺口修复、UI 可达补强、服务绑定、表现补强、配置补齐或验收补强，不重复开发。
- 策划详细设计：补齐目标、范围外、规则 / 状态机 / 算法、关键配置字段、跨系统关系、UI / 美术表现需求、验收样例和完成判定。
- 配置源落地：修改 `配置表(JSON)` 源数据，运行同步 / Validator / 固定样例或人工复核；字段说明、README、审计或任务拆分不等于配置完成。
- UI/UX 与美术设计 / 素材：基于 active UI 规格、VisualID、美术风格基准和本切片玩家路径，完成界面结构、素材需求、资源接入或专工交接；耗时图片生成可以拆给专工，但体验目标和验收口径仍归 Owner。
- 程序功能与素材接入：接入真实领域服务、运行时 UI / 素材和状态变化；游戏规则不得写进 UI Controller，素材不得绕过 VisualID / 资源系统。
- Owner 自验：Owner 按玩家路径跑通本切片，整理 smoke、P0、配置校验、ArtAcceptance、截图、日志、人工流程或 `validation_limited:*` 证据。自验只证明本切片已按目标整理证据，不等于最终完成。
- 职能总监验收：主策验规则 / 配置 / 节奏，主程验架构 / 真实服务 / 状态 / 测试，主美验视觉 / UI / 素材 / 运行时表现；影响体验总线、开放节奏或完成口径时，由游戏导演 / 制作人验收。
- 状态回写：把策划、配置、程序、美术 / UI 和全局体验影响分别回写到对应状态页和事实文档，不能用一条跨职能混合进度替代。

### 15.2 实现切片字段

每个实现切片至少包含：

1. 玩家结果：玩家完成后能看见或做到什么。
2. 范围外：哪些内容本轮不做，避免横向膨胀。
3. 服务坐标：对应游戏时长段、细案切片 ID、`14` 的对应细案和第 6 节模块宏观设计行。
4. Owner 责任流水：本切片覆盖哪些阶段，哪些阶段需要专工协助。
5. 事实来源：GDD、开发文档、美术规格、配置 README、状态页。
6. 允许改动范围：配置、代码、UI、素材、文档中哪些可以改。
7. 需要验收的主职能：主策、主程、主美中的哪些需要验收。
8. Owner 自验：玩家路径、固定样例、截图 / 报告、人工复核等第一层验收证据。
9. 外部验收：主策 / 主程 / 主美 / 游戏导演中哪些人验收，验收未完成时不得标记已完成。
10. 验证证据：smoke、P0 报告、配置校验、ArtAcceptance、人工验收或 `validation_limited:*`。
11. 状态回写：所有受影响状态页和事实文档。

## 16. 职能总监模式

| 角色 | 默认职责 | 不默认承担 |
|---|---|---|
| 主策 | 体验节奏、规则一致性、数值压力、系统开放顺序验收。 | 不把每个配置或 GDD 小改拆给单独策划 agent。 |
| 主程 | 架构边界、服务归属、测试门禁、代码质量验收。 | 不把每个实现点拆给单独程序 agent。 |
| 主美 / UI 视觉总监 | 视觉方向、UI 结构、素材质量、运行时美术验收。 | 不把每个界面和素材默认拆给单独美术 agent。 |
| 专门耗时 agent | 图片生成、大批量素材处理、大规模配置填充、批量校验。 | 不自行决定体验方向或系统优先级。 |

职能总监验收是完成门禁，不是默认执行分包。实现 Owner 可以请求职能总监验收，但不应把执行责任拆回多个职能 agent；Owner 自验不能单独作为最终完成结论。

## 17. 完成口径

一个玩家结果只有同时满足以下条件，才能称为完成：

- 玩家正常 UI 可达，不只存在于 debug、截图或只读预览。
- 关键操作调用真实领域服务或运行时配置，不由 UI 直接伪造状态。
- 操作前后状态变化可验证。
- 相关视觉 / UI 表达足以让玩家理解规则。
- 有可追溯验证证据；如果验证受限，必须记录 `validation_limited:<reason>`。
- Owner 自验和对应职能总监 / 游戏导演外部验收结论已记录；未完成外部验收时只能标记为验收中、阻塞或 `validation_limited:*`。
- 任务 Owner 已回写所有受影响状态页。
