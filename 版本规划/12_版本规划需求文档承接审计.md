# 版本规划需求文档承接审计

> **定位：** 本文档只审计 `版本规划/09_正式版核心纵切开发路线.md` 和 `版本规划/11_设计文档纵切批次矩阵.md` 中出现的需求项是否已经有详细文档承接。它不重新定义路线、不替代 GDD、不替代开发文档或美术文档。

---

## 1. 审计规则

版本规划中的需求项不能只是一句话。只要某个功能、系统、工具或验收门禁进入 `09` / `11` 的当前开发范围，就必须能追到详细需求文档。

合格的详细文档可以是：

- GDD。
- 规则卡。
- 策划承接清单。
- 内容包。
- 配置 README。
- 程序需求文档。
- 美术 / UI 规格或覆盖矩阵。
- 自动化验收方案。

每个承接文档至少应能回答：

1. 目标和玩家可见体验。
2. 范围外。
3. 核心规则、状态机、算法或生成约束。
4. 配置字段、枚举、ID 引用或资源引用。
5. 跨系统关系。
6. UI / 美术表现需求。
7. Validator、自动化验收或人工验收样例。
8. 完成判定。

## 2. 状态定义

| 状态 | 含义 | 处理方式 |
|---|---|---|
| `通过` | 版本规划需求已经有详细文档承接，可交给对应职能继续拆任务。 | 后续变更时同步维护。 |
| `观察` | 已有详细文档，但仍需要在进入实现前同步到配置 README、UI active 规格或 Validator。 | 不阻塞规划，但派任务时必须带上缺口。 |
| `缺口` | 只有路线中的一句话或泛泛描述，无法独立交付开发。 | 先补需求文档，再进入开发。 |

## 8. 后续维护门禁

后续任何人修改 `09` 或 `11` 时，必须同步执行以下检查：

1. 新增的功能方向是否已经有详细需求文档。
2. 新增的 GDD 批次职责是否能追到规则卡、承接清单、配置 README、开发文档或美术规格。
3. 如果只是新增一句功能名，必须先补详细需求文档，再把它列入当前开发范围。
4. 如果需求已有文档，只更新本文的承接表和审计状态。
5. 如果需求变成后续批次或归档内容，在本文标记为非当前门禁项，避免误导开发。

当前结论：截至 2026-05-24，版本规划 active 文档中提到的当前需求项均已有详细需求文档承接，未发现需要立即补文档的阻塞项。
