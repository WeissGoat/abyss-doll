# 正式版核心纵切开发路线

> **更新时间：** 2026-05-24
> **定位：** 本文档只定义项目从 MVP 验证转向“正式版核心纵切”的顶层目标、阶段边界和系统优先级。具体规则落到 `设计文档/`，具体程序拆分落到 `开发文档/`。

---

## 1. 阶段判断

当前项目已经完成 MVP 证明阶段：

*   背包网格、AP 回合制战斗、战斗掉落拾取、小镇卖出、撤离/战败结算、义体制造、层级解锁、2 层压力等核心链路已经跑通。
*   自动化试玩已完成多批稳定性验证，核心闭环没有系统性断点。
*   美术运行时验收工具已经能覆盖关键界面，后续可以作为 UI/美术接入质量门禁。
*   实际体验方向成立，整体接近《背包英雄》式的“背包构筑 + 局外成长 + 深层压力”框架。

因此，后续目标不再是继续补一个更完整的 MVP，而是进入：

```text
正式版核心纵切
```

这里的“纵切”只代表开发顺序，不代表质量降级：

```text
按正式版去处理，只不过纵向处理，依次完整处理每个系统。
```

也就是说，项目不会先用临时版本占位再返工；而是一次选中一个系统，把被选中的系统按正式版标准完成规则、配置、表现、验证和文档链路。未进入当前批次的系统只是还没轮到，不等于用临时方案替代正式设计。

---

## 2. 总原则

### 2.1 纵向完整，而不是横向铺量

后续每一轮开发应选择一个系统纵向做深：

```text
设计规则 -> 配置结构 -> 运行体验 -> UI/表现 -> 自动化验证 -> 文档同步
```

只有这条链路完整，才算该系统进入可持续扩展状态。被选中的系统应按正式版目标收口，而不是停在验证占位或临时规则上。

### 2.2 不做临时口径

用批次控制当前处理的系统和内容量，但不再主动设计“后续必定推翻”的临时规则。

如果一个系统进入当前纵切批次，就按正式版目标处理。内容量可以按批次逐步增加，但系统规则、数据结构、交互边界和验证方式不应以“以后重做”为前提。

### 2.3 规则归属清晰

本路线文档不承载具体系统规则。后续引用关系如下：

*   系统关系、优先级和循环健康度：`设计文档/GDD_00_系统关联总图.md`
*   背包战斗与局内网格：`设计文档/GDD_01_背包战斗与局内网格机制.md`
*   深渊探索、层级、安全区、撤离与失败：`设计文档/GDD_02_深渊地图遍历与搜打撤抉择.md`
*   小镇经济与长期压力：`设计文档/GDD_04_小镇循环与经济物价波浪模型.md`
*   物品职责、标签和生命周期：`设计文档/GDD_06_物品系统与物品生命周期.md`
*   局外成长、义体、底盘和构筑路线：`设计文档/GDD_08_人偶养成子模块全案.md`
*   程序边界、重构路线和编码约定：`开发文档/12_程序开发优化建议与重构路线.md`、`开发文档/13_编程规范与架构约定.md`

`设计文档/` 不会在同一批次全部并行开发。每份 GDD 的纵切批次、系统完成口径和当前依赖关系见：`版本规划/11_设计文档纵切批次矩阵.md`。

### 2.4 保留快速验证，但以正式沉淀为终点

Agent 自动化、白盒试玩和运行时截图验收仍然是效率优势。区别在于：验证通过后应沉淀为正式系统，而不是让临时验证口径长期占据主路径。

## 3. 正式版纵切范围

当前目标不是横向同时铺满所有正式版内容，而是把核心玩法链路按正式版质量纵向打穿：

```text
正式开局
  -> 第 1 层基础探索
  -> 第 2 层机制压力
  -> 局外卖出 / 制造 / 升级
  -> 更深层入口与下一阶段素材
  -> 可扩展到第 3 层及以上的系统骨架
```

### 3.1 当前纵切应完成

*   背包与物品生命周期正式化。
*   战斗与怪物机制框架正式化。
*   深渊探索、层级入口和撤离节奏正式化。
*   局外成长系统正式化。
*   基础经济与长期压力框架落地。
*   UI 与美术资源接入流程稳定化。
*   自动化验证从“能跑”升级为“系统质量门禁”。

### 3.2 范围控制方式

范围控制只控制“当前先处理哪个系统”，不控制“被处理系统是否按正式版完成”。

*   当前批次未选中的剧情、好感、势力订单、房间等系统不抢跑。
*   当前批次选中的系统必须给出正式版规则、配置结构、UI/表现需求和验证标准。
*   内容量可以随着系统批次扩展，但不能把临时规则写成主路径。
*   如果某系统已经被纳入 A1-A4 节点，就按正式版口径推进，不再标记为“完整版以后再做”。

---

## 4. 系统纵切优先级

### 4.1 第一优先：背包与物品生命周期

这是游戏最核心的体验资产。正式化目标是让玩家从拾取、携带、使用、丢弃、撤离、战败、出售、制造消耗中都能理解“物品为什么来到这里，又为什么离开这里”。

关联文档：`GDD_01`、`GDD_06`、`GDD_04`。

### 4.2 第二优先：战斗与怪物机制框架

AP 回合制已经成立，下一步应从“能打”升级为“可扩展、可读、可复查的战斗体验”。玩家应能理解每一次伤害、护盾、异常、诅咒、腐蚀和 SAN 变化。

关联文档：`GDD_01`、`GDD_06`、`开发文档/11_怪物AI与行动系统(MonsterActionAI).md`。

### 4.3 第三优先：深渊探索与层级节奏

深渊探索是正式版主干系统，应按节点网络、路线选择、层级入口、继续深入、撤离、失败、节点职责和节奏释放关系完整设计。若程序排期尚未进入该系统，可以不抢跑实现；一旦进入 A3，就不应以单线临时地图作为正式完成口径。

关联文档：`GDD_02`。

### 4.4 第四优先：局外成长系统

义体、底盘、配方和材料缺口需要从“验证能制造”升级为“玩家能形成构筑方向”。局外成长应明确改变下一次下潜的战斗、空间或续航策略。

关联文档：`GDD_08`、`GDD_06`。

### 4.5 第五优先：经济与长期压力

游戏需要稳定理由让玩家反复下深渊。经济系统进入纵切批次后，应按正式版压力链、收入支出、目标驱动和验证口径处理；当前优先先把至少一条能驱动中期决策的压力链做完整。

关联文档：`GDD_04`、`GDD_07`、`GDD_10`。

### 4.6 第六优先：UI 与美术工作流

UI 和美术不再只是白盒占位，而要逐步成为稳定表达规则的界面系统。运行时截图验收、资源 Manifest、VisualID 检查应成为后续变更的常规门禁。

关联文档：`美术文档/`、`开发文档/09_视觉资源系统程序开发规范.md`、`开发文档/14_Unity运行时美术自动验收方案.md`。

## 5. 阶段里程碑

### A0：路线切换与文档口径整理

目标：

*   明确项目不再以 MVP 补丁为主线。
*   将顶层路线、GDD 规则、程序落地文档分层管理。
*   标记旧 MVP 文档为历史验证材料，避免后续被误当作当前目标。

完成标准：

*   本路线文档建立。
*   `GDD_00` 和关键系统 GDD 关联到当前路线。
*   `02_开发里程碑与节点规划.md`、`GEMINI.md` 更新当前阶段。

### A1：核心边界收口

目标：

*   降低后续纵切开发的冲突风险。
*   让背包、物品、战斗、流程、表现各自拥有清晰责任边界。

完成标准：

*   当前核心闭环行为不倒退。
*   自动化测试和运行时美术验收保持可运行。
*   后续系统可以在清晰边界上继续扩展。

### A2：背包与战斗正式纵切

目标：

*   将核心玩法最关键的两个系统做成正式版基础。

完成标准：

*   玩家能清楚理解背包和战斗中的每个损失、收益、异常状态。
*   自动化测试覆盖关键物品生命周期和典型怪物行为。

### A3：深渊与局外成长纵切

目标：

*   把“下潜 -> 回来变强 -> 继续深入”的正式版脊梁做稳。

完成标准：

*   玩家不依赖测试说明，也能理解当前目标、下一层入口、升级路径和资源缺口。

### A4：经济压力与内容纵切

目标：

*   加入让玩家持续下深渊的长期动机。

完成标准：

*   玩家开始面对“今天做什么”的局外决策，而不仅是重复打怪。

## 6. 旧 MVP 文档处理方式

`00` 到 `08` 号版本规划文档保留为历史验证资料和阶段复盘，不删除。

后续引用规则：

*   需要了解 MVP 为什么这样定，读旧 MVP 文档。
*   需要运行自动化试玩，读 `07_MVP自动化试玩验收方案.md`。
*   需要复盘首轮调参，读 `08_MVP自动化试玩首轮报告.md`。
*   需要当前正式版核心纵切路线，以本文档为准。
*   如果旧 MVP 文档和当前 GDD / 本路线冲突，以当前 GDD 和本路线为准。

## 7. PM 版本规划管理口径

PM / 版本规划智能体负责维护本文档的阶段目标、系统优先级、里程碑和跨职能拆分口径，不替代具体系统事实来源。

当前 PM 执行层版本节点见：`版本规划/10_正式版核心纵切版本节点规划.md`。

版本规划变更同步规则：

*   阶段目标、系统优先级或里程碑变化时，更新本文档。
*   项目总目标、跨职能交接、阻塞项或下一步总优先级变化时，更新 `PROJECT_STATUS.md`。
*   PM 自身判断、最近完成、下一步建议和阻塞项写入 `agent_status/pm.md`。
*   具体规则变化写入对应 GDD；程序边界变化写入开发文档；美术/UI 交付变化写入美术文档。

每个正式纵切工作包至少应明确：

*   目标：本轮要让玩家或系统获得什么正式版能力。
*   范围外：本轮明确不铺开的内容量或支线系统。
*   事实来源：涉及的路线、GDD、开发文档、美术文档、配置或数值模型。
*   职能交接：策划、程序、美术/UI 各自需要产出什么。
*   验收方式：自动化测试、运行时截图验收、配置校验或人工走查入口。
