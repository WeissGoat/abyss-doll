# 正式版核心纵切开发路线

> **定位：** 本文是正式版开发的宏观总线，回答“接下来按什么优先级纵向完成哪些系统、长期节点如何推进、各职能状态回到哪里”。具体需求展开、GDD 批次和文档承接见 `版本规划/11_纵切批次与需求文档承接矩阵.md`。原 `12_正式版长期版本节点规划.md` 的长期节点和防重复派发规则已并入本文，不再作为 active 规划文档维护。

---

## 1. 当前阶段判断

项目已完成 MVP 证明阶段，当前进入正式版核心纵切。

已成立的基础判断：

- 背包网格、AP 回合制战斗、战斗掉落拾取、小镇卖出、撤离 / 战败结算、义体制造、层级解锁和二层压力等核心链路已经跑通。
- 自动化试玩和配置校验已证明核心闭环没有系统性断点。
- 运行时美术验收和 UI / VisualID 接入链路已经能作为后续质量门禁继续扩展。
- 实际玩法方向成立，项目目标转为正式版纵向开发，而不是继续补一个更完整的 MVP。

这里的“纵切”只代表开发顺序，不代表临时质量：

```text
按正式版去处理，只不过纵向处理，依次完整处理每个系统。
```

被选中的系统按正式版规则、配置、表现、验证和文档链路完成；未进入当前批次的系统只是暂缓，不写成半成品主路径。

## 3. 纵切原则

### 3.1 纵向完整

每轮正式纵切至少闭合以下链路：

```text
设计规则 -> 配置结构 -> 程序能力 -> UI / 表现 -> Validator / 自动验收 -> 文档同步
```

只完成其中一段不算系统完成。

### 3.2 用优先级控范围，不用临时规则控质量

范围控制只决定“先做哪个系统、先填多少内容量”。一旦某系统进入当前纵切，就按正式版标准处理规则、数据、交互、表现和验收。

### 3.3 需求不能只是一句话

任何写入当前开发范围的功能、系统、工具或验收门禁，都必须能追到详细需求文档。承接关系统一维护在 `11_纵切批次与需求文档承接矩阵.md`。

### 3.4 内容量跟随系统能力

第四层以后副本、大量怪物 / 物品 / 订单 / 剧情文本 / 美术资源属于内容生产，不抢核心系统纵切。先让前三层和局外循环具备正式配置、验收和扩展能力，再继续铺大规模内容。

## 4. 功能开发优先级

当前优先级按“是否阻塞正式版核心循环”排序。

> **状态核对：** 具体哪些程序、策划配置或美术工作已经具备验收证据，先看对应职能状态页和事实文档：PM 看 `agent_status/pm.md`，策划 / 配置看 `agent_status/design.md` 与 `设计文档/config/26_正式配置设计与填充推进计划.md`，程序看 `agent_status/program.md` 与开发文档，美术 / UI 看 `agent_status/art.md` 与美术文档。后续派发应围绕真实缺口定义为 bug 修复、验收补强、数据绑定、表现补强或配置补齐，避免把已具备证据的基础能力作为新任务重开。

| 优先级 | 功能方向 | 正式版目标 | 当前口径 |
|---|---|---|---|
| P0 | 配置 / Validator / 自动验收底座 | 配置能被机械检查，固定 seed 和报告能成为门禁，策划配置修改可被持续验证。 | 静态 `ConfigValidator` 已部分落地；短期重点是统一 P0 验收入口、报告、Strict 门禁和 seed 摘要。 |
| P1 | 背包、物品生命周期与战斗可读性 | 旋转、拾取、放置、撤离、战败、出售、制造消耗、怪物意图和战斗反馈形成正式主干。 | 当前最核心功能纵切，直接决定玩法手感。 |
| P2 | 深渊地图、层级入口与搜打撤节奏 | 节点网络、路线选择、层级入口、已通层直达、安全区、撤离 / 继续深入和失败结算可配置、可验收。 | 第二核心功能纵切，不把单线地图作为正式完成口径。 |
| P3 | 局外成长与构筑方向 | 底盘、义体、配方、材料缺口、维护和下潜许可让“回来变强”成立。 | 跟随 P2 打通下潜回流和再次挑战。 |
| P4 | 经济压力与轻量目标导向 | 售卖、维护、账单、材料目标、订单或等价压力链形成中期驱动力。 | 候选版本前至少完成一条可玩压力链。 |
| P5 | UI / 美术 Formal V1 接入 | 围绕当前功能纵切补表达、资源和截图验收，让玩家读懂规则。 | 作为功能可读性门禁，不作为独立横向铺量目标。 |

## 5. 当前主线顺序

### P0：配置 / Validator / 自动验收底座

目标：让正式配置和后续内容填充可以持续验证。

短期重点：

- 一键 P0 验收脚本。
- 统一 `report.json` / `report.md`。
- 固定 seed 回归摘要。
- ConfigValidator、Unity smoke test、UI 校验和 ArtAcceptance latest 汇总。

详细需求：`开发文档/15_P0配置Validator与自动验收底座需求.md`。

### P1：背包与战斗正式纵切

目标：把玩家最频繁接触的背包与战斗做成正式体验基础。

近期重点：

- 物品旋转、放置、拖拽取消、拾取、丢弃、使用、出售、制造消耗共用领域规则。
- 战利品拾取和背包容量压力闭环。
- 怪物意图、异常、诅咒、腐蚀、失败原因和收益损失可读。

主要承接：`GDD_01`、`GDD_06`、`GDD_09`。

### P2：深渊地图与搜打撤节奏

目标：把下潜过程从线性节点升级为正式节点网络。

近期重点：

- 多行节点网络、连线生成、路线主题和 seed 可复现。
- 层级入口、已通层直达、安全区、撤离 / 继续深入。
- 失败结算和路线风险收益表达。

主要承接：`GDD_02`。

### P3：局外成长与构筑方向

目标：让玩家回城后能形成下一轮下潜计划。

近期重点：

- 底盘、义体、配方、材料缺口。
- 维护、下潜许可和升级反馈。
- 人偶核心状态与基础交互反馈。

主要承接：`GDD_08`、`GDD_03`、`GDD_12`。

### P4：经济压力与长期目标

目标：提供持续下潜的中期驱动力。

近期重点：

- 售卖、维护支出、月租 / 账单或等价压力。
- 传闻价格波、订单目标、声望或黑市背叛入口。
- 经济压力不能在前三层造成不可恢复死锁。

主要承接：`GDD_04`、`GDD_07`、`GDD_10`。

### P5：UI / 美术正式表达

目标：让核心规则被玩家看懂。

近期重点：

- 当前功能涉及界面的 Formal V1 接入。
- VisualID、Approved 资源和运行时截图验收。
- 只跟随 P0-P4 当前主线补表现，不横向铺所有界面。

### 5.1 程序近期三段推进计划

定位：以下是程序侧最新实施顺序，承接用户当前优先级：先检查并支持策划已完成的 C1-C3 配置，再继续开发“功能未开放完”的主流程闭环，最后做程序架构优化 / 收口。实际完成状态仍以 `agent_status/program.md`、开发文档、代码事实和验收证据为准；需求承接仍以 `11_纵切批次与需求文档承接矩阵.md` 为准。

| 顺序 | 工作线 | 目标 | 完成口径 |
|---|---|---|---|
| 1 | C1-C3 配置程序支持 | 确认前三层正式配置能被运行时解析、校验、固定 seed 验收和玩家主流程消费。 | 配置同步、Validator、关键 smoke 或 P0 报告能说明前 3 层 Items / Rewards / Monsters / Dungeons / Orders / Rumors / Factions 的阻断与非阻断状态。 |
| 2 | 主流程未开放完闭环 | 把已存在的数据层 / 领域服务接到玩家正常 UI 路径，补齐下潜、地图、战斗、战利品、阶梯、撤离、出售、维护、再下潜。 | 玩家能从小镇出发，完成一段深渊，带回战利品，回城处理经济和维护，再次下潜；关键按钮调用真实领域服务并有状态变化证据。 |
| 3 | 程序架构优化 / 收口 | 在主流程打通后，收紧 `GameFlowController`、UI Controller、领域服务、EventBus、Validator 和测试入口职责。 | UI 只展示和调度，规则回到领域服务；Result / Report DTO、P0 报告和 smoke test 入口稳定，后续扩展不再堆到总控或 UI。 |

这三段是连续工作，不是只完成第一段就收工：

```text
C1-C3 配置可消费 -> 玩家主流程可连续操作 -> 架构边界收紧并沉淀为长期框架
```

### 5.2 第一优先级：C1-C3 配置程序支持

目标：策划已完成 C1-C3 配置源后，程序侧先确认这些配置真的能被当前运行时消费，而不是只停留在 JSON 存在或 README 说明。

工作包：

| 工作包 | 内容 | 验收重点 |
|---|---|---|
| `CFG-01` | 同步配置并静态 / 运行时审计 C1-C3 的字段解析、ID 引用、奖励表、怪物 AI、节点类型、订单、传闻、势力和固定 seed 样例。 | 输出阻断 / 非阻断缺口清单；如果 Unity Editor 不可用，必须记录 `validation_limited:<reason>` 和替代证据。 |
| `CFG-02` | 修复 `CFG-01` 发现的阻断性程序缺口，例如旧 smoke 口径、字段解析缺失、Validator 分级错误或层级入口消费问题。 | C1-C3 关键配置可同步、可解析、可校验，旧测试不再按 MVP 假设误判正式配置。 |

范围外：

- 不替策划重填数值或批量新增内容。
- 不把字段说明、审计结论或设计草案当成配置源完成。
- 不把美术缺图作为配置运行时失败处理，除非 VisualID 是当前程序契约的阻断项。

### 5.3 第二优先级：主流程未开放完闭环

目标：把已经存在的领域服务、只读快照和配置能力接入玩家正常 UI 路径，形成一个可玩的整体。判断口径是“玩家可达 + 调用真实服务 + 状态真实变化 + 有 smoke / P0 证据”，不是 debug 面板、ArtAcceptance 截图或只读预览。

主流程目标路径：

```text
小镇准备
-> 层选择 / 下潜许可
-> 深渊地图
-> 节点选择
-> 战斗 / 非战斗节点
-> 战利品拾取
-> 阶梯 / 安全区
-> 进入下一层或撤离
-> 结算回城
-> 出售 / 订单 / 账单 / 维护 / 成长
-> 再次下潜
```

工作包：

| 工作包 | 内容 | 验收重点 |
|---|---|---|
| `FLOW-01` | 玩家路径缺口审计：找出不可达入口、假按钮、只读面板、状态不回写、只在 debug / 验收截图可见和缺测试的断点。 | 输出按阻断级别排序的断点清单和实现顺序。 |
| `FLOW-02` | 打通层选择、下潜许可和地图进入。 | 已解锁层可进入，未解锁层显示原因，进入后地图节点与连线状态正常。 |
| `FLOW-03` | 打通地图节点、战斗、非战斗节点、战斗结算、战利品拾取 / 放弃和返回地图。 | 奖励来自 `RewardSystem`，战斗结算消费 `CombatOutcomeReport`，拾取 / 放弃状态真实。 |
| `FLOW-04` | 打通配置 `StairsNode`、安全区恢复、撤离、进入下一层和层级解锁。 | L1 -> L2 -> L3 可跑，撤离结算和下一层入口真实更新。 |
| `FLOW-05` | 打通小镇经济至少一条真实操作链。 | 出售 / 订单 / 账单至少一项真实改变金币、物品、声望、信任或账单状态。 |
| `FLOW-06` | 打通工坊成长至少一条真实操作链。 | 维护 / 制造 / 装备 / 交互至少一项真实消耗资源并刷新下潜许可或人偶状态。 |
| `FLOW-07` | 把分段能力串成黄金路径 smoke / P0 摘要。 | 小镇 -> 深渊 -> 战斗 -> 战利品 -> 回城 -> 出售 / 维护 -> 再下潜可复现。 |

未开放完的典型判定：

- 服务已存在但没有玩家正常 UI 入口。
- 面板能显示只读快照，但关键按钮没有调用真实领域服务。
- UI 操作后金币、物品、HP / SAN、层级解锁、订单、声望或维护状态没有真实回写。
- 功能只在 debug、验收预览对象或 ArtAcceptance 截图中可见。
- UI Controller 直接修改真实状态，没有走领域服务。
- 没有 smoke test、固定 seed 或 P0 报告入口证明该路径。

### 5.4 第三优先级：程序架构优化 / 收口

目标：主流程可达后再收紧真实暴露出来的耦合点，避免为了重构而重构，也避免总控和 UI 继续吞业务逻辑。架构收口服务于后续扩展，不能改变玩法结果。

工作包：

| 工作包 | 内容 | 验收重点 |
|---|---|---|
| `ARCH-01` | 职责边界审计：审查 `GameFlowController`、UI Controller、领域服务、EventBus、ConfigValidator 和 smoke test 的真实耦合点。 | 明确哪些规则仍在总控或 UI、哪些入口重复、哪些测试脆弱。 |
| `ARCH-02` | 分离流程编排与领域操作。 | `UI Button -> Controller -> Service -> Result DTO -> Refresh` 链路清晰，UI 不直接改 HP / SAN / 金币 / 背包 / 订单 / 奖励。 |
| `ARCH-03` | 只读快照与可操作服务配对。 | 每个可读面板知道对应操作服务；只有快照不能标记为可玩完成。 |
| `ARCH-04` | 收紧 Validator、P0 报告和 smoke test 入口。 | error / warning 口径稳定，主流程 smoke 能被统一报告引用。 |
| `ARCH-05` | 文档和状态防重复收口。 | 已完成项、未开放项、补强项和架构项命名清楚，避免重复开发或误报完成。 |

架构红线：

- `GameFlowController` 只做流程状态切换、场景上下文和面板协调，不承载奖励、经济、维护、层级解锁等业务规则。
- UI Controller 只展示状态、收集输入、调用服务和展示结果，不直接改写领域状态。
- 领域服务返回明确 Result / Report DTO，包含成功、失败原因、状态变化摘要和 UI 可展示文本。
- EventBus 用于跨模块通知，不作为隐藏业务执行入口。
- Smoke test 围绕玩家可见闭环和配置契约，不围绕内部实现碎片写脆弱断言。

### 5.5 执行节奏与切换条件

1. 先执行 `CFG-01`：同步 C1-C3 配置并产出程序消费缺口清单。
2. 若 `CFG-01` 发现阻断程序缺口，执行 `CFG-02` 修复；若只有非阻断 warning，记录后进入 `FLOW-01`。
3. 执行 `FLOW-01` 后，按断点阻断级别推进 `FLOW-02..FLOW-07`，优先打通“小镇 -> 下潜 -> 地图 -> 战斗 / 战利品 -> 阶梯 / 撤离 -> 回城 -> 出售 / 维护 -> 再下潜”。
4. 主流程每打通一段，都要补 smoke 或 P0 摘要，且回写 `agent_status/program.md`。
5. `ARCH-01..ARCH-05` 在主流程暴露出真实耦合点后执行；架构收口不抢在功能开放前做空转重构。
6. 有 Approved 美术资源和 active UI 规格时，随对应功能一起接入 VisualID / UGUI / ArtAcceptance；缺资源或规格不适配时记录到美术交接，不把占位表现标成正式完成。

单个工作包完成条件：

- 玩家主流程可达：不是只通过 debug 面板或验收预览对象看到结果。
- 真实服务调用：关键按钮调用后端或领域服务。
- 状态变化可验证：操作前后有明确运行时状态变化、失败原因或只读快照变化。
- 验收证据可追溯：有 smoke test、固定 seed、P0 报告或明确的 `validation_limited:<reason>`。
- 文档和状态回写：完成后更新 `agent_status/program.md`；影响阶段目标、跨职能交接或门禁时再同步 `PROJECT_STATUS.md`、`09` 或目标职能状态页。

程序侧防重复状态标签：

| 标签 | 派发含义 |
|---|---|
| `服务完成` | 领域服务、数据层或只读快照已有证据，但不能宣称玩家可玩完成；后续只派 UI 入口、服务绑定、状态回写或验收补强。 |
| `UI可达` | 玩家能进入入口，但仍需确认关键按钮是否调用真实服务。 |
| `展示已接入` | 只读 UI 已消费真实快照 / Report DTO，不等于可操作闭环。 |
| `可操作闭环完成` | 正常 UI 可达、真实服务调用、状态变化和验收证据同时成立；不得以同名基础功能重开，只能按 bug、验收补强、表现补强或配置补齐处理。 |
| `验收受限` | 存在 `validation_limited:*`，只能说明验证覆盖受限，不能把受限范围标为通过。 |
| `未开放` | 没有正常玩家入口或真实服务绑定，应按入口 / 服务 / 状态 / 验收拆分开发。 |
| `架构收口` | 只处理真实耦合点，不替代功能开放，也不改变玩法结果。 |

## 9. 防重复派发与状态口径

1. 派发任何工作前，先读取对应职能状态页，确认同名系统、功能或工作项的最新证据、真实缺口和后续批次位置。
2. 如果状态页显示该职能已经具备验收证据，后续任务必须按真实缺口命名为 bug 修复、验收补强、数据绑定、配置补齐、表现补齐或质量修复。
3. 同一系统涉及多个职能时，各职能分别记录状态；不得写一条“系统完成”替代分职能状态。
4. 字段说明、README、审计结论、任务拆分、ID 锁定和 JSON 修改前设计属于策划 / 配置证据，不等于配置源完成。只有配置源 JSON 或运行时配置副本落地并通过校验，才可称为配置完成。
5. 完成开发、配置、美术、UI、策划或验收工作后，必须回写对应职能状态页；只有影响本文的长期节点、优先级、节点门禁或通用派发规则时才更新本文。

## 10. PM 维护规则

- `09` 只维护宏观总线和功能优先级。
- 任何新增到当前范围的功能，先在 `11` 确认详细文档承接。
- 长期版本节点、节点门禁、职能进度入口和防重复派发规则写入本文；具体工作项状态和证据入口回到对应职能状态页与事实文档。
- 具体规则变化写入 GDD 或规则卡。
- 程序边界变化写入开发文档。
- 美术 / UI 交付变化写入美术文档。
- 配置字段和内容落点写入配置 README 或配置源。

每个正式纵切工作包至少明确：

- 目标。
- 范围外。
- 事实来源。
- 策划 / 程序 / 美术交接。
- 验收方式。
