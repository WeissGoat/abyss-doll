# 正式版核心纵切开发路线

> **定位：** 本文是正式版开发的宏观总线，回答“接下来按什么优先级纵向完成哪些系统、长期节点如何推进、各职能状态回到哪里”。具体需求展开、GDD 批次和文档承接见 `版本规划/11_纵切批次与需求文档承接矩阵.md`。原 `12_正式版长期版本节点规划.md` 的长期节点和防重复派发规则已并入本文，不再作为 active 规划文档维护。

---

## 1. 当前阶段判断

项目已完成 MVP 证明阶段，当前进入正式版核心纵切。

已成立的基础判断：

- 背包网格、AP 回合制战斗、战斗掉落拾取、小镇卖出、撤离 / 战败结算、义体制造、层级解锁和二层压力等核心链路已经跑通。
- 自动化试玩和配置校验已证明核心闭环没有系统性断点。
- 运行时美术验收和 UI / VisualID 接入链路已经能作为后续质量门禁继续扩展。
- 实际玩法方向成立，项目目标转为正式版纵向开发，而不是继续补一个更完整的 MVP。

这里的“纵切”只代表开发顺序，不代表临时质量：

```text
按正式版去处理，只不过纵向处理，依次完整处理每个系统。
```

被选中的系统按正式版规则、配置、表现、验证和文档链路完成；未进入当前批次的系统只是暂缓，不写成半成品主路径。

## 3. 纵切原则

### 3.1 纵向完整

每轮正式纵切至少闭合以下链路：

```text
设计规则 -> 配置结构 -> 程序能力 -> UI / 表现 -> Validator / 自动验收 -> 文档同步
```

只完成其中一段不算系统完成。

### 3.2 用优先级控范围，不用临时规则控质量

范围控制只决定“先做哪个系统、先填多少内容量”。一旦某系统进入当前纵切，就按正式版标准处理规则、数据、交互、表现和验收。

### 3.3 需求不能只是一句话

任何写入当前开发范围的功能、系统、工具或验收门禁，都必须能追到详细需求文档。承接关系统一维护在 `11_纵切批次与需求文档承接矩阵.md`。

### 3.4 内容量跟随系统能力

第四层以后副本、大量怪物 / 物品 / 订单 / 剧情文本 / 美术资源属于内容生产，不抢核心系统纵切。先让前三层和局外循环具备正式配置、验收和扩展能力，再继续铺大规模内容。

## 4. 功能开发优先级

当前优先级按“是否阻塞正式版核心循环”排序。

> **状态核对：** 具体哪些程序、策划配置或美术工作已经具备验收证据，先看对应职能状态页和事实文档：PM 看 `agent_status/pm.md`，策划 / 配置看 `agent_status/design.md` 与 `设计文档/config/26_正式配置设计与填充推进计划.md`，程序看 `agent_status/program.md` 与开发文档，美术 / UI 看 `agent_status/art.md` 与美术文档。后续派发应围绕真实缺口定义为 bug 修复、验收补强、数据绑定、表现补强或配置补齐，避免把已具备证据的基础能力作为新任务重开。

| 优先级 | 功能方向 | 正式版目标 | 当前口径 |
|---|---|---|---|
| P0 | 配置 / Validator / 自动验收底座 | 配置能被机械检查，固定 seed 和报告能成为门禁，策划配置修改可被持续验证。 | 静态 `ConfigValidator` 已部分落地；短期重点是统一 P0 验收入口、报告、Strict 门禁和 seed 摘要。 |
| P1 | 背包、物品生命周期与战斗可读性 | 旋转、拾取、放置、撤离、战败、出售、制造消耗、怪物意图和战斗反馈形成正式主干。 | 当前最核心功能纵切，直接决定玩法手感。 |
| P2 | 深渊地图、层级入口与搜打撤节奏 | 节点网络、路线选择、层级入口、已通层直达、安全区、撤离 / 继续深入和失败结算可配置、可验收。 | 第二核心功能纵切，不把单线地图作为正式完成口径。 |
| P3 | 局外成长与构筑方向 | 底盘、义体、配方、材料缺口、维护和下潜许可让“回来变强”成立。 | 跟随 P2 打通下潜回流和再次挑战。 |
| P4 | 经济压力与轻量目标导向 | 售卖、维护、账单、材料目标、订单或等价压力链形成中期驱动力。 | 候选版本前至少完成一条可玩压力链。 |
| P5 | UI / 美术 Formal V1 接入 | 围绕当前功能纵切补表达、资源和截图验收，让玩家读懂规则。 | 作为功能可读性门禁，不作为独立横向铺量目标。 |

## 5. 当前主线顺序

### P0：配置 / Validator / 自动验收底座

目标：让正式配置和后续内容填充可以持续验证。

短期重点：

- 一键 P0 验收脚本。
- 统一 `report.json` / `report.md`。
- 固定 seed 回归摘要。
- ConfigValidator、Unity smoke test、UI 校验和 ArtAcceptance latest 汇总。

详细需求：`开发文档/15_P0配置Validator与自动验收底座需求.md`。

### P1：背包与战斗正式纵切

目标：把玩家最频繁接触的背包与战斗做成正式体验基础。

近期重点：

- 物品旋转、放置、拖拽取消、拾取、丢弃、使用、出售、制造消耗共用领域规则。
- 战利品拾取和背包容量压力闭环。
- 怪物意图、异常、诅咒、腐蚀、失败原因和收益损失可读。

主要承接：`GDD_01`、`GDD_06`、`GDD_09`。

### P2：深渊地图与搜打撤节奏

目标：把下潜过程从线性节点升级为正式节点网络。

近期重点：

- 多行节点网络、连线生成、路线主题和 seed 可复现。
- 层级入口、已通层直达、安全区、撤离 / 继续深入。
- 失败结算和路线风险收益表达。

主要承接：`GDD_02`。

### P3：局外成长与构筑方向

目标：让玩家回城后能形成下一轮下潜计划。

近期重点：

- 底盘、义体、配方、材料缺口。
- 维护、下潜许可和升级反馈。
- 人偶核心状态与基础交互反馈。

主要承接：`GDD_08`、`GDD_03`、`GDD_12`。

### P4：经济压力与长期目标

目标：提供持续下潜的中期驱动力。

近期重点：

- 售卖、维护支出、月租 / 账单或等价压力。
- 传闻价格波、订单目标、声望或黑市背叛入口。
- 经济压力不能在前三层造成不可恢复死锁。

主要承接：`GDD_04`、`GDD_07`、`GDD_10`。

### P5：UI / 美术正式表达

目标：让核心规则被玩家看懂。

近期重点：

- 当前功能涉及界面的 Formal V1 接入。
- VisualID、Approved 资源和运行时截图验收。
- 只跟随 P0-P4 当前主线补表现，不横向铺所有界面。

### 5.1 程序近期推进计划

定位：以下是程序侧近期实施顺序，用于把已落地的后端 / 领域服务接入玩家主流程。实际完成状态仍以 `agent_status/program.md`、开发文档、代码事实和验收证据为准；需求承接仍以 `11_纵切批次与需求文档承接矩阵.md` 为准。

#### 第一阶段：P1 战斗 UI 消费层

目标：让战斗 HUD 和战斗结算界面真实消费 `MonsterIntentPreviewService`、`CombatOutcomeReport`、`CombatTimelineRecorder`，把战斗数据从日志 / 只读快照推进到玩家可见流程。

交付口径：

- 怪物意图、锁定行动、可执行 / 阻塞原因在战斗中可见。
- HP 战败、SAN 崩溃、胜利结算、战利品、收益损失和最近时间线在结算中可读。
- UI Controller 只展示状态和调用后端入口，不直接改写 HP、SAN、掉落、背包或怪物行动。

验收入口：`CombatReadabilityTextServiceSmokeTest`、`CombatOutcomeReportSmokeTest`，以及战斗 HUD / 战斗结算主流程 smoke test。

#### 第二阶段：P4 经济 UI 操作闭环

目标：把订单、商店 / 出售渠道、传闻、账单 / 月租面板接入 `TownEconomyService` 与 `TownEconomyOverviewService`，形成小镇经济的真实可玩操作。

交付口径：

- 玩家可从 UI 接单、查看进度、交付、失败 / 放弃并看到声望、信任、金币和物品流向变化。
- 出售渠道使用真实估值和传闻价格波，不再停留在静态预览。
- 日结、月租、欠账和典当反馈由经济服务给出，UI 只负责展示选择和结果。

验收入口：`TownEconomyServiceSmokeTest`、`TownEconomyOverviewServiceSmokeTest`、经济相关 Formal V1 面板 smoke test。

#### 第三阶段：P3 工坊成长完整操作

目标：把底盘、义体、制造、维护、材料缺口和下潜许可接入 `GrowthFeedbackService`、`MaintenanceService`、`DiveReadinessService` 等真实服务，让回城后的成长决策可操作。

交付口径：

- 制造、装备、维护和材料缺口能从工坊主流程触发，并给出成功 / 失败原因。
- 下潜许可反馈能解释层级锁定、人偶状态、磨损 / 侵蚀、底盘、义体和背包合法性。
- 人偶核心状态与基础交互结果在 Formal V1 工坊流程中可读。

验收入口：`GrowthFeedbackServiceSmokeTest`、`MaintenanceServiceSmokeTest`、`DiveReadinessSmokeTest`、`WorkshopFormalV1PanelBindingSmokeTest`，以及工坊主流程 smoke test。

#### 第四阶段：P2 前三层正式配置与 Validator

目标：把 L1-L3 的节点网络、奖励、风险、安全区、阶梯、层级解锁和固定 seed 样例落到正式 JSON 与 Validator 门禁，让前三层具备稳定可验收的探索节奏。

交付口径：

- L1-L3 配置源完成并同步到 Unity 运行时副本。
- 固定 seed 能复现节点网络、关键路线、风险表达、奖励引用和层间入口。
- Validator 能区分 error / warning，并输出可被 PM、策划和程序复核的失败原因。

验收入口：`DungeonSeedAcceptanceSmokeTest`、`DungeonNodeTypesSmokeTest`、`DungeonMapVisibilitySmokeTest`、`ConfigValidationSmokeTest` 和 P0 统一验收报告。

#### 持续项：P0 Strict / report / seed 摘要

目标：随着 P1-P4 接入玩家流程，持续强化 `Invoke-P0Validation.ps1`、`report.json` / `report.md`、Strict 门禁和固定 seed 摘要。

交付口径：

- 新增系统必须能进入统一验收入口。
- warning 需要能说明是否阻塞候选版本，避免长期积累成不可判断的噪音。
- ArtAcceptance、UI 规格校验、ConfigValidator 和 Unity smoke test 的结果在 P0 报告中有稳定摘要。

### 5.2 下一轮程序工作包

定位：下一轮程序开发目标不是继续扩散系统数量，而是把已存在的数据层、后端服务和资源接入玩家能连续体验的主流程。工作包只描述派发顺序和完成口径，具体实现状态仍回到 `agent_status/program.md`。

#### W1：战斗玩家可见闭环收口

目标：把 P1 战斗只读数据层推进到玩家可见、可判断、可复盘。

范围：

- 战斗 HUD 显示怪物意图、锁定行动、可执行状态、关键伤害 / 干涉描述。
- 战斗结算界面消费 `CombatOutcomeReport` 与 `CombatTimelineRecorder`，展示胜负原因、SAN 崩溃 / HP 战败、战利品、收益损失和最近时间线。
- 保持 UI Controller 只展示和调用后端入口，不在表现层改写战斗规则或结算数据。

完成口径：战斗 HUD 和战斗结算主流程 smoke test 能证明玩家在正常战斗路径中看到上述信息。

#### W2：小镇经济真实操作闭环

目标：把小镇经济从只读概览推进到可操作的订单、出售、传闻和账单链路。

范围：

- 订单面板接入 `TownEconomyService`，支持接单、查看进度、交付、失败 / 放弃结果反馈。
- 出售渠道接入真实估值、传闻价格波和物品流向，不只展示静态文本。
- 账单 / 月租 / 欠账 / 典当反馈由经济服务产出，UI 只展示选择、确认和结果。

完成口径：玩家能从小镇 UI 触发至少一条“出售 / 订单 / 账单压力”链路，并在金币、声望、信任或物品上看到真实状态变化。

#### W3：工坊成长真实操作闭环

目标：让回城后的维护、制造、装备、材料缺口和下潜许可成为可操作决策。

范围：

- 维护按钮调用 `MaintenanceService`，展示成本、成功结果和失败原因。
- 制造 / 装备入口调用正式成长服务，展示材料缺口、金币缺口、可执行状态和结果。
- 下潜许可反馈解释层级锁定、人偶状态、磨损 / 侵蚀、底盘、义体和运行时背包合法性。
- 人偶核心状态和基础交互结果接入工坊主流程，而不是只停留在调试面板。

完成口径：玩家在工坊中能完成维护或制造类操作，并能据此决定是否再次下潜。

#### W4：前三层正式配置与 Validator 门禁

目标：让 L1-L3 探索节奏成为稳定可验收内容，而不是只依赖当前样例配置。

范围：

- 配置源补齐 L1-L3 节点网络、奖励、风险、安全区、阶梯、层级解锁和固定 seed 样例。
- Validator 覆盖关键引用、奖励表、节点类型、层级入口、风险表达和 VisualID。
- 固定 seed 摘要能复现关键路线、Boss / 阶梯可达性、奖励引用和安全区节奏。

完成口径：`ConfigValidationSmokeTest`、深渊相关 smoke test 与 P0 统一报告能稳定解释失败原因。

#### W5：P0 验收门禁持续收口

目标：让每个新接入的功能都能被统一验收脚本持续检查。

范围：

- 修正与正式配置口径不一致的旧 smoke test。
- 处理 `Invoke-P0Validation.ps1` 的 warning 分类、Strict 规则和 report 字段一致性。
- 新增或调整功能后同步加入 P0 报告摘要，避免只在单测日志中可见。

完成口径：P0 报告能清楚区分 pass、warning、blocked 和 failed，并能给 PM / 策划 / 程序复核提供稳定入口。

#### W6：美术资源随功能接入

目标：有 Approved 资源和 VisualID 时，程序接入应随功能一起完成资源绑定和运行时验收。

范围：

- 接入前读取 `美术文档/_generated/可接入素材清单.md` 和 active UI 规格。
- `program_integrate` 有待处理项时，优先完成 Registry / VisualID 绑定，再进入对应 UI 或系统表现接入。
- 缺少资源或规格不适配时，记录到 `agent_status/art.md` 或美术交接文档，由美术侧补齐；程序侧只做明确的临时视觉降级，不把资源缺口伪装成正式完成。

完成口径：相关界面既有真实业务入口，也能在 ArtAcceptance 或对应 UI smoke test 中看到正确资源绑定。

### 5.3 下一步程序执行顺序与切换条件

定位：本节只定义下一轮程序开发的执行节奏和切换条件，不替代 `agent_status/program.md` 的实现状态记录。每个工作包完成后，程序状态页必须记录代码事实、测试入口、P0 报告入口和仍未完成项。

#### 执行顺序

1. P0 验收底座先行检查：进入任何新功能前先确认 `Invoke-P0Validation.ps1`、关键 Unity smoke test、文档校验和当前配置同步没有阻断项。若阻断来自报告采集或旧测试口径，优先修复；若阻断来自策划配置或美术交付，记录到对应职能状态页后再决定是否切换工作包。
2. P1 战斗玩家可见闭环：优先把战斗 HUD 和战斗结算从只读数据层接到玩家主流程。重点不是新增战斗规则，而是让怪物意图、锁定行动、胜负原因、SAN / HP 战败、战利品和战斗时间线在正常游玩路径中可见。
3. P4 小镇经济真实操作闭环：在战斗结算和回城后，优先补出售、订单、传闻、账单 / 月租等能推动下一次下潜的操作。完成标准是 UI 调用 `TownEconomyService` / `TownEconomyOverviewService` 产生真实金币、声望、信任、物品或账单状态变化。
4. P3 工坊成长真实操作闭环：把维护、制造、装备、材料缺口、下潜许可和人偶交互从只读快照推进到工坊主流程。完成标准是玩家能在回城后做出一次真实成长或维护决策，并看到下一次下潜许可或构筑状态变化。
5. P2 前三层正式配置与 Validator：在主循环可玩后，集中补 L1-L3 的正式 JSON、固定 seed 样例、节点网络、奖励、风险、安全区、阶梯和层级解锁 Validator。该工作需要和策划配置状态页同步，不把 README、审计或设计草案直接当作配置源完成。
6. P5 表现与美术验收跟随功能：有 Approved 资源和 active UI 规格时，随对应功能一起接入 VisualID、UGUI 绑定和 ArtAcceptance 截图点；没有资源时记录明确缺口，不阻塞无资源依赖的领域服务和验证工作。

#### 单个工作包完成条件

- 玩家主流程可达：不是只通过 debug 面板或验收预览对象看到结果，至少有一条正常 UI 路径能进入该功能。
- 真实服务调用：关键按钮调用后端或领域服务，UI Controller 不直接改写 HP、SAN、金币、背包、掉落、订单、声望或成长状态。
- 状态变化可验证：操作前后有明确的运行时状态变化、失败原因或只读快照变化，并有 smoke test 或 P0 报告入口覆盖。
- 表现资源同步：如果 Approved 资源已经存在，完成 VisualID / Registry / UGUI 绑定；如果缺资源或规格不适配，写入美术交接而不是把占位图标记为正式完成。
- 文档和状态回写：完成后更新 `agent_status/program.md`；影响阶段目标、跨职能交接或门禁时再同步 `PROJECT_STATUS.md`、`09` 或目标职能状态页。

#### 暂缓范围

- 不在当前阶段横向铺所有 UI 页面；只接入当前 W1-W4 主流程需要的界面。
- 不在程序侧替策划批量填内容；程序负责 Validator、配置解析、运行时消费和失败原因表达。
- 不把截图覆盖、资源登记、只读预览或 debug 入口单独视为玩家可玩完成。

## 9. 防重复派发与状态口径

1. 派发任何工作前，先读取对应职能状态页，确认同名系统、功能或工作项的最新证据、真实缺口和后续批次位置。
2. 如果状态页显示该职能已经具备验收证据，后续任务必须按真实缺口命名为 bug 修复、验收补强、数据绑定、配置补齐、表现补齐或质量修复。
3. 同一系统涉及多个职能时，各职能分别记录状态；不得写一条“系统完成”替代分职能状态。
4. 字段说明、README、审计结论、任务拆分、ID 锁定和 JSON 修改前设计属于策划 / 配置证据，不等于配置源完成。只有配置源 JSON 或运行时配置副本落地并通过校验，才可称为配置完成。
5. 完成开发、配置、美术、UI、策划或验收工作后，必须回写对应职能状态页；只有影响本文的长期节点、优先级、节点门禁或通用派发规则时才更新本文。

## 10. PM 维护规则

- `09` 只维护宏观总线和功能优先级。
- 任何新增到当前范围的功能，先在 `11` 确认详细文档承接。
- 长期版本节点、节点门禁、职能进度入口和防重复派发规则写入本文；具体工作项状态和证据入口回到对应职能状态页与事实文档。
- 具体规则变化写入 GDD 或规则卡。
- 程序边界变化写入开发文档。
- 美术 / UI 交付变化写入美术文档。
- 配置字段和内容落点写入配置 README 或配置源。

每个正式纵切工作包至少明确：

- 目标。
- 范围外。
- 事实来源。
- 策划 / 程序 / 美术交接。
- 验收方式。
