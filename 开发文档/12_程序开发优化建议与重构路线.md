# 程序开发优化建议与重构路线

> **定位：** 本文档记录当前代码体检后发现的工程优化方向。它不是新功能需求清单，而是用于指导后续程序重构、任务拆分和 agent 协作的技术债收口路线。
> **当前阶段：** 正式版核心纵切：A1 核心边界收口。
> **更新时间：** 2026-05-22

---

## 1. 总体判断

项目已从 MVP 验证切换到正式版核心纵切。程序侧的目标也随之变化：后续不再优先继续堆功能点，而是先把已经跑通的核心闭环沉淀为正式系统骨架。

当前项目的核心架构方向是正确的：

* 玩法核心已经基本收敛到 `CoreBackend`、`CombatSystem`、`DungeonManager`、`WorkshopSystem` 等纯 C# 系统。
* 物品、奖励、怪物 AI、深渊节点、视觉资源均在向数据驱动靠拢。
* `ConfigValidator`、SmokeTest 和 headless 测试已经具备项目级质量门禁雏形。
* 美术资源通过 `VisualID -> VisualAssetRegistry -> UGUI` 接入，避免 JSON 直接引用 Unity 对象。

随着 MVP 证明阶段结束，部分表现层和交互层代码开始变重。当前最值得处理的不是新增大框架，而是把已经跑通的功能按职责重新收口，避免后续卖出、制造、战斗道具、结算、UI 换皮继续堆到同几个脚本里。

后续所有重构都要遵循 [`13_编程规范与架构约定.md`](./13_编程规范与架构约定.md)：功能可以慢慢填充，但框架、配置、Validator、测试和文档链路必须按正式版方向设计。

---

## 2. A1 程序侧目标

A1 的程序目标是“核心边界收口”，不是为了重构而重构。完成后应满足：

* `GameFlowController` 不再继续吸收具体业务规则。
* `CombatSystem` 回到战斗回合、胜负推进和战斗状态本身。
* 道具使用由独立 `ItemUseService` 承担，能被战斗、安全屋、未来事件节点复用。
* 背包拖拽和整理由 `InventoryInteractionService` 或等价服务统一处理，UI 不再直接修改背包真实状态。
* Runtime fallback UI 作为历史债务集中收口，并逐步从正式验收路径下线。
* 自动化测试与运行时美术验收继续可运行，作为边界收口的回归门禁。

---

## 3. 优先级路线

### P0：近期应优先处理

目标：降低后续功能迭代的碰撞风险。

* 拆分 `GameFlowController` 的职责。
* 将 `ItemUseService` 从 `CombatSystem.cs` 中独立出来。
* 收口背包拖拽对后端状态的直接修改。
* 逐步下线运行时 fallback UI，真实 UI 走场景或 Prefab 绑定；新增正式功能不得依赖 fallback 面板。

### P1：正式版纵切扩展前处理

目标：让配置、表现、校验形成稳定协作契约。

* 把背包 UI 尺寸和界面位置从硬编码迁入布局配置或显示规格。
* 强化 `ConfigValidator`，让 UI、视觉资源、旧字段和缺失配置在开发期暴露。
* 将 `HUDController`、结算 UI、战利品 UI 从“运行时搭界面”调整为“绑定已有层级并刷新数据”。
* 整理深渊地图生成策略，让层结构规则继续配置化。

### P2：内容扩展前处理

目标：为后续多层深渊、更多怪物、更多 UI 面板和存档打基础。

* 为 `ConfigManager` 增加只读 `ConfigDatabase` 或访问接口，降低全局静态字典扩散。
* 梳理事件订阅生命周期，减少依赖析构函数或隐式清理。
* 为重要服务建立更细的自动化测试，特别是背包交互、物品使用和 UI 事件桥接。

---

## 4. GameFlowController 瘦身

### 4.0 当前落地状态

已完成第一阶段背包表现层拆分：

* 新增 `InventoryPresentationController`，统一承接背包 UI 的显示、隐藏、布局、物品 UI 同步、层级管理和暂存丢弃 UI 清理。
* `GameFlowController` 不再订阅 `GameEventBus.OnItemPlaced` / `OnItemRemoved` 来直接生成或销毁背包物品 UI。
* `GameFlowController` 只把当前屏幕上下文映射给 `InventoryPresentationController`，例如 Workshop、DungeonMap、Combat、CombatLoot、SafeRoom、Stairs。
* `DraggableItemUI` 优先通过 `InventoryPresentationController.Active` 获取背包物品层和暂存丢弃权限，降低对流程控制器的直接依赖。
* `InventoryInteractionService` 继续负责背包真实规则，表现控制器只根据后端状态同步 UI，不成为状态源。

本阶段目标不是替换所有历史 UI，而是先把最容易和功能开发冲突的背包表现职责从流程控制器中拿出来，作为后续并行开发的稳定边界。

### 4.1 当前问题

`GameFlowController` 当前同时承担以下职责：

* 屏幕状态切换。
* Dungeon / Combat / Loot / Settlement 事件响应。
* 运行时创建战利品面板和结算面板。
* Debug 初始资源注入。

这些职责在 MVP 验证阶段集中到一个脚本里能快速推进，但后续每新增一个 UI 面板或流程节点，都容易改到同一个文件，造成冲突和回归风险。

### 4.2 建议拆分

推荐拆为：

* `GameScreenRouter`：只负责当前屏幕状态与面板显隐。
* `DungeonFlowPresenter`：只处理深渊流程事件，例如进入地图、战斗、战利品、结算。
* `InventoryPresentationController`：只处理背包 UI 的显示、隐藏、布局、同步和层级。
* `RuntimePanelFallbackFactory`：现存 fallback UI 在未完全替换前集中放在这个类里，并由开关控制。

### 4.3 约定

`GameFlowController` 或后续替代类应保持为“流程编排器”，不直接承担具体 UI 构建细节，也不直接修改背包领域状态。

## 5. ItemUseService 独立

### 5.0 当前落地状态

已完成第一阶段边界收口：

* `ItemUseService` 已从 `CombatSystem.cs` 移出到 `UnityClient/Assets/Scripts/Items/ItemUseService.cs`。
* 对外静态 API 保持不变，现有 UI 与测试仍通过 `ItemUseService.TryUseItem(...)`、`TryConfirmPendingTarget(...)` 和目标选择状态查询访问。
* 本阶段只调整系统归属，不改变战斗消耗品、安全屋消耗品、武器选敌和消耗品守卫规则。
* 后续仍建议继续拆出 `ItemTargetSelectionService`，并把 Heal / RestoreSAN / Shield 等直接 payload 逐步沉淀到效果系统。

已验证：

```text
dotnet build UnityClient/Assembly-CSharp.csproj --no-restore
Unity batchmode -executeMethod ItemUseSmokeTest.Run
```

### 5.1 当前问题

历史上 `ItemUseService` 定义在 `CombatSystem.cs` 内部，但它实际已经跨越多个场景：

* 战斗中使用武器和消耗品。
* 安全屋中使用消耗品。
* 等待敌方目标选择。
* 结算 AP、HP、SAN、护盾。
* 执行配置效果。
* 消耗物品并刷新背包。

这使 `CombatSystem.cs` 同时承载战斗回合和物品使用两类系统职责。

### 5.2 建议拆分

推荐新增目录：

```text
UnityClient/Assets/Scripts/Items/
    ItemUseService.cs
    ItemUseContext.cs
    ItemTargetSelectionService.cs
```

第一步可以只移动文件，不改变行为：

* `ItemUseService` 负责使用入口、场景校验和效果执行。
* `ItemTargetSelectionService` 负责“点击武器后等待选择敌人”的状态。
* `CombatSystem` 只保留战斗回合和胜负推进。

### 5.3 后续方向

物品使用逻辑最终应进一步数据驱动：

* 直接 payload，如 Heal / RestoreSAN / Shield，可以逐步迁入效果系统。
* UI 不判断物品能不能用，只调用 `ItemUseService.TryUseItem(...)` 并展示失败原因。
* `ConfigValidator` 校验手动使用物品是否具备可执行 payload 或 effect。

### 5.4 A1 设计卡

```text
功能名称：ItemUseService 独立
系统归属：Items / ItemUseService
状态归属：HP、SAN、AP、护盾仍归战斗对象或领域对象；物品消耗和背包位置仍归 BackpackGrid / 背包服务
涉及配置：Item 使用条件、EffectID、payload、目标类型
核心 API：TryUseItem(context, item, target, out reason)
事件通知：物品消耗、属性变化、战斗日志、UI 刷新事件
UI 边界：UI 只发起使用请求并展示 reason，不判断规则
扩展点：EffectFactory、ItemUseContext、ItemTargetSelectionService
ConfigValidator：校验可手动使用物品存在可执行 payload 或 Effect
测试覆盖：战斗武器、战斗消耗品、安全屋消耗品、失败原因
文档位置：本文件 + 后续 Items 系统文档
提交边界：先移动文件保持行为不变，再逐步拆目标选择与效果执行
```

## 6. 背包交互服务化

### 6.0 当前落地状态

已完成 A1A 第一版：

* `BackpackGrid` 新增 `BackpackPlacementResult` / `BackpackPlacementFailure`，放置校验不再只返回 bool，而是返回旋转、占格列表与失败原因。
* 物品旋转统一按 `0/90/180/270` 规范化，旋转后的 shape 会重新归一到左上 `(0,0)`，避免负坐标导致误判越界。
* `InventoryInteractionService` 统一承接 `RequestPickUp`、`RequestPlace`、`RequestRestore`、`RequestStageDiscard`、`PreviewPlacement`、`RequestRotateHeldItem`。
* `RequestRotateHeldItem` 只允许拖拽拿起后的物品旋转，避免直接修改仍在背包矩阵中的物品导致状态不同步。
* `DraggableItemUI` 支持拖拽中按 `R` 旋转，取消拖拽会恢复原坐标和原旋转。
* `GridSlotUI` 的拖拽预览改为消费 `InventoryInteractionService.PreviewPlacement()`，合法/非法高亮与真实放置共用同一套规则。
* 成功放置后仍统一触发 `GridSolver.RecalculateAllEffects()` 与 `GameEventBus.PublishItemPlaced()`，保证相邻、方向、光环、被动链路立即刷新。
* `DraggableItemUI` 点击使用时不再执行历史“失联物品自动修复”。如果 UI 物品不在当前背包网格中，只记录警告并停止使用，避免 UI 悄悄改写真实背包状态。

已验证：

```text
dotnet build UnityClient/Assembly-CSharp.csproj --no-restore
Unity batchmode -executeMethod InventoryInteractionServiceSmokeTest.Run
Unity batchmode -executeMethod CombatLootDropTest.Run
```

后续收口：

* 战利品拾取、安全屋整理、非战斗背包整理已共享拖拽服务入口，并已通过 `InventoryPresentationController` 统一背包显示与同步边界。
* 旋转输入当前为拖拽中的 `R` 键，后续可接入输入配置或 UI 按钮，但不改变领域规则入口。
* 背包 UI 尺寸和布局仍需继续收口到 `InventoryDisplaySpec` / `InventoryLayoutProfile`，避免不同界面散落硬编码。

### 6.1 当前问题

`DraggableItemUI` 已通过 `InventoryInteractionService` 承接拿起、放置、恢复、暂存丢弃和旋转，历史“自动修复失联物品”逻辑已删除。当前仍需关注的是：UI 可以持有拖拽中的临时显示态，但真实背包状态必须始终由 `BackpackGrid` 与交互服务维护。

风险：

* UI 拖拽过程中的临时显示态如果没有通过服务恢复，可能表现为“显示在 UI 上，但后端不承认”的异常。
* 战利品拾取、地图背包整理、安全屋整理必须继续复用同一套服务入口，不能重新分叉各自的拿起 / 放下 / 丢弃规则。
* 禁止恢复 UI 自动修复真实状态；状态不同步应通过日志、Validator 和 smoke test 定位生命周期源头。

### 6.2 已落地服务

当前服务位置：

```text
UnityClient/Assets/Scripts/Inventory/
    InventoryInteractionService.cs
```

当前核心 API：

```csharp
public bool RequestPickUp(ItemEntity item, InventoryInteractionContext context, out string reason);
public bool RequestPlace(ItemEntity item, int x, int y, InventoryInteractionContext context, out string reason);
public bool PreviewPlacement(ItemEntity item, int x, int y, InventoryInteractionContext context, out BackpackPlacementResult result, out string reason);
public bool RequestRotateHeldItem(ItemEntity item, int rotationDelta, InventoryInteractionContext context, out int newRotation, out string reason);
public bool RequestStageDiscard(ItemEntity item, InventoryInteractionContext context, out string reason);
public bool RequestConfirmDiscardStagedItems(InventoryInteractionContext context);
public bool RequestCancelDrag(ItemEntity item, InventoryInteractionContext context);
```

### 6.3 约定

* UI 只发起请求，不直接调用 `grid.RemoveItem()` 或 `grid.PlaceItem()`。
* UI 预览不得自行推导占格，必须使用 `PreviewPlacement()` 返回的 `OccupiedCells`。
* 旋转只允许发生在“已拿起”的交互态，提交放置时由服务把旋转写回 `BackpackGrid`。
* 背包状态变化统一由服务发布 `GameEventBus.PublishItemPlaced/Removed`。
* 结算界面和地图背包整理可以共享“移出背包后关闭时销毁”的规则。
* UI 层不得重新引入“失联物品自动修复”；所有状态不同步问题都应暴露为日志、测试或 Validator 问题。

### 6.4 A1 设计卡

```text
功能名称：InventoryInteractionService
系统归属：Inventory / 背包交互服务
状态归属：BackpackGrid 是真实格子状态；UI 只持有拖拽中的显示状态
涉及配置：背包上下文规则、是否允许暂存丢弃、是否允许战利品进入背包
核心 API：RequestPickUp / RequestPlace / RequestStageDiscard / RequestConfirmDiscard / RequestCancelDrag
事件通知：GameEventBus.PublishItemPlaced / PublishItemRemoved
UI 边界：DraggableItemUI 只发起请求，不直接 RemoveItem / PlaceItem
扩展点：InventoryInteractionContext、不同界面规则策略
ConfigValidator：校验关键背包 UI 与格子规格，后续校验上下文配置
测试覆盖：拖拽、放回、失败恢复、丢弃确认、战利品拾取
文档位置：本文件 + 后续 InventoryInteractionService 文档
提交边界：服务 API 已接入；后续提交聚焦布局配置化、更多 smoke test 与输入配置化
```

## 7. Runtime Fallback UI 收口

### 7.1 当前问题

当前 `GameFlowController` 和 `HUDController` 中仍有较多运行时创建 UI 的逻辑，例如动态创建战利品面板、结算面板、敌人卡片、状态条等。

这在白盒验证阶段很有价值，但当真实 UI 资源开始接入后，运行时拼界面会带来几个问题：

* 美术层级和程序层级不一致。
* UI 样式调整需要改 C#。
* 缺失引用时自动创建 fallback，可能掩盖场景配置错误。
* 更难检查 raycastTarget、CanvasGroup、sorting、anchor 是否符合规范。

### 7.2 建议策略

正式版纵切路径：

* UI 面板应由场景对象或 Prefab 提供。
* Controller 只负责绑定字段、刷新数据、注册按钮事件。
* 缺少关键 Controller 或字段时，`ConfigValidator` 或 Editor 校验应报错。

历史兜底收口路径：

* 现存 fallback UI 在移除前必须集中到 `RuntimePanelFallbackFactory`。
* 由显式开关控制，例如 `allowRuntimeFallbackPanels`。
* fallback 只用于历史功能回归和开发验证，不作为正式验收路径；新增正式功能不得新增散落 fallback。

### 7.3 A1 设计卡

```text
功能名称：Runtime fallback UI 收口
系统归属：UI Infrastructure / RuntimePanelFallbackFactory
状态归属：fallback 只负责临时表现对象，不拥有玩法状态
涉及配置：allowRuntimeFallbackPanels 开关、正式模式校验规则
核心 API：CreateCombatLootPanel / CreateSettlementPanel 等集中入口
事件通知：无领域事件，只暴露日志和校验错误
UI 边界：正式 Controller 绑定已有层级；fallback 不进入正式验收路径
扩展点：新增临时面板必须走工厂和开关
ConfigValidator：正式模式缺关键 UI 字段时 error
测试覆盖：fallback 开关开/关、正式模式缺引用报错
文档位置：本文件 + 14_Unity运行时美术自动验收方案.md
提交边界：先集中工厂，再接开关，最后逐步替换正式 UI
```

## 8. 背包 UI 布局配置化

### 8.1 当前问题

背包 UI 布局配置化已完成第一步收口：

* 新增 `InventoryDisplaySpec`，统一承接格子尺寸、格子间距、物品占格尺寸、拖拽抓取格偏移、背包底盘 padding 和各界面布局 profile。
* `DraggableItemUI` 不再自行写死 `100f` 计算物品尺寸和拖拽偏移。
* `InventoryPresentationController` 不再自行维护格子尺寸、间距和各界面背包位置，而是读取 `InventoryDisplaySpec.ResolveLayoutProfile()`。
* `GridGenerator` 和 `MVPEditorSetup` 已统一通过 `InventoryDisplaySpec.ApplyGridLayout()` 初始化 GridLayoutGroup，避免运行时和编辑器骨架默认值分叉。
* 新增 `InventoryGridLayoutAssetValidator` Editor 工具，扫描 Prefab / Scene 中 `GridGenerator.gridParent` 的 `GridLayoutGroup` 默认值是否符合 `InventoryDisplaySpec`，并提供手动修复菜单。
* `InventoryGridLayoutAssetValidatorTest` 已通过 Unity 自动测试守护执行，当前扫描到 1 个背包网格资产/场景目标并通过。
* 运行时美术验收中的背包格尺寸检查不再写死 `100x100` 文案，而是读取同一份规格。

仍需继续收口：

* `InventoryDisplaySpec` 当前仍是代码规格入口，尚未提升为可由资产配置的 `InventoryLayoutProfile`。
* 工坊、战斗、战利品、安全屋、地图背包的 anchoredPosition 已集中，但仍需要和 Formal V1 UI active 规格继续对齐。
* 已新增 `tools/agent/Invoke-UnitySmokeTests.ps1`，把 `InventoryInteractionServiceSmokeTest`、`InventoryDisplaySpecSmokeTest` 和 `InventoryGridLayoutAssetValidatorTest` 纳入复制程序智能体可一键执行的 Unity smoke test 入口。

这些值已经和美术侧 DisplaySpec 产生交集，后续如果 UI 重新设计，应先调整 profile / 规格入口，再由表现层统一消费。

### 8.2 建议方案

短期：

* 继续让新增背包 UI 只消费 `InventoryDisplaySpec`，不要新增局部常量。
* 继续让 `InventoryInteractionServiceSmokeTest`、`InventoryDisplaySpecSmokeTest` 和 `InventoryGridLayoutAssetValidatorTest` 通过 `tools/agent/Invoke-UnitySmokeTests.ps1` 作为 A1A 背包交互与表现回归入口。
* 后续新增背包交互 smoke test 时，优先追加到 `Invoke-UnitySmokeTests.ps1` 默认测试清单，避免散落手动触发命令。

中期：

* 使用 `InventoryLayoutProfile` ScriptableObject 管理不同界面的背包布局。
* 通过 screen state 查询布局，而不是 switch 中写死坐标。
* 背包玩法占格尺寸和美术图标展示尺寸继续分离。

## 9. 深渊生成策略继续配置化

### 9.1 当前问题

当前深渊层生成已支持 `NodePool`、`EndNode`、节点类型配置，但仍存在程序规则：

* 线性路径固定。
* `ExpectedNodeCount - 1` 个随机节点后固定追加 Boss。
* Boss 通过 `BossNode` 字段固定创建为 `CombatNode`。
* EndNode 再追加为层末特殊节点。

这符合历史 MVP 阶段的单线验证目标，但后续如果要做“无 Boss 层”“多 Boss 层”“事件层”“分支路线”，这些规则会继续挤进 `DungeonLayer.GenerateMapTree()`。

### 9.2 建议方案

可以在 dungeon JSON 中逐步引入生成策略：

```json
{
  "LayerID": 1,
  "GenerationPolicy": "LinearWithBossAndEnd",
  "MainPathNodeCount": 3,
  "BossNodeEntry": {
    "NodeType": "CombatNode",
    "MonsterIDs": ["elite_scrap_guard"],
    "NodeIconID": "node_boss_icon"
  },
  "EndNode": {
    "NodeType": "StairsNode"
  }
}
```

程序侧新增 `DungeonMapGenerator`：

* `DungeonManager` 负责加载层和流程推进。
* `DungeonMapGenerator` 负责根据配置生成节点图。
* `NodeFactory` 继续负责节点实例化。

## 10. ConfigManager 抽象

### 10.1 当前问题

`ConfigManager` 目前是全静态字典，简单易用，但新系统越来越多后会出现：

* 任意代码都能直接读取全局配置。
* 测试隔离较弱。
* 后续热重载、多套配置、存档版本迁移不方便。
* 无法清晰表达“配置只读”。

### 10.2 建议方案

短期不需要大改，可以新增只读访问层：

```csharp
public sealed class ConfigDatabase {
    public IReadOnlyDictionary<string, ItemEntity> Items { get; }
    public IReadOnlyDictionary<string, MonsterEntity> Monsters { get; }
    public IReadOnlyDictionary<int, DungeonConfig> Dungeons { get; }
}
```

过渡方式：

* `ConfigManager` 继续负责加载。
* `CoreBackend` 持有当前 `ConfigDatabase`。
* 新代码优先依赖 `ConfigDatabase` 或服务接口。
* 老代码逐步减少直接访问 `ConfigManager.StaticDict`。

## 11. ConfigValidator 强化方向

当前 `ConfigValidator` 已经是项目很重要的质量门禁，建议继续扩大职责，但要保持它只做校验，不做运行时修复。

建议新增校验：

* 关键 UI 面板是否存在并挂载正确 Controller。
* `GameFlowController` 关键字段是否绑定。
* 正式模式下是否禁止 runtime fallback panel。
* 所有手动使用物品是否有可执行 payload 或 effect。
* 所有 `VisualID` 是否存在于 registry，必要项缺失时从 warning 升级为 error。
* 所有旧字段残留是否直接 error，不保留兼容路径。
* 所有可配置枚举是否能解析，禁止业务逻辑散落裸字符串判断。

## 12. 事件订阅生命周期

### 12.1 当前问题

部分非 `MonoBehaviour` 类通过构造函数订阅事件，并尝试在析构函数中取消订阅。C# 析构函数执行时机不稳定，Unity 环境下更不适合作为事件生命周期保障。

### 12.2 建议方案

* 对纯 C# 系统提供显式 `Dispose()` 或 `Shutdown()`。
* `CoreBackend.InitAllSystems()` 之前统一 reset event bus，目前已有这个方向。
* `CoreBackend` 后续如果支持重启、读档或测试多次初始化，应显式释放旧系统事件订阅。
* `EventBus` 可提供 listener count debug，用于测试后检查是否泄漏。

## 13. 推荐落地顺序

### 第一步：低风险文件移动

* 将 `ItemUseService` 移出 `CombatSystem.cs`。
* 新增 `Items/` 目录。
* 不改行为，只补引用和测试。

验收：

* `dotnet build UnityClient.sln` 通过。
* 战斗中武器使用、药水使用、安全屋使用仍正常。

### 第二步：背包交互服务

* 新增 `InventoryInteractionService`。
* `DraggableItemUI` 改为调用服务。
* 历史自动修复逻辑已删除，后续禁止 UI 悄悄修复真实背包状态。

验收：

* 背包拖拽、放回、丢弃、战利品拾取仍正常。
* UI 不再直接承担背包状态修复。

### 第三步：GameFlowController 瘦身

* 先拆 `InventoryPresentationController`。
* 再拆 `DungeonFlowPresenter`。
* 最后保留或替换 `GameFlowController` 为轻量 router。

验收：

* 界面切换不变。
* 背包层级和拖拽不被背景或遮罩阻挡。
* 战利品、结算、安全屋、阶梯流程正常。

### 第四步：真实 UI 路径收口

* fallback UI 集中管理并加开关。
* 正式场景缺关键 UI 时校验报错。
* Controller 只绑定和刷新，不负责大规模动态搭建。

验收：

* 美术 UI 资源替换不需要修改核心玩法代码。
* UI 缺引用能在开发期发现，而不是运行时静默创建临时面板。

## 14. 验收门禁

每个边界收口任务完成时，至少应检查：

* `dotnet build Assembly-CSharp.csproj` 通过。
* 涉及 Editor 或 Validator 时，`dotnet build Assembly-CSharp-Editor.csproj` 通过。
* 相关 smoke test 或现有自动化入口可运行。
* 涉及 UI/美术表现时，运行时美术验收报告保持 `PASSED`。
* `ConfigValidator` 能发现新增配置错误，不通过运行时 fallback 静默修复。
* 文档状态同步更新。
* 提交只包含当前任务相关文件，不混入其他 agent 的美术、配置或工具改动。

---

## 15. 禁止项与反例

后续代码中应尽量避免：

* 在 UI 脚本里直接修改 HP、SAN、金币、背包格子等领域状态。
* 在 `GameFlowController` 继续新增具体业务系统逻辑。
* 在业务逻辑里散落 `normalized == "SomeConfigString"`。
* 为了临时跑通长期保留新旧两套兼容路径。
* JSON 直接引用 Unity Sprite、Prefab 或场景对象。
* Runtime fallback UI 成为正式玩法路径。
* 用析构函数作为事件取消订阅的主要手段。
* 把配置缺失静默降级为默认行为，导致问题被隐藏。

---

## 16. 当前建议结论

下一阶段如果不做新功能，最值得优先推进的程序优化是：

```text
ItemUseService 独立
    -> InventoryInteractionService
    -> GameFlowController 瘦身
    -> Runtime fallback UI 收口
```

这条路线能最大程度降低后续接入“小镇独立 UI、义体制造 UI、战斗道具闭环、结算表现、更多美术 UI”的互相干扰风险，同时保持 MVP 已经跑通的核心体验不被大改打断。
