# 编程规范与架构约定

> **定位：** 本文档是项目程序开发的硬性约束。它规定功能实现前必须满足的架构设计、模块归属、扩展方式、配置校验与协作规范。
> **核心原则：** 功能范围可以逐步填充，但框架、归属、扩展边界和验证链路必须按正式版标准设计。任何实现都必须先明确框架归属和扩展边界，再进入代码落地。
> **更新时间：** 2026-05-22

---

## 0. 当前阶段口径

项目当前已从 MVP 验证切换到“正式版核心纵切”。后续程序开发以 [`版本规划/09_正式版核心纵切开发路线.md`](../../版本规划/09_正式版核心纵切开发路线.md) 为顶层路线。

这意味着：

* 新功能不再以“先补一个能跑的 MVP 口径”为目标，而是以正式版系统骨架为目标。
* 通过批次控制当前处理的系统和内容量，但进入当前批次的规则、接口、模块边界、Validator 和测试入口必须按正式版标准完成。
* 每个被推进的系统都应走完整纵切链路：规则、配置、领域逻辑、表现层、Validator、测试和文档。
* A1 程序侧重点是核心边界收口，让背包、物品、战斗、流程和表现层能在清晰边界上继续扩展。

如果旧 MVP 文档、旧实现习惯与本约定冲突，以当前 GDD、正式版纵切路线和本文档为准。

---

## 1. 总原则

本项目不是以“先能跑”为最高目标，而是以“可持续扩展的可玩闭环”为目标。

因此：

* 不能因为处于开发阶段，就绕过架构设计直接写业务代码。
* 不能因为当前只有一个用例，就把规则写死到总控类或 UI 类中。
* 不能因为 MVP 范围小，就降低模块边界、配置驱动、测试和校验要求。
* 任何新增机制都必须先回答：归属哪个系统、由谁持有状态、如何配置、如何扩展、如何验证。
* 不能把“当前只需要一个功能点”作为写死规则、跳过配置或跳过服务边界的理由。
* 功能可以小步实现，但代码落点必须是未来可扩展的正式框架落点。

推荐判断标准：

```text
如果这个逻辑未来可能被策划、数值、美术、UI 或其他 agent 继续扩展，
它就不能以硬编码形式散落在业务流程里，
必须进入明确的系统、配置、工厂、效果、奖励表、Action 或服务接口。
```

## 2. 功能开工前设计卡

每个非纯展示改动，在写代码前必须先形成最小设计卡。设计卡可以很短，但不能省略。设计卡既可以写入任务回复，也可以写入对应开发文档；涉及系统级能力时，必须沉淀到开发文档。

```text
功能名称：
系统归属：
状态归属：
涉及配置：
核心 API：
事件通知：
UI 边界：
扩展点：
ConfigValidator：
测试覆盖：
文档位置：
提交边界：
```

### 2.0 开工准入

以下情况不应直接开写代码：

* 找不到明确系统归属。
* 状态应该归领域层还是 UI 层说不清。
* 配置字段、枚举、工厂 key 或注册类型没有设计。
* 没有说明 Validator 如何发现配置错误。
* 没有说明至少一个 smoke test 或手动验收入口。
* 需要改多个系统但没有拆出提交边界。

如果功能本身很小，也可以用一句话设计卡完成准入，例如“归属 `RewardSystem`，调用方只配置 `RewardID`，Validator 校验奖励表存在，SmokeTest 覆盖保底与权重掉落”。

### 2.1 系统归属

必须明确功能属于哪个系统。

示例：

* 掉落生成归 `RewardSystem`。
* 怪物决策归 `MonsterActionAI`。
* 道具使用归 `ItemUseService`。
* 背包拖拽规则归 `InventoryInteractionService`。
* 深渊地图生成归 `DungeonMapGenerator` 或 `DungeonManager` 下的独立生成模块。
* 视觉资源映射归 `VisualAssetRegistry` 与 `VisualAssetService`。

如果找不到归属，不允许直接塞进 `GameFlowController`、`DungeonManager`、`CombatSystem` 或 UI Controller。应先补系统边界。

### 2.2 状态归属

必须明确哪个对象拥有真实状态。

* HP、SAN、AP、护盾属于领域对象或战斗对象。
* 背包格子、物品位置属于 `BackpackGrid` 或背包交互服务。
* 金币、仓库、已解锁层级属于 `PlayerProfile`。
* 当前深渊层、当前节点属于 `DungeonManager`。
* UI 只持有显示状态和交互中间状态，不持有玩法事实。

## 3. 分层约定

正式版纵切阶段的默认分层是：

```text
配置与数据
    -> 领域服务 / 规则解算
    -> 流程编排
    -> 表现层绑定与反馈
    -> 自动化验证与文档
```

领域层、编排层和表现层之间不应互相代替职责。

### 3.1 领域层

领域层必须尽量保持纯 C#。

允许：

* 数据实体。
* 系统服务。
* 解算器。
* 工厂。
* 配置解析。
* 事件发布。

不允许：

* 依赖具体 UI 对象。
* 依赖场景层级。
* 直接引用 Sprite、Prefab、Image、Button 等表现对象。
* 为了表现效果改变真实结算时序。

### 3.2 表现层

表现层负责显示、输入和动画。

允许：

* 调用后端公开 API。
* 监听 EventBus。
* 播放动画和音效。
* 根据 VisualID 请求资源。
* 展示失败原因。

不允许：

* 直接修改 HP、SAN、金币、背包格子、掉落归属等领域状态。
* 自己推导玩法规则。
* 在 UI Controller 中生成奖励、结算胜负、修改怪物 AI。
* 把缺失配置静默修复成另一套玩法逻辑。

### 3.3 编排层

`GameFlowController` 一类流程脚本只负责“何时切换到哪个界面”。它不应继续承载具体业务规则。

应避免：

* 在流程脚本里写背包摆放规则。
* 在流程脚本里写掉落生成。
* 在流程脚本里写物品效果。
* 在流程脚本里写 UI 大量动态创建细节。

当前 `GameFlowController` 仍承载较多历史职责，后续新增功能不得继续扩大它的业务范围。需要接入流程时，应优先考虑：

* 屏幕切换：`GameScreenRouter` 或等价路由器。
* 深渊流程事件：`DungeonFlowPresenter` 或等价流程表现器。
* 背包显示与同步：`InventoryPresentationController` 或等价表现控制器。
* 历史兜底 UI 收口：`RuntimePanelFallbackFactory` 或等价集中工厂。

### 3.4 并行 agent 协作边界

当程序开发 agent 与 UI/美术接入 agent 并行工作时，必须以系统边界拆分，而不是按“谁顺手改哪个文件”拆分。

功能开发 agent 负责：

* 领域模型与服务，例如 `BackpackGrid`、`InventoryInteractionService`、`RewardSystem`、`ItemUseService`、`CombatSystem`。
* 配置结构、Validator、测试和事件发布。
* 玩法规则的失败原因、回滚逻辑和状态一致性。

UI/美术接入 agent 负责：

* 表现控制器、Prefab、VisualID、UGUI 层级和资源绑定。
* 视觉反馈、动画、截图验收和 DisplaySpec 适配。
* 只读展示后端状态，不直接改写真实玩法状态。

共享边界必须稳定：

* 背包真实规则统一走 `InventoryInteractionService`。
* 背包显示和物品 UI 同步统一走 `InventoryPresentationController`。
* 流程切换由 `GameFlowController` 或后续路由器传递上下文，不承接具体规则和具体 UI 构建。
* 如果一个需求需要跨边界，先补接口或事件，再让另一侧消费，不允许直接跨层调用内部实现。

## 4. 配置驱动约定

### 4.1 内容规则默认配置化

以下内容必须优先由配置表达：

* 物品基础属性、占格、图标、效果。
* 怪物 HP、奖励、AI Actions。
* 深渊层、节点池、Boss、EndNode、背景。
* 奖励表、保底掉落、权重池、空掉落。
* 义体配方、成本、效果。
* 视觉资源 VisualID。

代码负责机制，配置负责内容。

### 4.2 JSON 字符串与运行时类型

JSON 中可以使用字符串，保证策划和 agent 可读。

运行时不允许在业务逻辑里散落裸字符串判断。字符串必须集中解析为：

* enum。
* 注册类型。
* 工厂 key。
* Validator 可检查的 ID。

示例：

```text
允许：MonsterActionConfigParser.TryParseTarget(...)
避免：normalized == "RandomPlayerWeapon" 分散在多个业务类里
```

### 4.3 不保留双轨兼容

当项目决定把某个系统迁移到新架构时，应同批完成：

* 数据结构迁移。
* JSON 配置迁移。
* 运行时代码迁移。
* Validator 校验更新。
* 测试更新。
* 文档状态更新。

不应长期保留新旧两套运行路径。若迁移有风险，应通过分支、提交和测试控制风险，而不是在主代码中维护双轨逻辑。

## 5. 扩展点约定

新增机制应优先接入已有扩展点。

### 5.1 物品效果

新增物品或义体效果时：

* 优先新增 `EffectBase` 实现。
* 通过 `EffectFactory` 注册或发现。
* 在 JSON 中配置 `EffectID` 和参数。
* 在 `ConfigValidator` 中校验参数合法性。

不应为某个具体物品在 `CombatSystem`、`GridSolver` 或 UI 中写特殊分支。

### 5.2 奖励与掉落

新增奖励来源时：

* 调用方只配置 `RewardID`。
* 具体保底、权重、空掉落、奖励组合由 `RewardSystem` 解析。
* 调用方只决定奖励流向，例如拾取面板、背包、金币、任务结算。

不应在怪物、节点、事件或 UI 中直接写随机掉落逻辑。

### 5.3 怪物行为

新增怪物行为时：

* 普通攻击、技能、背包干涉都应表达为 `MonsterAction`。
* 决策逻辑属于 Selector。
* 目标选择属于 TargetSelector。
* 行为执行属于 Action。
* 配置合法性属于 `ConfigValidator`。

不应把怪物行为写进 `CombatSystem.StartEnemyTurn()`。

### 5.4 深渊节点

新增节点类型时：

* 新增 `NodeBase` 派生类。
* 通过 `NodeFactory` 创建。
* 由 dungeon JSON 配置节点类型和参数。
* UI 只根据节点数据展示和请求进入。

不应在地图 UI 或 `DungeonManager` 中用硬编码判断具体节点功能。

### 5.5 视觉资源

新增美术资源时：

* JSON 只配置 `VisualID`。
* Unity 资源引用放在 `VisualAssetRegistry`。
* 表现层通过 `VisualAssetService` 获取资源。
* 缺资源由校验和 fallback 图暴露，不影响玩法核心测试。

JSON 不直接引用 Sprite、Prefab、AudioClip 或场景对象。

## 6. UI 开发约定

### 6.1 UI 不拥有玩法事实

UI 可以：

* 展示背包物品。
* 发起拖拽请求。
* 展示战利品。
* 展示小镇卖出界面。
* 展示义体制造界面。

UI 不可以：

* 自己决定物品是否进入背包。
* 自己销毁真实物品数据。
* 自己生成掉落。
* 自己修改金币。
* 自己判定战斗胜负。

### 6.2 Controller 只做绑定和刷新

正式 UI 接入后，Controller 应以绑定已有层级为主。

推荐：

* 面板结构由场景或 Prefab 提供。
* Controller 负责字段绑定、事件注册、刷新显示。
* 大规模布局和组件创建不写在业务 Controller 中。

运行时 fallback UI 不应成为正式路径。现存 fallback 在完全移除前只允许作为历史债务集中收口，应满足：

* 由集中工厂创建，不散落在业务 Controller。
* 由显式开关控制。
* 正式验收路径缺少关键 UI 时应报错，而不是静默创建临时面板。
* 运行时美术验收需要能暴露层级、遮罩、Raycast 和 VisualID 问题。
* 新增正式功能不得新增散落 fallback。

### 6.3 背包玩法尺寸与视觉尺寸分离

背包占格由 `ItemGridComponent.Shape` 和 `BackpackGrid` 决定。

视觉图标只影响显示，不影响：

* 占用格子。
* 可放置性。
* 旋转碰撞。
* 战斗效果。

## 7. ConfigValidator 约定

每新增一个可配置系统，必须同步补校验。

Validator 应检查：

* ID 是否存在。
* enum 或注册类型是否可解析。
* 参数是否合法。
* 引用资源是否存在。
* 旧字段是否残留。
* 必要 UI 或 VisualID 是否缺失。
* 配置组合是否互相兼容。

Validator 不负责修复配置。它只负责暴露问题。

---

## 8. 测试约定

每个新系统至少需要 smoke test。

核心逻辑应能 headless 验证：

* 奖励生成。
* 怪物行动。
* 道具使用。
* 背包放置。
* 深渊层级推进。
* 战败和撤离结算。
* 配置合法性。

手动 Unity 测试可以作为体验验证，但不能替代核心逻辑测试。

正式版纵切阶段，测试不仅用于证明“能跑”，还要作为系统质量门禁。涉及配置、奖励、怪物行为、物品生命周期、深渊层级推进、UI/美术接入的改动，应同步考虑：

* `ConfigValidator` 是否能暴露错误配置。
* headless smoke test 是否能覆盖核心规则。
* 运行时美术验收是否需要新增截图或检查项。
* 文档是否更新当前落地状态。

---

## 9. 文档约定

系统级功能必须有文档落点。

文档需要说明：

* 系统定位。
* 数据结构。
* 配置格式。
* 运行时流程。
* 扩展方式。
* Validator 规则。
* 测试建议。
* 当前落地状态。

代码落地后，应更新文档状态，避免文档只停留在设计稿。

---

## 10. Git 与协作约定

* 一个完整任务完成后建议提交 commit。
* 不把无关文件混入提交。
* 不回退其他人或其他 agent 的改动，除非明确要求。
* 发现已有未提交改动时，先判断是否与当前任务相关。
* 如果任务会大范围重构，应先拆出安全边界，再分阶段提交。

---

## 11. 禁止项

以下做法原则上禁止：

* 以开发阶段为理由跳过架构归属设计。
* 在 UI 脚本里直接修改领域状态。
* 在总控类里继续堆具体业务规则。
* 为单个内容写死特殊逻辑。
* 在业务代码里散落裸字符串判断。
* JSON 直接引用 Unity 对象。
* 长期维护新旧两套运行路径。
* 缺配置时静默改成另一套默认玩法。
* 只手测、不补核心逻辑测试。
* 代码改了但文档不更新。

---

## 12. 最终约定

本项目程序开发的默认路径是：

```text
先确定系统归属
    -> 设计数据结构和扩展点
    -> 补配置和 Validator
    -> 实现领域逻辑
    -> 接表现层
    -> 补测试
    -> 更新文档
```

任何功能如果无法说清楚上述路径，就不应直接进入代码实现。

A1 的程序执行优先级是：

```text
ItemUseService 独立
    -> InventoryInteractionService
    -> GameFlowController 瘦身
    -> Runtime fallback UI 收口
```

后续新增系统原则上必须在这条边界收口路线之上继续扩展，而不是继续扩大历史总控脚本或 UI 脚本的职责。
