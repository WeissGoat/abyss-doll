# 程序开发规范目录入口

`rules/` 只放长期有效的程序硬约束和协作约定，不放具体功能需求、不记录实现进度。具体系统如何实现，回到 `开发文档/` 根目录的系统文档、GDD、配置文档和状态页。

## 阅读顺序

| 顺序 | 文档 | 只负责回答 |
|---|---|---|
| 00 | `00_程序开发总规则.md` | 开工前必须满足什么门禁，哪些行为禁止，功能如何进入正式框架。 |
| 01 | `01_客户端分层与领域架构规范.md` | 领域层、CoreBackend、事件总线、工厂和扩展点如何分层。 |
| 02 | `02_Unity表现层与编辑器构建规范.md` | UGUI、场景 / Prefab / Editor 构建、表现层输入和射线边界如何做。 |
| 03 | `03_视觉资源系统程序开发规范.md` | VisualID、VisualAssetRegistry、VisualAssetService、DisplaySpec 和美术资源接入契约。 |
| 04 | `04_自动化测试与验收流程规范.md` | AutoTestDaemon、`.test_trigger`、headless smoke test 和验收报告如何使用。 |

## 职责边界

- 总规则只写所有程序工作都必须遵守的准入、红线和协作约束，不展开具体系统细节。
- 架构规范只写客户端分层和领域系统扩展方式，不重复 UI 资源尺寸、截图验收和测试触发流程。
- Unity 表现层规范只写运行时 UGUI、Prefab / 场景 / Editor 构建和表现层交互边界，不写玩法规则。
- 视觉资源规范只写程序如何消费 Approved 资源和 VisualID，不记录美术生产流程。
- 自动化测试规范只写测试框架、触发方式、报告和测试编写规则，不替代具体系统 smoke test 需求。测试规范强调业务行为和验收场景，不鼓励围绕内部实现碎片写过细测试。

## 使用规则

- 开发新功能前，先读 `00_程序开发总规则.md`，用最小设计卡确认系统归属、状态归属、配置、Validator、测试和文档落点。
- 涉及领域架构或新扩展点时，再读 `01_客户端分层与领域架构规范.md`。
- 涉及 Unity UI、Prefab、场景或 Editor 构建时，再读 `02_Unity表现层与编辑器构建规范.md`。
- 涉及美术资源、VisualID 或 DisplaySpec 时，再读 `03_视觉资源系统程序开发规范.md`。
- 涉及自动化验证、Unity smoke test 或验收报告时，再读 `04_自动化测试与验收流程规范.md`。

## 维护规则

- 如果某条规范只对一个系统有效，应写入对应系统开发文档，而不是写进 `rules/`。
- 如果某条规范会影响所有程序 agent 的开工方式、架构边界或提交流程，优先写入 `00_程序开发总规则.md`。
- 如果发现两份规则文档描述同一件事，以更靠前的文档定义“原则”，靠后的专项文档只保留“落地方式”。
