# 程序开发总规则

本文是所有程序工作的通用门禁，只规定“必须遵守什么”和“不能越过什么边界”。具体怎么分层看 `01_客户端分层与领域架构规范.md`，Unity UI 怎么落地看 `02_Unity表现层与编辑器构建规范.md`，美术资源怎么接看 `03_视觉资源系统程序开发规范.md`，测试怎么跑看 `04_自动化测试与验收流程规范.md`。

## 1. 当前阶段口径

项目当前以正式版核心纵切为目标。功能范围可以分批填充，但进入当前批次的系统边界、数据结构、配置、Validator、测试入口和文档落点必须按正式框架设计。

- 不以“先能跑”为最高目标，而以“可扩展、可验证、可继续协作的可玩闭环”为目标。
- 不因为当前用例少，就把规则写死在 UI、流程脚本或临时总控类里。
- 不长期保留新旧双轨运行路径；迁移应同批更新配置、代码、Validator、测试和文档。
- 旧 MVP 文档或旧实现习惯与当前 GDD、正式纵切路线、本规则冲突时，以当前事实源为准。

## 2. 开工门禁

任何非纯展示改动，在写代码前必须能回答下面的最小设计卡。设计卡可以写在任务回复、开发文档或系统需求文档里，但系统级能力必须沉淀到文档。

```text
功能名称：
系统归属：
状态归属：
涉及配置：
核心 API：
事件通知：
UI 边界：
扩展点：
ConfigValidator：
测试覆盖：
文档位置：
提交边界：
```

以下情况不应直接写代码：

- 找不到明确系统归属。
- 真实状态属于领域层还是 UI 层说不清。
- 配置字段、枚举、工厂 key、注册类型或扩展点没有设计。
- 没有说明 Validator 如何暴露错误配置。
- 没有至少一个 smoke test、自动验收或明确人工验收入口。
- 需要跨多个系统但没有拆出提交边界和接口边界。

## 3. 通用分层红线

默认链路是：

```text
配置与数据 -> 领域服务 / 规则解算 -> 流程编排 -> 表现层绑定与反馈 -> 自动化验证与文档
```

- 领域层拥有玩法事实，尽量保持纯 C#，不依赖具体 UI、场景、Sprite、Prefab、Image 或 Button。
- 编排层只负责流程切换、上下文传递和调用公开 API，不承载具体玩法规则。
- 表现层只负责显示、输入、动画和失败原因展示，不直接修改 HP、SAN、金币、背包格子、掉落归属、怪物 AI 或结算结果。
- 配置负责内容，代码负责机制。JSON 可以保留可读字符串，但运行时业务逻辑不得散落裸字符串判断，应集中解析为 enum、注册类型、工厂 key 或 Validator 可检查的 ID。
- 新扩展优先进入现有扩展点：Effect、Reward、MonsterAction、Node、VisualID、领域服务或工厂，而不是塞进总控、流程或 UI Controller。

## 4. 系统归属规则

找不到归属时先补系统边界，不允许直接塞进 `GameFlowController`、`DungeonManager`、`CombatSystem` 或 UI Controller。

- 掉落生成归 `RewardSystem`。
- 怪物决策归怪物 AI / Action 系统。
- 道具使用归 `ItemUseService` 或等价物品服务。
- 背包交互规则归 `InventoryInteractionService`。
- 深渊地图生成归地图生成模块或 `DungeonManager` 下的独立生成服务。
- 视觉资源映射归 `VisualAssetRegistry` 与 `VisualAssetService`。
- 玩家长期资产、金币、仓库、解锁层级归 `PlayerProfile` 或等价局外状态容器。

## 5. 配置与 Validator

每新增一个可配置系统，必须同步考虑 Validator。

Validator 应检查：

- ID 是否存在。
- enum、工厂 key 或注册类型是否可解析。
- 参数范围是否合法。
- 跨表引用是否存在。
- 旧字段是否残留。
- 必要 VisualID、UI 入口或资源引用是否缺失。
- 配置组合是否互相兼容。

Validator 不负责修复配置，只负责暴露问题。缺配置时不得静默改成另一套默认玩法。

## 6. 测试与验收

每个新系统至少需要一个 smoke test、自动验收或明确人工验收证据。核心逻辑应优先支持 headless 验证。

优先覆盖：

- 配置合法性。
- 领域规则成功 / 失败路径。
- 失败回滚和失败原因。
- 关键事件是否发布。
- UI 是否只调用公开 API，不直接改真实状态。
- 美术 / VisualID 接入是否有运行时验收覆盖。

手动 Unity 测试可以作为体验验证，但不能替代核心逻辑测试。

## 7. 文档与状态

系统级功能落地后必须更新对应文档和状态页。

- 通用规则变更写入 `rules/`。
- 具体系统 API、状态机、配置字段、Validator、测试样例写入 `开发文档/` 对应系统文档。
- 策划规则和配置意图写入 GDD / 配置文档。
- 美术资源和 UI 规格写入美术文档。
- 完成后回写 `agent_status/program.md`；影响阶段、跨职能交接或阻塞项时同步 `PROJECT_STATUS.md`。

## 8. Git 与协作

- 只提交与当前任务相关的文件。
- 不回滚他人或其他 agent 的无关改动。
- Unity 资产移动必须同步移动 `.meta`。
- 大范围重构应拆出安全边界并分阶段提交。
- 并行 agent 协作时按系统边界拆分，不按“谁先碰哪个文件”拆分。

## 9. 禁止项

- 以开发阶段为理由跳过架构归属设计。
- 在 UI 脚本里直接修改领域状态。
- 在流程总控里继续堆具体玩法规则。
- 为单个内容写死特殊逻辑。
- 在业务代码里散落裸字符串判断。
- JSON 直接引用 Unity 对象。
- 长期维护新旧两套运行路径。
- 缺配置时静默补另一套默认玩法。
- 只手测、不补核心逻辑测试。
- 代码改了但文档和状态页不更新。
