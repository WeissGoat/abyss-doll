# 自动化测试与验收流程规范

> 定位：本文只规定程序自动化测试和验收工具链，包括 smoke 测试的 Unity Test Framework 包装与 MCP `run_tests` 运行、兼容路径 AutoTestDaemon / `.test_trigger`、报告读取、测试编写规则和里程碑发布门禁。具体系统应该测什么，由对应系统开发文档或需求文档定义。

---
## 一、 工作流与工程化思维 (Workflow & Engineering)

### 1. 自动化优先与 TDD (Auto-Agentic Workflow)
*   **先验灵魂，再塑肉体**：在没有 UI 甚至是场景的情况下，必须先编写纯底层的单元测试 / 冒烟测试（Smoke Test）。
*   **自动化闭环**：AI 写码后用 Unity MCP 编译并运行 smoke 测试（`refresh_unity` -> `run_tests` -> `get_test_job`），零人工干预；没有 MCP 时由“幽灵探针” AutoTestDaemon 监听 `.test_trigger` 完成同样的闭环。只要底层逻辑（测试用例）没跑绿，绝不推进表现层。

### 2. 编辑器工具化 (Editor Automation)
*   **代码生成 UI**：极度反感在 Unity Inspector 中手动拖拽、连线、对齐 UI 预制体。
*   **幂等性构建**：倾向于编写极其硬核的 Editor 扩展（如 `MVPEditorSetup.cs`），一键 `DestroyIfExists` 并通过纯 C# 代码动态生成整个界面的层级树 (Hierarchy)、挂载组件和绑定引用。做到随时可推翻、随时可重建。

### 3. 务实的技术选型 (Pragmatic Tech Choices)
*   **实用主义至上**：不盲目追求新技术。例如在发现 UI Toolkit 在处理重度网格物理拖拽和射线穿透（Raycast）存在深层缺陷时，能够立刻果断止损，全局回退并统一使用经过验证的传统 `UGUI`，避免无谓的内耗。

---

## 二、 框架概述 (Overview)

在传统的 Unity 开发中，测试业务逻辑往往需要“编写代码 -> 挂载到 GameObject -> 点击 Play -> 观看动画 -> 查阅 Console”。这种流程极度消耗时间，且容易将底层数值 Bug 与前端表现 Bug 混淆。

2026-10-02 起，smoke 测试的主路径是 Unity Test Framework：`UnityClient/Assets/Editor/P3SmokeTests/` 的 `P3.SmokeTests.Editor` 程序集把每个测试包成 EditMode 用例，由 Unity MCP `run_tests` 运行，见第五节。下文第三节的 AutoTestDaemon 保留为没有 MCP 时的兼容路径；第四节的无头降级两条路径共用。

为此，我们开发了 **“幽灵探针 (AutoTestDaemon)”**。它是一个常驻在 Unity 编辑器后台的无头 (Headless) 测试框架。它的核心使命是：**在没有任何场景、没有任何 UI、时间静止的情况下，以毫秒级的速度瞬间推演完极其复杂的 C# 后端系统逻辑，并输出结构化的体检报告。**

---

## 三、 核心架构与工作原理 (Architecture & Mechanics)

该框架的运转基于一条极其精妙的五步自动闭环：

1.  **静默监听 (File Watcher)**：
    驻留在 `Scripts/Editor/` 的 `AutoTestDaemon.cs` 利用 C# 的 `FileSystemWatcher`，死死盯住外部文件 `Logs/.test_trigger`。
2.  **外部触发 (CLI Trigger)**：
    AI 或开发者在外部命令行（PowerShell）中，将需要测试的类名与方法名（例如：`BackendSmokeTest.Run`）写入该触发文件。
3.  **强制重载 (Auto Compile)**：
    探针一旦监听到文件变更，立刻在主线程调用 `AssetDatabase.Refresh()`。这会强制 Unity 编译刚刚由 AI 写入的最新业务代码和测试脚本。
4.  **反射执行与拦截 (Reflection & Intercept)**：
    利用 `[DidReloadScripts]` 钩子，编译完成后探针瞬间苏醒。它通过 `System.Reflection` 动态定位到测试方法并执行。在此期间，探针会接管 `Application.logMessageReceived`，**全量拦截**所有的 `Debug.Log`、`LogWarning` 以及致命的 `Exception` 空指针。
5.  **生成体检报告 (Report Generation)**：
    测试跑完后，探针将截获的所有日志组合成一段 JSON 格式的数据，落地到 `Logs/TestReport.json`，并标记状态为 `PASSED` 或 `FAILED`。外部的 AI 读取该文件后，即可决定是继续开发，还是根据错误堆栈进行代码自愈。

## 四、 表现层降级机制 (The Headless Fallback)

测试框架最棘手的问题在于**“时间流逝”**。在实机游戏中，战斗表现队列 (`VisualQueue`) 会让一个火球飞 0.5 秒再扣血。如果在测试里也等 0.5 秒，测试效率将极其低下。

**降级原理：**
在 `VisualQueue.cs` 中，我们定义了全局静态变量 `public static bool IsHeadless = true;`。
*   当实机游戏启动（`GameFlowController` 或 `VisualQueueRunner` 运行）时，会将此值设为 `false`，开启排队缓冲。
*   但在探针跑测试时，没有任何 MonoBehaviour 会运行，该值保持 `true`。此时，`VisualQueue` 在接收到任何表现指令时，**会直接 `while (enumerator.MoveNext()) { }` 将内部的协程瞬间同步跑完**。这保证了即使底层逻辑中夹杂了 UI 表现代码，测试依然能在 1 毫秒内出结果。

## 五、 自动化测试流程 (SOP: Standard Operating Procedure)

当需要开发一个新系统（如：复杂的深渊掉落算法）时，标准流程如下：

### Step 1: 编写测试用例 (Test Case Writing)
创建一个纯静态类，编写不依赖场景的测试逻辑。
```csharp
public static class DropAlgorithmTest {
    public static void Run() {
        // 1. 初始化无头黑盒
        CoreBackend core = new CoreBackend();
        core.InitAllSystems();
        
        // 2. 强行注入静态上下文 (极其重要，替代 GameRoot 的作用)
        GameRoot.Core = core; 
        
        // 3. 构造极端测试环境
        var player = core.CurrentPlayer;
        player.Money = 0;
        
        // 4. 执行业务逻辑
        core.Dungeon.SettleDropLogic(); 
        
        // 5. 硬核断言 (Assert)
        if (player.StashInventory.Count > 0) {
            Debug.Log("Drop Logic PASSED.");
        } else {
            Debug.LogError("Drop Logic FAILED: Inventory is empty."); // LogError 会自动让报告变为 FAILED
        }
    }
}
```

### Step 2: 编译并运行 (Compile & Run)
用 Unity MCP 依次执行：

1. `refresh_unity`（`compile=request`）编译最新代码，再用 `read_console` 确认没有编译错误。
2. `run_tests`：`mode=EditMode`，`assembly_names=["P3.SmokeTests.Editor"]`，`include_failed_tests=true`。只跑本次相关用例时加 `test_names=["DropAlgorithmTest.Run"]`；按门禁跑时加 `category_names`（`foundation`、`t0_core`、`p0_core`）。
3. 用 `get_test_job`（`wait_timeout=60`）读取结果。

包装程序集 `UnityClient/Assets/Editor/P3SmokeTests/` 在编译后自动把新测试列为用例，测试本身不需要引用 NUnit。用例名是 `类名.Run`；登记在 `UnityClient/Assets/Editor/P3Validation/program_validation_profiles.json` smoke set 里的入口另带对应分类。

### Step 3: 读取结果并修复 (Fetch & Auto-Heal)
*   **若有失败用例**：读取失败用例的首条错误和堆栈，修改 C# 业务代码，回到 Step 2。
*   **若全部通过**：底层逻辑宣告竣工，可以通知前端同学动手绑定 UI。

已知失败的用例记录在 `agent_status/program.md`；报告结果时区分新增失败和已知失败。

### 兼容路径：AutoTestDaemon
没有 Unity MCP 时，在 PowerShell 中写入触发文件，写 `RUN_ALL_TESTS` 则运行全部测试：
```powershell
Set-Content -Path "UnityClient/Logs/.test_trigger" -Value "DropAlgorithmTest.Run"
```
如果 Unity 处于后台失焦状态且迟迟不开始编译，切回 Unity 窗口点击一下。然后读取报告：
```powershell
Get-Content "UnityClient/Logs/TestReport.json"
```
报告只给出整体 `PASSED` / `FAILED`，失败的测试要从日志里找。

## 六、测试粒度原则

测试优先面向业务行为、玩家可见结果、配置契约和验收场景，不面向内部实现碎片。

- 推荐测试“一个业务闭环”：例如一次战斗结算、一次掉落生成、一次道具使用、一次维护扣费、一次层级推进。
- 测试断言应关注输入、公开 API、领域状态变化、失败原因、事件、报告和可验收输出。
- 不推荐为私有方法、临时中间变量、循环次数、内部排序细节或纯实现步骤写脆弱测试。
- 如果内部算法复杂，可以通过覆盖代表性业务场景、边界场景和失败回滚来验证，而不是把测试拆到每个微小函数。
- 测试名称和日志应描述业务意图，而不是描述实现细节；后续重构实现时，只要业务契约不变，测试应尽量不需要修改。
- 对配置数据的断言应从配置实体或构造对象动态计算，避免把策划数值硬编码进测试。

## 七、P0 报告状态语义

`Invoke-P0Validation.ps1` 的报告必须把失败、警告和验证受限分开：

- `Failed` / `ErrorCount`：真实配置、代码、smoke 或 ArtAcceptance latest 失败。
- `WarningCount`：普通模式可继续但需要跟踪的问题，`-Strict` 下会阻断。
- `Blocked` / `BlockedCount`：工具无法覆盖验证范围，例如 Unity Editor 未运行或 AutoTestDaemon 没有产出匹配报告。
- `ValidationLimitations`：机器可读的受限原因列表，code 使用 `validation_limited:*`，例如 `validation_limited:UnityEditorNotRunning`。

主流程 smoke 必须进入 P0 `SmokeTestRegistry`，并标记 `IsMainFlow=true`，不能只散落在脚本局部变量、聊天记录或单独日志中。

## 八、 测试编写铁律 (Golden Rules for Tests)

1.  **绝对禁止 MonoBehaviour**：测试类必须是纯粹的 `public static class`，类名以 `Test` 结尾，测试入口必须是 `public static void Run()`；这样包装程序集和 AutoTestDaemon 都能自动发现它。
2.  **不要忘记上帝视角赋值**：实机中 `GameRoot` 负责把 `CoreBackend` 存入静态变量。在测试用例里，你必须手动写下 `GameRoot.Core = new CoreBackend();`，否则后续所有依靠 `GameRoot.Core` 寻址的单例全部会报空指针。
3.  **用 Error 宣判失败**：测试本身不需要引用 NUnit。只要在测试中执行了 `Debug.LogError(...)` 或者抛出了任何未捕获的 `Exception`，`run_tests` 的包装用例和 AutoTestDaemon 都会判为失败。

## 九、 测试编写避坑指南 (Common Gotchas)

### Common Mistake: 避免在断言中硬编码配置数据

**Symptom**: 修改了 JSON 配置表（如物品底价 `BaseValue`），业务逻辑依然正确，但自动化测试报错 `FAILED: Expected 1550, got 1400`。

**Cause**: 在测试用例的断言阶段，使用了手算或硬编码的数字（例如：`int expectedMoney = initialMoney + 250 + 800;`），而不是从创建的测试实体中动态获取属性。

**Fix**: 将硬编码的值替换为动态计算：
```csharp
// 不要这样做 (Bad)
// int expectedMoney = initialMoney + 250 + 800; 

// 应该这样做 (Good)
int expectedMoney = initialMoney + loot1.BaseValue + loot2.BaseValue;
```

**Prevention**: 在编写涉及配置表数据（如价格、伤害、容量）的测试断言时，**永远优先使用对象身上的属性 (`entity.Property`) 作为预期值的计算因子**。测试的目的是验证“逻辑计算过程是否正确”，而不是“配置表里的数字是不是固定的 250”。

## 十、两轮验收与报告规范

进入验收阶段的实现切片，后续默认执行两轮验收：

```text
第一轮：做事会话自验
第二轮：外部验收（用户或独立会话）
```

做事的会话先自验一次，确认玩家路径、自动化报告、截图证据和文档验收项已经达到可提交状态；自验不通过时不得提交外部验收。外部验收由用户或独立会话完成（见 `rules/02_智能体任务路由与完成协议.md`），可以使用做事会话提供的运行入口、测试命令、截图目录和已知限制，但必须独立给出最终验收结论。

自验报告和外部验收报告都至少包含 `问题` 和 `建议` 两部分：

### 10.1 问题

`问题` 用于记录阻断完成或影响玩家体验 / 功能正确性的事实缺陷。每条问题必须包含：

- 严重级别：`P0 阻断`、`P1 重要`、`P2 可后续优化`。
- 现象：实际看到的表现、失败断言或错误日志。
- 证据：截图、日志、测试报告路径或复现步骤。
- 对应标准：引用验收文档、设计文档或开发方案中的具体要求。
- 影响：说明为什么影响通过、受限通过或完成标记。

无问题时必须明确写 `问题：未发现阻断进入下一轮 / 完成的问题。`

### 10.2 建议

`建议` 用于记录不直接阻断完成、但能提升体验、稳定性、可维护性或后续验收效率的改进项。每条建议必须包含：

- 建议内容：具体改动，不写空泛表述。
- 价值：说明改善的玩家体验、工程质量或验收稳定性。
- 优先级：`建议 P0`、`建议 P1`、`建议 P2`。
- 是否阻断：明确写 `不阻断`；如果阻断，必须移入 `问题`。

无建议时必须明确写 `建议：暂无额外建议。`

### 10.3 结论

自验报告结论只能使用：

| 结论 | 使用条件 |
|---|---|
| `自验通过，提交外部验收` | 无 P0 / P1 问题，证据完整，玩家路径和自动化断言满足验收标准。 |
| `自验不通过，继续修复` | 存在 P0 / P1 问题，或缺少关键证据。 |
| `自验受限，记录限制后提交判断` | 主路径可跑，但存在明确 `validation_limited:*`，需要外部验收判断限制是否影响结论。 |

外部验收报告结论只能使用：

| 结论 | 使用条件 |
|---|---|
| `通过` | 自验已提交；外部验收未发现 P0 / P1 问题，证据完整，玩家路径和自动化断言满足验收标准。 |
| `受限通过` | 主路径可判断，但存在明确 `validation_limited:*` 限制，且限制不影响本轮结论。 |
| `不通过` | 存在 P0 / P1 问题，或缺少关键证据。 |

标记实现切片完成前，必须能追溯到自验报告和对应外部验收报告；没有外部验收报告时只能标记为自验完成或待验收。

## 十一、Unity MCP 验收入口

- 程序自动化使用 `p3-program-validation`：smoke 测试经 `P3.SmokeTests.Editor` 包装后用 MCP `run_tests` 运行，配置同步和 UI 规格用静态脚本检查。运行时美术检查使用 `p3-art-validation`。不得恢复旧混合 `p3-validation`。
- AutoTestDaemon、`.test_trigger` 和 `Invoke-P0Validation.ps1` 保留为没有 MCP 时的兼容路径和 CI 路径。
- 不用 `manage_ui`、`execute_code`、任意 `execute_menu_item` 作为正式验收步骤。
- 美术轻量检查的截图保存到 `UnityClient/Logs/P3ArtCheck/<RunID>/` 才算证据；`t0_art_seal` 与 `art_regression` 仍走 ArtRun 的 prepare / finalize 截图票据。只在对话里看过的实时截图不是正式证据。
- ArtRun Profile 只记录技术结果和证据，不维护人工主美判断或外部复核状态。

## 十二、程序与美术分开声明

程序验收与美术检查分开进行、分开声明：程序结果不要求截图，也不声明视觉完成；美术检查不运行全量 smoke，也不修改领域状态。

## 十三、里程碑发布门禁

里程碑或发布前按以下清单逐项确认，结论写进 `PROJECT_STATUS.md`：

1. 程序：配置同步后 `run_tests` 全量运行（含配置校验用例 `ConfigValidationSmokeTest`），失败用例都已修复，或已登记为已知问题并经用户确认；UI 规格校验通过。
2. 美术：里程碑范围内的界面都有通过的轻量检查记录；需要封板时有 `t0_art_seal`，大范围 UI 变化后有 `art_regression`。
3. 体验：用户按 `rules/02_智能体任务路由与完成协议.md` 做外部验收，确认玩家路径。

原 `p3-release-validation` 已删除；`tools/agent/p3-validation-core/Merge-P3ReleaseEvidence.ps1` 保留，只用于读取旧 ProgramRunID 与 ArtRunID。
