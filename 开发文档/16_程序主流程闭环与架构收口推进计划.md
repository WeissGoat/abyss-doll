# 程序主流程闭环与架构收口推进计划

> **定位：** 本文档承接用户最新程序优先级：先支持策划 C1-C3 配置，再继续开发“功能未开放完”的主流程闭环，最后做程序架构优化 / 收口。
> 它补足 `agent_status/program.md` 中不能展开过长的执行细节。

---

## 0. 本轮三段优先级总览

本轮不是只做 C1-C3 配置审计。三段优先级都属于程序侧接下来的连续工作，只是执行顺序不同：

| 优先级 | 本轮要解决什么 | 为什么现在要做 | 完成后玩家能感知到什么 |
|---|---|---|---|
| 1. C1-C3 配置程序支持 | 确认前三层正式配置能被运行时解析、校验、固定 seed 验收和主流程消费。 | 策划已经完成 C1-C3 配置源，程序必须先确认“配置可用”，否则后续主流程会踩到字段、引用或旧测试口径问题。 | 前三层怪物、奖励、节点、订单、传闻等不会只是 JSON 存在，而是能在游戏路径里被正确消费。 |
| 2. 主流程可玩闭环 | 把已经存在的数据层 / 领域服务接入玩家正常 UI 路径，补齐下潜、地图、战斗、战利品、阶梯、撤离、出售、维护、再下潜。 | 当前很多系统已经有服务或只读快照，但玩家体验里仍可能不可达、不可操作或状态不回写。 | 玩家能从小镇出发，打一段深渊，带回战利品，回城处理经济和维护，再次下潜。 |
| 3. 程序架构优化 / 收口 | 在主流程打通后，收紧 `GameFlowController`、UI Controller、领域服务、EventBus、Validator 和测试入口职责。 | 功能开放过程中会暴露真实耦合点；此时收口能避免总控和 UI 继续堆业务逻辑。 | 后续新增层、怪物、经济或工坊功能时，不需要改一堆无关 Controller，也更容易测试。 |

这三段的关系是：

```text
配置可消费
-> 玩家路径可连续操作
-> 架构边界收紧并沉淀成可持续扩展框架
```

因此后续执行时不能把“完成 C1-C3 审计”误判为本轮结束；只有 `FLOW` 与 `ARCH` 对应工作包也被执行、验证并回写，才算完成用户这次给出的三段优先级。

### 0.1 当前三段执行状态

这三段要分开判断，避免把“程序已有服务”“玩家已经可玩”和“架构已经收口”混成同一个完成结论。

| 优先级 | 当前状态 | 已有证据 | 接下来怎么推进 |
|---|---|---|---|
| 1. C1-C3 配置程序支持 | 当前批次已完成可做审计，未发现阻断性程序缺口。 | `CFG-01` / `CFG-02` 已完成；配置同步通过；C1-C3 静态交叉审计 error=0、warning=0；P0 报告记录 Unity Editor 未运行导致的 `validation_limited`。 | 不继续占主线；后续只在 Unity runtime 补跑或人工体验发现真实阻断时按 bug / 验收补强处理。 |
| 2. 主流程可玩闭环 | 当前已有一轮可验证程序补强，但不能只用“服务存在”宣称体验完成。 | `FLOW-01..FLOW-07` 已按玩家路径补强并纳入 smoke / P0 入口，包括层选择、地图、战斗 / 节点、战利品、阶梯 / 撤离、小镇出售、工坊维护和黄金路径 smoke。 | 进入体验复核和真实阻断修复：重点看正常 UI 是否可达、按钮是否调用真实服务、状态是否回写、Unity runtime 是否能跑过。若发现断点，按对应 `FLOW-*` 追加 bug 修复，不重开整条基础线。 |
| 3. 程序架构优化 / 收口 | 已完成首批审计、工坊领域操作服务化，以及可读快照 / 可操作服务配对矩阵。 | `ARCH-01` 已输出 12 条耦合点；`ARCH-02` 已新增 `ChassisUpgradeService` / `ProstheticCraftingService` 并让 UI 消费 Result DTO；`ARCH-03` 已明确 Combat / Dungeon / Economy / Growth / Doll 等面板的完成分类。 | 下一步进入 `ARCH-04`：收口 Validator、P0 报告字段、Unity smoke 发现机制和 `validation_limited` 表达；随后处理 `GameFlowController` fallback 与 `DungeonManager` 结算职责。 |

## 1. 总原则

当前程序侧不能再用“数据层已经有服务”替代“玩家可玩闭环已经开放”。

后续判断分三层：

| 层级 | 含义 | 是否等于完成 |
|---|---|---|
| 数据 / 领域服务完成 | 纯 C# 服务、只读快照、配置解析或 smoke test 已存在。 | 不等于玩家可玩完成。 |
| UI 可达 | 玩家能从正常 UI 路径进入该功能。 | 仍不等于完成，必须调用真实服务。 |
| 主流程闭环完成 | 玩家从正常路径操作后，真实领域状态发生变化，并有 smoke / P0 报告证据。 | 可以标记为该段程序功能开放完成。 |

程序推进顺序固定为：

```text
C1-C3 配置程序支持 -> 主流程可玩闭环 -> 架构优化 / 收口
```

UI / 美术接入跟随功能推进：有 Approved 资源和 active 规格时同步接入；没有资源时记录缺口，不阻塞无资源依赖的领域服务和验证。

## 2. 第一优先级：C1-C3 配置程序支持

### 2.1 目标

策划已完成 C1-C3 配置源后，程序侧必须确认这些配置真的能被运行时消费，而不是只停留在 JSON 已落地。

覆盖范围：

- `Items`
- `Rewards`
- `Monsters`
- `Dungeons`
- `Orders`
- `Rumors`
- `Factions`
- `Events`
- 前三层固定 seed 样例

### 2.2 主要任务

| 任务 | 程序动作 | 重点文件 / 系统 | 验收 |
|---|---|---|---|
| `CFG-01` 配置同步与静态审计 | 执行配置同步，检查 C1-C3 是否有字段解析、ID 引用、VisualID、RewardID、MonsterID、NodeType、Order / Rumor 引用缺口。 | `ConfigManager`、`ConfigValidator`、`配置表(JSON)/`、`UnityClient/Assets/StreamingAssets/Configs` | `Sync-Configs.ps1 -Clean` 通过；产出阻断 / 非阻断缺口。 |
| `CFG-02` 旧测试口径修正 | 修正仍按旧 MVP 假设断言的 smoke test，例如 Boss 保底奖励与精英奖励职责混淆。 | `CombatLootDropTest`、`RewardSystemSmokeTest`、`DungeonSeedAcceptanceSmokeTest` | 测试断言与 C1-C3 正式配置口径一致。 |
| `CFG-03` Validator 扩展 | 把前三层正式配置的关键引用纳入 error / warning 分级，避免运行时才发现断链。 | `ConfigValidator`、`15_P0配置Validator与自动验收底座需求.md` | P0 报告能解释每个 error / warning 是否阻塞候选版本。 |
| `CFG-04` 固定 seed 验收 | 对 C1-C3 代表性 seed 输出可读摘要，覆盖 Boss / Stairs 可达、奖励引用、风险提示和层级入口。 | `DungeonSeedAcceptanceService`、`DungeonMapReadabilityTextService` | 固定 seed smoke 可重复，失败原因可读。 |

### 2.3 完成判定

- C1-C3 配置同步无阻断错误。
- P0 报告能稳定输出配置、seed、Unity smoke 和文档校验结果。
- 旧测试不再用历史口径误判正式配置。
- 若 Unity Editor / batchmode 无法运行，必须记录 `validation_limited:<reason>` 和替代证据。

## 3. 第二优先级：主流程可玩闭环

### 3.1 目标

把已经存在的领域服务和只读快照接入玩家正常路径，让项目形成可玩的整体，而不是只有分散的系统测试。

目标玩家路径：

```text
小镇准备
-> 层选择 / 下潜许可
-> 深渊地图
-> 节点选择
-> 战斗 / 非战斗节点
-> 战利品拾取
-> 阶梯 / 安全区
-> 进入下一层或撤离
-> 结算回城
-> 出售 / 订单 / 账单 / 维护 / 成长
-> 再次下潜
```

### 3.2 “未开放完”的识别口径

以下任一情况都算未开放完：

| 类型 | 说明 |
|---|---|
| 入口不可达 | 服务已存在，但玩家正常 UI 没有按钮或路径进入。 |
| 只读不可操作 | 面板只显示快照，关键按钮没有调用真实领域服务。 |
| 状态未回写 | 操作后金币、物品、HP / SAN、层级解锁、订单、声望、维护状态没有真实变化。 |
| 只在 debug / ArtAcceptance 可见 | 截图验收、debug preview 或测试专用对象可见，不等于玩家路径可达。 |
| UI 直接改状态 | Controller 自己改 HP、金币、背包、订单等，不经过领域服务。 |
| 验收不可复现 | 没有 smoke test、固定 seed 或 P0 报告入口证明该段路径。 |

### 3.3 主流程工作包总览

| 工作包 | 类型 | 目标 | 验收重点 |
|---|---|---|---|
| `FLOW-01` | 审计 | 找出玩家正常路径中不可达、假按钮、只读面板、状态不回写和缺测试的断点。 | 输出断点清单和实现顺序。 |
| `FLOW-02` | 功能开放 | 打通层选择、下潜许可和对应层地图进入。 | 已解锁层可进入，未解锁层有原因，地图节点可点击。 |
| `FLOW-03` | 功能开放 | 打通地图节点、战斗、非战斗节点、战利品拾取和返回地图。 | 战斗和节点奖励来自真实服务，拾取 / 放弃状态正确。 |
| `FLOW-04` | 功能开放 | 打通阶梯、安全区、撤离、进入下一层和层级解锁。 | L1 -> L2 -> L3 可跑，撤离结算和下一层入口真实更新。 |
| `FLOW-05` | 功能开放 | 打通小镇经济至少一条真实操作链。 | 出售 / 订单 / 账单至少一项真实改变金币、物品、声望或账单状态。 |
| `FLOW-06` | 功能开放 | 打通工坊成长至少一条真实操作链。 | 维护 / 制造 / 装备 / 交互至少一项真实消耗资源并刷新下潜许可或人偶状态。 |
| `FLOW-07` | 验收 | 把分段能力串成一条黄金路径 smoke / P0 摘要。 | 小镇 -> 深渊 -> 战斗 -> 战利品 -> 回城 -> 出售 / 维护 -> 再下潜可复现。 |

#### `FLOW-01`：玩家路径缺口审计

目标：先列清楚哪些段落是“服务已有但 UI 未开放”，哪些段落是“UI 有但只读 / 假按钮”，哪些段落是“可操作但无验收”。

重点检查：

- `GameFlowController`
- `WorkshopUIController`
- `DungeonStartLayerUIController`
- `DungeonMapUIController`
- `DungeonNodeResultUIController`
- `HUDController`
- `SettlementUIController`
- `WorkshopFormalV1PanelController`
- `WorkshopFormalV1PanelActionService`

输出：

- 主流程断点清单。
- 每个断点的归因：入口、服务绑定、状态回写、表现、验收。
- 后续实现顺序。

#### `FLOW-02`：层选择 / 下潜 / 地图进入闭环

目标：玩家能从小镇进入层选择，选择已解锁层，经过 `DiveReadinessService` 检查后进入对应深渊地图。

关键要求：

- 层选择 UI 只展示 `PlayerProfile` 已解锁层。
- 未解锁层给出可读原因，不强行 StartRun。
- `DungeonManager.StartRunAtLayer()` 是唯一领域入口。
- 地图 UI 消费 `DungeonMapVisibilityService` / `DungeonMapReadabilityTextService`，不自己推断可点节点。

验收：

- 已通层直达可用。
- 未解锁层不可进入且原因可见。
- 进入层后地图节点可点击，节点连接关系不异常。

#### `FLOW-03`：地图节点 / 战斗 / 战利品闭环

目标：玩家能从地图进入战斗或非战斗节点，完成节点后进入战利品拾取或节点结果界面，再回到地图。

关键要求：

- 战斗节点由 `CombatNode` 负责战斗结算归属，完成后抛事件通知外界。
- 怪物意图、战斗时间线、胜负原因使用 `CombatOutcomeReport` / `CombatReadabilityTextService`。
- 战利品来自 `RewardSystem`，拾取进入背包，放弃 / 移出背包关闭后销毁。
- 非战斗节点的 `OutcomeEffects` 和 `RewardID` 走统一节点结果路径。

验收：

- 战斗胜利能看到并处理真实战利品。
- 战斗失败能展示 HP / SAN / 阵营全灭原因。
- 非战斗节点能执行结果并返回地图。
- 相关测试覆盖 Boss 保底奖励、节点奖励、拾取后账本。

#### `FLOW-04`：阶梯 / 安全区 / 撤离 / 进入下一层闭环

目标：玩家打到层末后进入配置出来的 `StairsNode`，选择进入下一层或返回小镇。

关键要求：

- `StairsNode` 来自配置，不写死。
- 进入阶梯 / 安全区调用 `DungeonSafeZoneService` 恢复 HP / SAN。
- 进入下一层不清空本轮战利品账本。
- 返回小镇走撤离结算，不再由 Boss 胜利自动回城。
- 到达第 N 层阶梯时解锁第 `N + 1` 层入口。

验收：

- L1 -> L2 -> L3 路径可跑。
- 阶梯进入下一层后节点可点击。
- 撤离结算能统计本轮带出 / 遗失 / 已拾取战利品。

#### `FLOW-05`：小镇经济操作闭环

目标：回城后玩家能通过小镇 UI 触发至少一条真实经济压力链。

优先链路：

```text
背包 / 仓库物品 -> 出售渠道 / 传闻倍率 -> 金币变化 -> 物品移除
```

后续链路：

- 接订单。
- 查看订单进度。
- 交付订单物品。
- 声望 / 信任 / 奖励变化。
- 日结 / 月租 / 典当反馈。

关键要求：

- 出售不区分“是否战利品”，只要在玩家可出售容器内就可被估值。
- UI 调用 `TownEconomyService`，不直接加金币或删除物品。
- 订单 / 传闻 / 账单的只读概览和操作按钮分开。

验收：

- 基础验收：出售后金币增加、物品减少、反馈可见。
- 基础验收：传闻倍率能影响估值，并由 smoke test 或 P0 摘要覆盖。
- 后续扩展验收：订单接取 / 交付、账单 / 月租或典当至少一条继续接入真实服务；这些不阻塞本轮出售链路完成，但不能被只读面板冒充为可玩完成。

#### `FLOW-06`：工坊成长操作闭环

目标：回城后玩家能做一次真实维护或成长决策，并据此决定是否再次下潜。

优先链路：

```text
维护方案 -> 成本检查 -> 扣金币 / 材料 -> HP / SAN / 磨损 / 侵蚀变化 -> 下潜许可刷新
```

后续链路：

- 义体制造。
- 义体装备。
- 底盘升级。
- 人偶基础交互。
- 材料缺口提示。

关键要求：

- UI 调用 `MaintenanceService`、`GrowthFeedbackService`、`DiveReadinessService`、`DollInteractionService`。
- 失败原因必须来自领域服务结果，而不是 UI 字符串硬写。
- 制造 / 装备 / 维护消耗要覆盖仓库和当前背包成本来源。

验收：

- 一次维护操作能真实改变状态。
- 维护后下潜许可重新计算。
- 材料不足时能显示缺口。

#### `FLOW-07`：整条黄金路径 smoke / P0 摘要

目标：不是只测孤立服务，而是覆盖一条玩家可连续执行的路径。

推荐第一条黄金路径：

```text
从小镇选择 L1
-> 进入地图
-> 完成一个战斗节点
-> 拾取一件奖励
-> 到达阶梯
-> 撤离回城
-> 出售一件物品
-> 执行一次维护
-> 再次下潜许可通过
```

验收：

- smoke test 能输出每一步的状态摘要。
- P0 报告中能引用该 smoke test 的结果。
- 失败时能定位到路径的具体步骤。

## 4. 第三优先级：程序架构优化 / 收口

### 4.1 切入条件

架构收口不是暂停功能开发去大重构。只有满足以下条件之一才进入：

- 某段主流程已可玩，但职责边界明显阻碍下一段继续开发。
- 某个 Controller 或总控继续堆业务规则会违反分层规范。
- 某个功能已有两处以上重复入口或重复状态修改。
- P0 / smoke test 因架构混乱无法稳定验证。

### 4.2 收口目标

| 模块 | 收口目标 |
|---|---|
| `GameFlowController` | 只负责流程状态切换、场景上下文和面板协调，不承载奖励、背包、经济、维护、层级解锁等业务规则。 |
| UI Controller | 只展示状态、收集输入、调用服务、显示结果；不直接改 HP / SAN / 金币 / 背包 / 订单 / 奖励。 |
| 领域服务 | 每个操作返回明确 Result / Report DTO，包含成功、失败原因、状态变化摘要和 UI 可展示文本。 |
| EventBus | 用于跨模块通知，不当成隐藏业务执行入口；事件 payload 必须是快照或结果对象。 |
| ConfigValidator | 从“顺手检查”收口为配置契约门禁，字段、ID、枚举、VisualID、seed 都有明确 error / warning 口径。 |
| Smoke Test | 围绕玩家可见闭环和配置契约，不围绕内部实现碎片写脆弱断言。 |

### 4.3 架构工作包总览

| 工作包 | 类型 | 目标 | 验收重点 |
|---|---|---|---|
| `ARCH-01` | 审计 | 审查主流程打通后暴露出的职责边界问题。 | 明确哪些规则仍在总控或 UI，哪些入口重复，哪些测试脆弱。 |

#### `ARCH-02`：流程编排与领域操作分离

目标：

- 流程编排层只处理“接下来显示哪个界面”。
- 领域操作层处理“状态如何变化”。

推荐模式：

```text
UI Button
-> UI Controller
-> ActionService / DomainService
-> Result DTO
-> EventBus / Controller Refresh
```

禁止模式：

```text
UI Button
-> Controller 直接 player.Gold += n
-> Controller 直接 inventory.Remove(item)
```

1. `CFG-01 -> CFG-04`：先证明 C1-C3 配置可被程序消费。
2. `FLOW-01`：做主流程断点审计。
3. `FLOW-02 -> FLOW-04`：先打通下潜、地图、战斗、战利品、阶梯、结算。
4. `FLOW-05`：开放小镇经济至少一条真实操作链。
5. `FLOW-06`：开放工坊维护 / 成长至少一条真实操作链。
6. `FLOW-07`：补整条黄金路径 smoke / P0 摘要。
7. `ARCH-01 -> ARCH-05`：根据已经暴露的真实耦合点做收口。

每个工作包完成后都要：

- 跑对应 smoke / P0 验证。
- 回写 `agent_status/program.md`。
- 如果影响策划配置或美术资源，写入对应职能状态页或 `PROJECT_STATUS.md` 交接。
- 单独提交，不混入无关 submodule、本地工具或其他 agent 改动。

## 6. 当前明确风险

| 风险 | 处理方式 |
|---|---|
| 服务层完成被误判为可玩完成 | 状态页必须区分“服务完成”“UI 可达”“可操作闭环完成”。 |
| UI / 美术任务压过程序主流程 | UI / 美术只跟随当前功能闭环，不单独横向铺量。 |
| 旧 smoke test 按历史口径误报 | C1-C3 支持阶段优先修测试口径。 |
| 架构收口变成无边界重构 | 只收真实阻碍主流程的耦合点，且每次重构必须有回归测试。 |
| 主流程 smoke 过大不稳定 | 先做分段 smoke，再汇总黄金路径摘要。 |
