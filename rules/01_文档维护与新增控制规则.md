# 文档维护与新增控制规则

> 所有智能体在新增、重写、拆分、归档或调整项目文档前必须先读本规则。

## 核心原则

项目文档以维护为先。能补充既有事实来源的，不新建文档；确需新增时，必须同时检查是否有旧文档需要归档、废弃或合并。文档数量要受控，单篇文档保持高内聚，文档之间保持低耦合。

## 写文档前检查

1. 先检索现有文档：使用 `rg`、`DOCS_INDEX.md`、`docs_index.json`、相关 README、状态页和职能视图确认是否已有承接位置。
2. 判断内容归属：事实写事实文档，进度写状态页，路线写版本规划，交接写承接文档，生成物通过流水线更新。
3. 优先补充已有文档：如果新内容只是现有主题的规则补充、字段补充、验收补充或状态更新，应写回原文档。
4. 不用聊天结论替代文档：进入开发、配置、表现或验收的内容，必须能被对应事实来源独立承接。

## 新增文档门禁

只有同时满足以下条件，才允许新增文档：

1. 有稳定主题和单一职责，不能自然放入既有事实来源。
2. 有明确 owner、`domain`、`update_rule`、状态和后续维护入口。
3. 不会制造第二套进度表、第二套事实来源或跨职能混合台账。
4. 新文档能降低复杂度，而不是把同一主题拆散到更多位置。
5. 已检查相关旧文档、草稿、历史页和重复页，明确是否需要归档、废弃、合并或更新链接。

## 归档与废弃

- 被新文档替代的旧文档，应按目录既有模式移入 `_archive/`，或将 `status` 改为 `historical` / `deprecated`。
- 旧文档仍保留追溯价值时，正文开头应说明当前事实来源指向哪里。
- 归档或废弃后必须更新 README、状态页、`related` 双向关系和必要的入口文档。
- 不保留“看起来仍 active、实际已过时”的文档。

## 设计与实施计划文档

需要先设计、再实施的功能、重构或流程变更，用过程文档承接：

- 设计（spec）写入 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`，实施计划（plan）写入 `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`；不放在 `.codex/`、`tmp/` 或领域目录。
- 两者都是过程文档：补齐元数据头，`type` 为 `design` / `plan`，`source_of_truth: false`。
- 状态：编写和待批准时为 `draft`，执行中为 `active`，实施完成后改为 `historical`，并在正文开头注明实施提交和现行事实来源。
- 实施完成后，规则、契约、配置和流程事实回写到领域事实文档或 Skill，进度回写状态页；spec / plan 不继续充当事实来源。

## 数量控制

- 不新增一两句话的孤立文档；短内容优先补进对应 README、状态页、规则卡、GDD、开发文档或美术文档。
- 不为同一任务建立多张进度表；实现进度回到对应职能状态页和事实文档。
- 不把路线、规则、配置、程序实现、美术交付和验收证据混在同一张横向大表里。
- 长文档如果已经过载，优先按主题边界拆分；拆分后必须保留清晰入口和归属说明。

## 关联与验证

新增或调整文档时必须：

1. 补齐 YAML 元数据头，至少包含 `id`、`title`、`type`、`role`、`domain`、`status`。
2. 维护 `related` 双向互链，避免断链、自指和重复关联。
3. 更新对应目录 README、职能状态页、项目状态页或版本规划入口。
4. 生成物目录不手写维护；通过对应脚本刷新。
5. 运行 `.\tools\docs\Generate-DocsIndex.ps1` 和 `.\tools\docs\Validate-Docs.ps1`，并把失败原因回写到状态页或最终回复。

## 规则命名口径

后续项目里的 `rules/` 默认指根目录的 agent 必读规则。策划业务规则统一称为 `规则卡`，路径为 `设计文档/规则卡/`；程序专项规则保留在 `开发文档/rules/`。
