# 智能体任务路由与完成协议

> 本文件定义 Project P3 稳定的跨职能执行协议。游戏规则、程序契约、视觉规格、配置内容和当前状态仍以对应领域事实文档与状态页为准。

## 适用范围

本协议适用于需要设计、实现、配置、素材接入、验证、验收或状态回写的实际任务。根入口 `AGENTS.md` 负责选择职责路径；本文件负责说明选定职责后如何执行和完成。

本文件不记录当前 T0-T4 进展、不维护职能必读清单、不替代 GDD、开发文档、美术文档、配置源或状态页。

## 任务角色与主责任选择

一个任务必须有且只有一个主责任角色，其他角色作为受影响职能或外部验收方。

1. 改变玩家体验主线、系统开放节奏、深渊包装、全局优先级或完成口径：游戏导演 / 制作人负责。
2. 补齐 T0-T4 某个游戏时长段的玩家旅程、剧情 / 新手节奏、系统自然开放和下一段钩子：0-12 小时细案 Owner 负责。
3. 已有完成细案，目标是落地一个玩家能看到或做到的结果：实现 Owner 负责。
4. 仅修改 GDD、数值、配置意图或配置源：主策 / 数值职责负责，并按需要接受实现 Owner 统筹。
5. 仅修改 Unity、领域服务、架构、Validator 或自动测试：主程 / Unity 职责负责，并按需要接受实现 Owner 统筹。
6. 仅修改 UI、视觉规格、素材生产或运行时美术验收：主美 / UI 职责负责，并按需要接受实现 Owner 统筹。
7. 仅处理纯 UGUI 表现层接入：UI 程序职责负责，但玩法规则和领域状态仍属于程序领域服务。
8. 仅处理文档元数据、索引和关系网：知识库智能体负责。
9. 长期、拆分、恢复或持续执行：在已有详细来源材料的前提下使用 P3 Mission；Mission 不是新的事实来源。

当任务同时命中多个角色时，优先按玩家结果选择主责任角色。已有细案的跨职能落地默认由实现 Owner 负责；职能总监默认负责总体设计把关和外部验收，不作为常规实现分包。

## 标准责任流水

默认工作模式是：

```text
细案 Owner 统一设计 -> 实现 Owner 纵切负责 -> 职能总监验收
```

实现 Owner 围绕单一玩家结果按以下顺序推进：

```text
证据审计
  -> 阅读细案与领域事实
  -> 本切片具体方案
  -> 策划详细设计
  -> 配置源落地
  -> UI/UX 与美术设计 / 素材
  -> 程序功能与素材接入
  -> Owner 自验
  -> 职能总监 / 游戏导演外部验收
  -> 状态与事实回写
```

并非每个切片都必须修改所有职能文件，但 Owner 必须明确哪些阶段属于本轮、哪些不适用、哪些由专工协助、哪些等待外部验收。

未完成设计的时长段不作为实现 Owner 正式开工依据。若只有一句目标、聊天结论或模糊 TODO，先由对应职责补齐详细设计或计划事实，再进入实现或 P3 Mission。

## 实现切片承接字段

实现切片至少写清以下内容：

- 玩家结果：完成后玩家能看到、理解或做到什么。
- 范围外：本轮明确不做什么。
- 细案来源：对应 `14` 的时长段 / 细案切片 ID、目标细案文档和 `13` 的模块宏观设计行。
- Owner 责任流水：本轮覆盖哪些阶段，哪些阶段由专工协助。
- 事实来源：目标 GDD、规则卡、配置 README、开发文档、美术规格、状态页。
- 允许改动范围：配置、代码、UI、素材和文档中哪些路径可以改。
- 需要验收的主职能：主策、主程、主美 / UI 或游戏导演中的哪些角色需要验收。
- Owner 自验：玩家路径、固定样例、截图、报告、自动测试或人工复核。
- 外部验收：验收人、验收入口和未验收时允许声明的边界。
- 验证证据：smoke、P0、配置校验、ArtAcceptance、人工验收或 `validation_limited:*`。
- 状态回写：所有受影响状态页、事实文档和必要的全局入口。

## Owner、自验、外部验收与专工

### Owner

Owner 对同一个玩家结果的方案一致性、实现链路、证据整理和状态回写负责。实现 Owner 可以跨职能修改，但必须遵守所有受影响领域的事实来源与工程边界。

### Owner 自验

Owner 自验是第一层验收，证明玩家路径或目标结果已按约定运行，并整理可复核证据。Owner 自验不等于最终完成。

### 外部验收

最终完成需要对应主策、主程、主美 / UI 视觉总监或游戏导演 / 制作人的外部验收。验收未完成时，只能声明已获得的证据级别，例如“实现接通”“Owner 自验通过”“条件通过”，不得写成最终完成。

### 专工

图片生成、大批量素材处理、大规模配置填充、批量校验等耗时工作可以交给专工。专工必须获得明确的输入、输出、允许改动范围和验收标准，只交付指定产物，不自行改变体验方向、规则方向、系统优先级或完成口径。

## 防重复派发与完成判定

- 开工前检索对应状态页和事实文档。已完成或进行中的同名玩家结果不得重复派发，只能建立缺口补齐、验收修复、表现补强、字段迁移、配置补齐或数值校准子项。
- 路线条目、字段说明、README、审计结论、任务拆分、ID 锁定和修改前设计不等于实现或配置完成。
- 配置只有在 `配置表(JSON)` 源落地、同步通过、关键引用 error 为 0，并具有 Validator、固定样例或人工复核证据后，才能标记 `配置完成`。
- 服务存在但正常 UI 不可达、静态面板存在但状态不变化、debug preview 或只读快照存在，都不能直接标记玩家结果完成。
- 没有验收证据不得把条目标记为 `已完成`。
- `11` 和其他需求承接文档不维护实现进度；实现进度回到对应状态页和事实文档。

## 状态与事实回写矩阵

| 变化类型 | 必须回写 | 条件性回写 |
|---|---|---|
| 项目阶段、总目标、跨职能交接或阻塞 | `PROJECT_STATUS.md` | `agent_status/director.md` |
| 玩家体验主线、开放节奏、深渊包装、Owner 工作流、优先级或全局完成口径 | `agent_status/director.md` | `PROJECT_STATUS.md`、`13`、必要的 `09` |
| T0-T4 细案、实现切片入口、玩家路径、验收样例或细案状态 | 目标细案、`14`、`agent_status/director.md` | `PROJECT_STATUS.md`、`13`、`09` |
| 策划、数值、GDD 或配置工作 | `agent_status/design.md` 和目标设计 / 配置事实 | `PROJECT_STATUS.md`、导演状态 |
| 程序、Unity、Validator 或自动测试工作 | `agent_status/program.md` 和目标开发事实 | `PROJECT_STATUS.md`、导演状态 |
| 美术、UI、素材或运行时美术验收工作 | `agent_status/art.md` 和目标美术事实 | `PROJECT_STATUS.md`、导演状态 |
| 同一玩家结果涉及多个职能 | 所有受影响职能状态页和各自事实文档 | 全局入口按变化类型判断 |

状态页至少维护：`最后更新`、`最近完成`、`当前关注`、`下一步建议`、`问题 / 阻塞`，并提供关键证据入口。记录必须简短、事实化、可延续，不粘贴聊天记录。

如果产生给其他职能的交接，同时写入 `PROJECT_STATUS.md` 和目标职能状态页。不要用一条跨职能混合执行行替代各职能事实。

## 验证受限与阻塞记录

无法完成某项验证时，不得静默跳过。应记录：

- `validation_limited:<reason>`：环境或外部条件限制了验证范围，例如 Unity Editor 未运行。
- 已执行的验证及结果。
- 未执行的验证及原因。
- 当前允许声明的边界。
- 后续补验入口。

阻塞只有在实际无法继续推进时记录。困难、耗时、存在警告或需要后续优化不自动等于阻塞。

## Git 与工作区完成要求

- 工作区可能已有用户或其他智能体的改动；不得回滚、覆盖或顺带清理无关脏文件。
- 开工前和提交前查看 `git status --short`，明确已有改动和本任务改动。
- 只暂存当前任务相关文件；大型工作区 checkpoint 必须明确排除本地目录、生成缓存和未授权 submodule 内部改动。
- `tools/ai-image-gateway` 是 submodule；除非任务明确处理该子模块，否则不在父仓库提交其内部改动。
- 移动、复制或重命名 Unity 资产时必须同步处理 `.meta`，保留 GUID。
- 生成物通过对应流水线刷新；除非任务明确修复生成物，不手写修改生成目录。
- 提交前运行与风险相称的验证，并在最终回复中区分“验证通过”“条件通过”“仅 checkpoint”或 `validation_limited:*`。
