# 智能体任务路由与完成协议

> 本文件定义 Project P3 稳定的跨职能执行协议。游戏规则、程序契约、视觉规格、配置内容和当前状态仍以对应领域事实文档与状态页为准。

## 适用范围

本协议适用于需要设计、实现、配置、素材接入、验证、验收或状态回写的实际任务。根入口 `AGENTS.md` 负责选择职责路径；本文件负责说明选定职责后如何执行和完成。

本文件不记录当前 T0-T4 进展、不维护职能必读清单、不替代 GDD、开发文档、美术文档、配置源或状态页。

## 三条执行道

开工先选道，拿不准时选标准道；任务中途一旦碰到严格道的操作，就按严格道处理。

| 道 | 适用 | 要求 | 回写 |
|---|---|---|---|
| 探索道 | 原型、概念图、玩法 / UI 试做、技术 spike、方案对比 | 产出只留在探索区（工作分支、`tmp/`、`_IncomingAI` 候选）；不碰 Approved、`配置表(JSON)`、正式场景 / Prefab 和 active 事实文档；结论只算探索结论，不声明完成 | 不写状态页；值得保留的结论转成标准道任务 |
| 标准道（默认） | 常规代码、配置、文档、素材生产与标准资产入库 | 相关测试或校验通过；声明不超过证据；遵守全局硬边界 | 只在状态页的当前关注、阻塞或交接变化时改一行 |
| 严格道 | Owner 完整模块或玩家结果；不可逆或高成本操作（覆盖 Approved 或已接入资产、移动 Unity 资产、删除数据）；核心身份资产（主角立绘套组、首次风格锚点）；发布门禁 | 下文 Owner 责任流水、实现切片承接字段、自验与外部验收 | 按状态与事实回写矩阵 |

## 元工作预算

流程、校验器、文档治理、美术管线和 agent 工具都是元工作：

- 只在直接解阻当前优先级的玩家结果，或修复已经发生的问题时做；不为假想风险预先加门禁。
- 新增门禁、状态值或必填字段前，写明它拦住的真实问题；说不出来就不加。
- 脚本已经强制的规则不在 Skill 和文档里复述；文档只写意图、入口和需要人判断的地方。
- 开工健康检查会显示距最近一次游戏代码 / 配置改动的天数；超过一周没有游戏改动时，下一项工作优先回到当前优先级的玩家结果。

## 领域与 Owner 做法

Role 指领域：`全局`、`游戏导演`、`剧情`、`策划`、`程序`、`美术`、`知识库`。领域决定读哪套 View、写哪个状态页、文档由谁维护。任务按主要改动归到一个领域；改动跨多个领域时，读取并回写每个受影响的领域。

1. 玩家体验主线、系统开放节奏、深渊包装、全局优先级或完成口径：游戏导演 / 制作人。
2. 剧情大纲、叙事结构、角色关系、对白、CG / 漫画叙事一致性：剧情。
3. GDD、数值、配置意图或配置源：策划。
4. Unity、领域服务、架构、纯 UGUI、Validator 或自动测试：程序。
5. UI 视觉、视觉规格、素材生产、Manifest、VisualID 或运行时美术验收：美术。
6. 文档元数据、索引和关系网：知识库。
7. 项目级入口、状态和根规则：全局。

跨领域交付一个完整模块或玩家结果时，走严格道并按下文 Owner 做法推进。Owner 不是 Role：做事的会话按需切换领域视角，但每个领域的事实和状态写回各自的文档与状态页。长期、拆分、恢复或持续执行使用 P3 Mission，Mission 每行写实际领域。

## Owner 做法（严格道）

严格道下跨领域交付的默认工作模式是：

```text
做事的会话负责完整模块 -> 按需切换领域视角 -> 用户或独立会话外部验收
```

围绕完整模块或玩家结果按以下顺序推进：

```text
证据审计
  -> 阅读细案与领域事实
  -> 本切片具体方案
  -> 策划详细设计
  -> 配置源落地
  -> UI/UX 与美术设计 / 素材
  -> 程序功能与素材接入
  -> 自验
  -> 外部验收（用户或独立会话）
  -> 状态与事实回写
```

并非每个切片都必须修改所有领域的文件，但必须写明哪些阶段属于本轮、哪些不适用、哪些交给独立会话按某个领域处理、哪些等待外部验收。

未完成设计的时长段不作为进入实现阶段的正式依据。若只有一句目标、聊天结论或模糊 TODO，先由对应领域补齐详细设计，再进入实现或 P3 Mission。

## 设计与执行

需要先设计再实施的功能、重构或流程变更按以下顺序推进：

```text
设计 spec（含实施步骤，用户复核后定稿） -> 执行 -> 回写领域事实与状态页 -> spec 标记 historical
```

- 实施步骤写在 spec 末尾，不再单独写 plan。存放位置、元数据和状态规则见 `rules/01_文档维护与新增控制规则.md`。
- 单次会话能完成的直接执行；长期、跨会话或需要恢复的执行，用定稿 spec 生成 P3 Mission，进度只记在 Mission CSV。
- 探索道、小修复和单步改动不需要 spec，直接按本协议执行和回写。

## 实现切片承接字段（严格道）

严格道的实现切片至少写清以下内容：

- 玩家结果：完成后玩家能看到、理解或做到什么。
- 范围外：本轮明确不做什么。
- 细案来源：对应 `14` 的时长段 / 细案切片 ID、目标细案文档和 `13` 的模块宏观设计行。
- Owner 做法：本轮覆盖哪些阶段，哪些阶段交给独立会话按指定领域处理。
- 事实来源：目标 GDD、规则卡、配置 README、开发文档、美术规格、状态页。
- 允许改动范围：配置、代码、UI、素材和文档中哪些路径可以改。
- 需要外部验收的领域：剧情、策划、程序、美术或游戏导演中的哪些。
- 自验：玩家路径、固定样例、截图、报告、自动测试或人工复核。
- 外部验收：验收人、验收入口和未验收时允许声明的边界。
- 验证证据：smoke、P0、配置校验、ArtAcceptance、人工验收或 `validation_limited:*`。
- 状态回写：所有受影响状态页、事实文档和必要的全局入口。

## 自验、外部验收与独立委派

### Owner 做法的责任

按 Owner 做法交付时，做事的会话对方案一致性、跨领域协调、实现链路、证据整理和状态回写负责，并遵守所有受影响领域的事实来源与工程边界。

### 自验

做事的会话完成的验收都是自验：证明玩家路径或目标结果已按约定运行，并整理可复核证据。自验不等于最终完成。

### 外部验收

外部验收由做事会话以外的人或会话完成：

- 体验、方向、优先级和最终完成口径：由用户（制作人）验收。
- 剧情、策划、程序、美术的专业复核：新开一个独立会话，按对应 View 和验收标准检查，并把结论写回状态页。

外部验收未完成时，只能声明已获得的证据级别，例如“实现接通”“自验通过”“条件通过”，不得写成最终完成。

### 独立委派

把某个领域的一项工作交给独立会话时，给出明确的输入、输出、允许改动范围和验收标准。被委派的会话只交付指定产物，不自行改变体验方向、规则方向、系统优先级或完成口径。

## 防重复派发与完成判定

- 开工前检索对应状态页和事实文档。已完成或进行中的同名玩家结果不得重复派发，只能建立缺口补齐、验收修复、表现补强、字段迁移、配置补齐或数值校准子项。
- 路线条目、字段说明、README、审计结论、任务拆分、ID 锁定和修改前设计不等于实现或配置完成。
- 配置只有在 `配置表(JSON)` 源落地、同步通过、关键引用 error 为 0，并具有 Validator、固定样例或人工复核证据后，才能标记 `配置完成`。
- 服务存在但正常 UI 不可达、静态面板存在但状态不变化、debug preview 或只读快照存在，都不能直接标记玩家结果完成。
- 没有验收证据不得把条目标记为 `已完成`。
- `11` 和其他需求承接文档不维护实现进度；实现进度回到对应状态页和事实文档。

## 状态与事实回写矩阵

本矩阵用于严格道，以及标准道中状态真正发生变化的情况；标准道每次只改受影响状态页的一行，探索道不回写。

| 变化类型 | 必须回写 | 条件性回写 |
|---|---|---|
| 项目阶段、总目标、跨职能交接或阻塞 | `PROJECT_STATUS.md` | `agent_status/director.md` |
| 玩家体验主线、开放节奏、深渊包装、Owner 做法、优先级或全局完成口径 | `agent_status/director.md` | `PROJECT_STATUS.md`、`13`、必要的 `09` |
| T0-T4 细案、实现切片入口、玩家路径、验收样例或细案状态 | 目标细案、`14`、`agent_status/director.md` | `PROJECT_STATUS.md`、`13`、`09` |
| 策划、数值、GDD 或配置工作 | `agent_status/design.md` 和目标设计 / 配置事实 | `PROJECT_STATUS.md`、导演状态 |
| 程序、Unity、Validator 或自动测试工作 | `agent_status/program.md` 和目标开发事实 | `PROJECT_STATUS.md`、导演状态 |
| 美术、UI、素材或运行时美术验收工作 | `agent_status/art.md` 和目标美术事实 | `PROJECT_STATUS.md`、导演状态 |
| 同一玩家结果涉及多个领域 | 所有受影响领域的状态页和各自事实文档 | 全局入口按变化类型判断 |

状态页至少维护：`最后更新`、`最近完成`、`当前关注`、`下一步建议`、`问题 / 阻塞`，并提供关键证据入口。记录必须简短、事实化、可延续，不粘贴聊天记录。

如果产生给其他职能的交接，同时写入 `PROJECT_STATUS.md` 和目标职能状态页。不要用一条跨职能混合执行行替代各职能事实。

## 验证受限与阻塞记录

无法完成某项验证时，不得静默跳过。应记录：

- `validation_limited:<reason>`：环境或外部条件限制了验证范围，例如 Unity Editor 未运行。
- 已执行的验证及结果。
- 未执行的验证及原因。
- 当前允许声明的边界。
- 后续补验入口。

阻塞只有在实际无法继续推进时记录。困难、耗时、存在警告或需要后续优化不自动等于阻塞。

## Git 与工作区完成要求

- 工作区可能已有用户或其他智能体的改动；不得回滚、覆盖或顺带清理无关脏文件。
- 开工前和提交前查看 `git status --short`，明确已有改动和本任务改动。
- 只暂存当前任务相关文件，按任务或 Mission 行提交，避免把多项改动打包成一次 checkpoint；确需 checkpoint 时排除本地目录、生成缓存和未授权 submodule 内部改动。
- `tools/ai-image-gateway` 是 submodule；除非任务明确处理该子模块，否则不在父仓库提交其内部改动。
- 移动、复制或重命名 Unity 资产时必须同步处理 `.meta`，保留 GUID。
- 生成物通过对应流水线刷新；除非任务明确修复生成物，不手写修改生成目录。
- 提交前运行与风险相称的验证，并在最终回复中区分“验证通过”“条件通过”“仅 checkpoint”或 `validation_limited:*`。
