# 游戏导演 / 制作人阅读入口

> 本页是游戏导演 / 制作人智能体的开工导航，不替代 GDD、开发文档、美术文档、配置源或状态页。

## 开工顺序

1. `PROJECT_STATUS.md`：确认当前阶段、顶层目标、总优先级、跨职能交接和阻塞项。
2. `agent_status/director.md`：确认游戏导演 / 制作人侧当前判断、最近完成和下一步建议。
3. `版本规划/13_正式版全局体验总线与开放节奏.md`：确认玩家体验主线、系统开放节奏、深渊包装和任务 Owner 工作流。
4. `版本规划/14_0-12小时候选主循环细案设计.md`：确认 0-12 小时 T0-T4 细案索引、推进顺序和承接规则；实现 Owner 只承接已完成细案的实现切片。
5. `版本规划/0-12小时细案/` 中的目标细案：确认本切片玩家路径、系统开放、输入输出、UI / 美术表达和验收样例。
6. `版本规划/09_正式版核心纵切开发路线.md`：确认正式版核心纵切的开发优先级、长期节点、职能进度入口和防重复派发规则。
7. `版本规划/11_纵切批次与需求文档承接矩阵.md`：确认 GDD / 功能优先级的批次、完成口径和需求文档承接。
8. 按任务涉及范围读取 `agent_status/design.md`、`agent_status/program.md`、`agent_status/art.md`。
9. 进入具体系统事实来源：GDD、开发文档、美术路线、配置 README 或数值模型。

## 工作模式

- 默认按 `细案 Owner 统一设计 + 实现 Owner 纵切负责` 推进。
- 0-12 小时 T0-T4 由细案 Owner 逐个完善；`14` 维护索引和承接规则，具体细案在 `版本规划/0-12小时细案/` 中一案一文。未细化完成的切片不作为实现 Owner 正式开工依据。
- 实现 Owner 按 `证据审计 -> 阅读细案 -> 本切片具体方案设计 -> 配置源落地 -> UI/UX 与美术接入方案 -> 程序接入 -> Owner 自验 -> 职能总监验收 -> 状态回写` 串完整玩家结果。
- 实现 Owner 可以跨配置、程序、UI、美术和验证改动，但必须遵守细案、对应事实来源和工程边界；Owner 自验不替代主策 / 主程 / 主美 / 游戏导演的外部验收。
- 主策 / 主程 / 主美默认负责验收和整体设计，不作为常规实现分包。
- 图片生成、大批量素材处理和大规模配置填充可以拆给专门 agent，但必须有明确输入、输出、验收和回写路径，且不得自行改变体验目标、规则方向或完成口径。
- 旧 `agent_status/pm.md` 和 `知识库/views/pm.md` 只保留为兼容入口，不再作为 active 路由。
